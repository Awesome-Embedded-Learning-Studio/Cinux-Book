# 07 · GDB 回路:调试器说得出的话,和它说不出的东西

上一篇收尾的时候,咱们让 GDB 停在了 `0x7c00`,用 `si` 走了一步,看着 `eip` 从 `0x7c00` 挪到 `0x7c03`,那会儿笔者说这几个动作只是碰了一下,再往下的活都留给今天。上一篇末了还提过单步那对开关,今天要碰的正是它俩在裸机上的样子。

这一天迟早会来。您在 `0x7c00` 上按了断点,`continue` 过去,看着串口那头一动不动,心里就开始盘算:是不是我把值送错了地方,是不是我该看看它到底算出了什么。这类追查咱们会做很多遍,一直做到您闭着眼都能敲出那几行命令为止。可它有个前提,您得信它给出来的数是真数。今天这一趟,笔者打算把这个前提也翻一翻。

今天要做的活接着上一篇往下:让它停在咱们指的地方,把当时那几个数掏出来看,该改的当场改。这一串动作往后要一遍一遍地走,改一点东西,就照着走一圈。笔者管它叫回路,它不玄,就是转一圈,再转一圈。

## 条件断点:让它只在您关心的那一趟停下来

用的还是那枚 512 字节的镜像,源码七行,`as` 和 `ld` 的开关跟上一篇写得一模一样,您手上已经有的可以直接再用,不必重编。为了写下这一篇,笔者把 QEMU 用 `setsid` 挂到后台,给 `timeout` 留了 25 秒,省得它一直占着那个终端:

```bash
setsid nohup timeout 25 qemu-system-i386 \
  -drive format=raw,file=mbr.bin,if=floppy -boot a \
  -nographic -display none -S -gdb tcp:127.0.0.1:1253 &
```

端口这一回用的是 `1253`,跟上一篇那个 `1235` 不冲突,您在自己机器上随便挑一个空着的就行。接上以后,咱们让它在把那个字节装进 `al` 的地方停下来。

断点那句可以带条件,写法是在地址后面接一个 `if`,拿寄存器的名字当变量用,咱们这么写,GDB 认得:

```gdb
set architecture i8086
set confirm off
target remote 127.0.0.1:1253
break *0x7c03 if $dx == 0x3f8
continue
info registers eip dx
```

咱们跑出来是这样:

```text
Breakpoint 1 at 0x7c03

Breakpoint 1, 0x00007c03 in ?? ()
eip            0x7c03              0x7c03
dx             0x3f8               1016
```

`0x7c03` 是 `movb $0x4b,%al`,往 `al` 里装那个 `K` 的字节,真正把字节送出去的 `outb %al,%dx` 在 `0x7c05`。它停在这儿,说明条件是成立的,上一条 `movw $0x3f8,%dx` 已经把 `dx` 写成了 `0x3f8`,两条凑上,`if` 才放行。您把这个条件改成 `$dx == 0x2f8`,它就不会在这儿停,`continue` 会一直往下跑,直到在那个死循环里出不来,您只能等 `timeout` 把它收走。这一手在代码长起来以后很管用,不然一颗 CPU 走一遍,您得按几万次 `continue` 才轮得到想看的那一下。

还有一处得记上。上一篇咱们从头到尾只下过一个断点,`break *0x7c00`,那时候笔者心里嘀咕过一句:一次是不是只能挂一个?今天在同一台机器、同一个会话里试了一趟:敲 `break *0x7c00` 停一次,再敲 `break *0x7c05` 停一次,两次都停住了,稳稳当当。这个顾虑笔者撤回,断点想下几个下几个。那一趟的屏幕就长这样:

```text
Breakpoint 1 at 0x7c00
Breakpoint 1, 0x00007c00 in ?? ()
eip            0x7c00              0x7c00
cs             0x0                 0
Breakpoint 2 at 0x7c05
Breakpoint 2, 0x00007c05 in ?? ()
eip            0x7c05              0x7c05
```

## 寄存器当场改:`set` 一句话,下一句就生效

有一件事今天想当着您的面做一次。假设您手滑了,或者程序拐到了您不想让它去的地方,寄存器是可以现场拨回去的。让它停在 `0x7c03`,咱们再看:

```text
eip            0x7c03              0x7c03
（执行 set $eip = 0x7c00 后）
eip            0x7c00              0x7c00
```

那句 `set $eip = 0x7c00` 敲下去,回车,`info registers eip` 回来的就是新值,中间没有任何缓冲。您看到的两行,一行是改之前,一行是改之后,括号里那半句是笔者加进来交代动作的,不是 GDB 印的,您照着敲的时候它不会出现。

这里能改的不止 `eip`。`$dx`、`$ax` 这些一样能拿 `set` 拨,写法就是把寄存器的名字前面加一个 `$`。改完咱们再拿 `info registers` 回读,改了什么,它就印什么。

## 看内存:签名那两格是查得到的

扇区末尾的 `55 aa`,咱们上一篇是在文件里看的,用的是 `xxd`。程序跑起来以后它也在,就在 `0x7dfe` 开头的两个字节里:

```text
0x7dfe:	0x55	0xaa
```

命令是 `x/2xb 0x7dfe`。`x` 是看内存,`2` 是要看几格,`xb` 里的 `x` 说的是按十六进制印、`b` 说的是每格一字节。`0x7c00` 加上 510 正好是 `0x7dfe`,咱们在链接脚本里让游标摁下去的两格就落在这儿。文件末尾的两格,上一篇在 `xxd` 里看过,这回是机器里的同一处,印出来还是 `55 aa`,两边一模一样的时候,笔者对着那行看了几秒。

## 把这一串攒成一个脚本

上面这几屏,每一屏都得敲一遍命令,敲多了人会烦。咱们干脆把它们写进一个文件,以后让 GDB 自己读。

QEMU 那一半咱们没动,命令跟上面那个一字不差,只把端口换成了 `1255`,这样两场实验各用各的,不会搅在一起。

咱们写的 `.gdbinit`,内容是这样:

```gdb
set architecture i8086
set confirm off
target remote 127.0.0.1:1255
break *0x7c00
continue
info registers cs eip ax
x/2xb 0x7dfe
detach
quit
```

咱们把这一行敲下去,让它自己去读那个脚本:

```bash
gdb -q -nx -batch -x .gdbinit
```

敲下去的 `gdb` 那一行上有四个开关,得跟您交代清楚,不然哪天它自作主张去读了别的文件,您会一头雾水。`-q` 是别印那几行版本声明,省版面。`-nx` 是不去读任何一个默认的初始化文件,您家目录里的 `~/.gdbinit` 也好,系统里摆着的也好,今天都不参加演出,跑的只有笔者手上写好的这个脚本。`-x` 后面跟着文件的名字,意思是把它当脚本执行,一行一行往下走。`-batch` 是执行完就退,不留一个交互的提示符在您面前挂着。

咱们让脚本跑起来,拿到的是这样(前面手敲的那几屏里的寄存器行,跟这里一字不差,新面孔只有签名处的两格):

```text
Breakpoint 1 at 0x7c00

Breakpoint 1, 0x00007c00 in ?? ()
cs             0x0                 0
eip            0x7c00              0x7c00
ax             0xaa55              -21931
0x7dfe:	0x55	0xaa
```

这一屏里有三件东西得给咱们提个醒。`cs` 印的是 `0x0`,它不是笔者在脚本里写错了什么。`eip` 是 `0x7c00`,`x/2xb` 拿到的两格也是对的,这一屏里除了段寄存器,别的都挺好。`ax` 里那个 `0xaa55` 不是咱们写进去的,那七行里没有哪一句碰过 `ax`,那是 BIOS 把扇区搬过来的时候留下的旧值。签名落在文件末尾,跟 `ax` 里这个数是两处地方。

脚本写进文件以后,咱们再看一眼那一屏,敲的就是上面那一行 `gdb`。这回没有敲 `break`,也没有敲 `continue`,`cs`、`eip`、`ax` 和签名两格自己就印在了屏幕上。

## 回路:换掉源码里的一个数,看字节跟着动哪儿

到这儿,命令都齐了,咱们把它们串成一件真事。笔者这一回要动的是那个往 `al` 里放字符的地方。改之前它写的是一个字符 `'K'`,笔者把它换成一个十六进制数 `0x51`,也就是字母 `Q`:

```diff
-    movb $'K', %al
+    movb $0x51, %al
```

改完重编重链,咱们敲的还是上一篇的两条:`as --32 -o mbr.o mbr.s` 把源码编成目标文件,`ld -m elf_i386 -T tiny-raw.ld --oformat binary -o mbrQ.bin mbr.o` 再把它链成裸产物。这一篇用的还是上一篇的 `tiny-raw.ld`,不是 04 篇的 `tiny.ld`。跟上一篇比,开关一个没动,变的是两样:源码里那个数,和产物的名字(`mbr.bin` 换成了 `mbrQ.bin`):

```text
$ ls -l mbr.bin mbrQ.bin
-rwxr-xr-x 1 … 512 … mbr.bin
-rwxr-xr-x 1 … 512 … mbrQ.bin

$ xxd -l 8 mbr.bin
00000000: baf8 03b0 4bee ebfe                      ....K...
$ xxd -l 8 mbrQ.bin
00000000: baf8 03b0 51ee ebfe                      ....Q...
```

两边的尺寸那一栏都是 512,那个长的 `-rwxr-xr-x` 和一串属主时间,笔者用 `…` 收掉了,跟这一趟没关系。

前八个字节摆在一起看最有意思。除了偏移 4 上那个字节从 `4b` 变成 `51`,其余七个字节逐字节相同:`4b` 是 ASCII 的 `K`,`51` 是 `Q`。笔者改的是源码里的一个数,机器码里真正跟着动的只有偏移 4 上的一位,别的地方连一个 bit 都没漂。

到这一步,咱们把这一篇叫回路的那件事凑齐了:改一行,重编,重新断在同一个地方,只看该看的那几个。它为什么可靠,笔者琢磨过一阵。这一路上每一个数都是咱们自己放进去的,源码里的立即数和断点地址,都是笔者写下去、挑定的,`xxd` 印出来的字节是文件里的原样。回路不靠谁替咱们作证,它只负责把“笔者改的”和“机器里长的”摆到一起,让咱们自己对。

## `ni` 为什么在裸机上退化成 `si`

回路可靠,可不等于照着它问什么都能问出真话。今天咱们碰到的第一处,是它手上的说明不够用。

上一篇已经领教过一回,笔者叫它反汇编那一屏。今天再让 `x/4i 0x7c00` 说一遍——上次只给了头一行,这回把四行一起印全,记性好的朋友可以直接跳过:

```text
=> 0x7c00:	mov    $0x51b003f8,%edx
   0x7c05:	out    %al,(%dx)
   0x7c06:	jmp    0x7c06
   0x7c08:	add    $0x0,%al
```

它把 `ba f8 03`(`movw $0x3f8,%dx`)和 `b0 51`(`movb $0x51,%al`)硬拼成了一条 `mov $0x51b003f8,%edx`,五个字节当成一条,后面每一条指令的地址就都跟着错开了。可咱们知道实际的头一条只有三个字节,证据也在上一篇里:`si` 一次,`eip` 从 `0x7c00` 走到 `0x7c03`。

这一屏是按上一篇的 `tiny-raw.ld` 链出来的产物解的。末那一行解的是镜像偏移 8 起那几个字节,而那几个字节是什么、还在不在,随链接脚本而变:这一篇的脚本没拦 `.note`,那几个字节还在,印出来就是 `add $0x0,%al`。04 篇后来补的那块 `/DISCARD/` 会把 `.note` 清掉,偏移 8 上就没有那几个字节,印出来是 `add %al,(%eax)`。反汇编那一屏今天笔者不重讲,要借它说另一件事。`ni` 管的是单步里“跨过子程序”那一手,跟“钻进去”的 `si` 是一对,在裸机上它出了点毛病。

咱们写一个带 `call` 的最小样例,源码存成 `callsample.s`,还是 `.code16`,还是 512 字节,内容是:

```asm
.code16
.globl _start
_start:
    jmp main
sub:
    ret
main:
    call sub
fin:
    jmp fin
```

照上面编链的两条命令,`as` 和 `ld` 一编一链,产物存成 `callsample.bin`,还是 512 字节。这个数不是笔者报给您听的,`ls -l` 一量就出来:

```bash
as --32 -o callsample.o callsample.s
ld -m elf_i386 -T tiny-raw.ld --oformat binary -o callsample.bin callsample.o
ls -l callsample.bin
```

```text
-rwxr-xr-x 1 … … 512 Oct  1 17:47 callsample.bin
```

512 是从哪儿来的,上一篇那道手法:同一个链接脚本把游标摁到第 510 格,再让签名占住最后两格,文件就停在 512。咱们看偏移 3 起的三个字节,`e8 fc ff`,那是 `call` 的机器码,它把控制权送到子程序 `sub` 去。

`ni` 这个命令的名字听着就明白,step over,一次走一步,碰到子程序调用就整条跨过去,停在调用的下一条。`si` 是 step into,碰到调用就一头钻进去,停在子程序的头一条。今天笔者想看看在这里,step over 和 step into 这对命令会怎么样。

咱们让 GDB 断在 `0x7c03`,也就是 `call` 落的地方,然后分别走一步。QEMU 那一半跟前面一模一样,只把镜像换成那个带 `call` 的样例,端口用 `1285`。

咱们敲的命令就这几句,两趟各跑一次:

```gdb
set architecture i8086
set confirm off
target remote 127.0.0.1:1285
break *0x7c03
continue
info registers eip
si                 # 另一趟把这一行换成 ni
info registers eip
detach
```

两趟各起一台 QEMU,两个脚本只差一个词。咱们用 `si` 的那一趟,印出来是这样:

```text
Breakpoint 1 at 0x7c03

Breakpoint 1, 0x00007c03 in ?? ()
eip            0x7c03              0x7c03
0x00007c02 in ?? ()
eip            0x7c02              0x7c02
```

咱们换 `ni` 再跑一趟,印出来是这样:

```text
Breakpoint 1 at 0x7c03

Breakpoint 1, 0x00007c03 in ?? ()
eip            0x7c03              0x7c03
0x00007c02 in ?? ()
eip            0x7c02              0x7c02
```

咱们把两屏摆在一起,一个字节都不差,收成一张表就是这样:

| 操作 | 之后 `eip` |
|---|---|
| `si` | `0x7c02`(进到子程序里) |
| `ni` | `0x7c02`(也进到子程序里) |

`0x7c02` 就是 `sub` 的头一条,一条 `ret`。子程序里没有别的东西,一步就到底。`si` 进到这里,这一点笔者认。`ni` 也进了这里,这一下就有点意思了。`ni` 不是该跨过去吗,怎么跟着 `si` 一起钻了进来?

笔者想知道是不是裸机才这样,于是换了个场合,在咱们开发它的电脑上编一个带调试信息的普通程序,`gcc -g -O0`,内容是 `int sub(int x){return x+1;} int main(void){return sub(41);}`。在 `main` 里按 `ni`,它没往里钻,安安稳稳地跨过了 `sub()`,停在 `call` 的下一条上,本机量出来是 `main+14`——换个编译器、换个架构,这个偏移就会变,本机这个数只对本机这次编译成立。

差别就出来了。那边有 `-g` 编出来的调试信息,这边只有一枚 512 字节的裸产物。根子在 `ni` 自己身上。它是 step over,要跨过一条子程序调用,光看出眼前是一次调用还不够。它得知道这个子程序叫什么名字,从哪儿到哪儿。咱们问一句,这套说明从哪里来?从符号和调试信息里来,编译器编程序的时候,顺手把它们写进了产物里。裸机上没有这些说明,`e8 fc ff` 它认得出来是 `call`,断到 `0x7c00` 之后再反汇编,它印的就是一条 `call`。可它手里没有 `sub` 这个名字,也没有边界,判不出该不该跨过去,只能照着一条一条往下走,行为就跟 `si` 没有两样。刚才反汇编拼错字节,是另一条路线上的毛病,跟这里不是一回事。这叫退化,不是两个命令差不多。

笔者得特意说一句,您别往另一个方向记。今天这一趟不能拿来演示 `si` 和 `ni` 的差别,因为在这儿它俩根本没有差别,今天只把“它退化了”和“为什么退化”讲明白。

## 段寄存器只在固件阶段说真话

第二处比前面更怪。前面碰上的那件事,它给的数不假,是它手上的说明不够。这里它答了一个数,可这个数咱们没法确定该怎么看。

回到刚接上的那一刹那。机器还停在复位向量上,那会儿咱们读 `cs` 和 `eip`,拿到的是 `cs=0xf000`、`eip=0xfff0`。这里有一处例外得记清:**复位那一刻,`cs` 的基址不是 `0xf000` 乘十六** —— 手册给这一刻开了个特例,基址直接是 `0xffff0000`,所以上电以后头一条指令落在 `0xfffffff0`。让它在固件里走一步,`eip` 从 `0xfff0` 变成 `0xe05b`,`cs` 还是 `0xf000`。这一步不是随便挪一下:`0xfff0` 上躺着一条远跳,跳完 `cs` 被重新装了一次,**从这一次起,基址才按实模式的算法重算**。往后这一段路上它稳得很。

同一台 QEMU 里接着往下走,让脚本 `continue` 到咱们自己的引导扇区,断在 `0x7c00`。下面是同一台机器、同一枚镜像上连着读到的三个时刻,请您把镜头落在这三行上:

| 时刻 | `info registers cs eip` 读到 | 判定 |
|---|---|---|
| 刚连上(复位向量) | `cs=0xf000`、`eip=0xfff0` | 选择子是读得到的,基址得另算 |
| `si` 一次后(仍在固件里) | `cs=0xf000`、`eip=0xe05b` | 可用 |
| `continue` 到 `0x7c00`(引导扇区) | `cs=0x0`、`eip=0x7c00` | 段寄存器读回来是 0 |

咱们看这两行。第二行里 `cs*16 + eip` 算出来 `0xf0000 + 0xe05b`,拼出物理地址,这活儿干得漂亮。第一行是那个特例:那一刻 `cs` 印的 `0xf000` 只是选择子,基址得按手册另算,是 `0xffff0000`,所以那一行不能拿 `cs` 乘十六去凑。第三行是那个怪地方:断在 `0x7c00` 的时候,`eip` 印的 `0x7c00` 是对的,`ax` 印的 `0xaa55` 也对,偏偏 `cs` 回了 `0x0`。

它不是整体读取失败,同一屏里别的几行都在,单单段寄存器回了零。那这个零,是不是机器当时的真实状态?笔者说不好,也不敢替它答这一句。能确定的只有一条:这个数到底是什么意思,咱们判不了,那就别拿它作证。所以咱们在这儿得给自己立一条能背着走的说法:要演示实模式下的 `cs:eip`,必须在机器还在固件里的时候读,那会儿印出来的 `0xf000` 才是真值。等到程序跑进了引导扇区,`cs` 就不能再拿去作证了。想说明咱们的代码落在了哪儿,改用断点地址 `0x7c00`,或者干脆去看 QEMU 那边的记录,别拿 `cs` 的读数说事。

这里还有个尾巴,笔者得跟您提一句。前面脚本那一屏跑出来的也是同一个数,脚本里那句 `continue` 走到 `0x7c00` 才停,那时候的 `cs` 同样是 `0x0`。咱们看,这不是这一趟才碰上的孤例,只要程序落到引导扇区上,`cs` 回的就是这个零。

## 债:栈里的进出、内存断点和反汇编的别的通道

今天欠下的债,咱们也记一笔。`call` 一进去,栈指针是怎么进出的,咱们只看了 `eip`,栈上那半截一个字都没碰。内存断点那一路,一个也没下。反汇编除了这一屏之外还有什么通道,也没试。这三样都得等手上有带符号、有调试信息的东西,才谈得上怎么还。这些债都算另开一课的活。

单步那对开关真正的差别,得等手上有带符号的东西了才说得清。今天这几笔债也一样,咱们记在这儿,等那一天。

## 512 字节的产物,只有偏移 4 的一个字节不一样

今天做下来的事,最后都落到这枚 `mbrQ.bin` 上。前面几节敲过的命令,数都还印在屏幕上,跟咱们走完这一趟的是这枚产物:它是笔者动了源码里一个数重编出来的,拿在手上跟改之前那枚 `mbr.bin` 摆在一起,差在哪儿,一眼就看得出来。

今天碰到的两处,前面都出现过。`ni` 一次出在并排摆开的两趟单步会话里,它认得 `e8 fc ff` 是一次调用,却判不出 `sub` 从哪儿到哪儿,在裸机上就跟 `si` 一样钻进了子程序。`cs` 一次出在段寄存器印出来的表上,它跑进引导扇区以后回的那个零,咱们说不出它是什么意思,也就不能拿它作证。

笔者这回翻的几本书里,没有一本讲过调试回路。CSAPP 里落笔讲到 GDB 的地方是书页 254 到 256 的一整节,通篇按 32 位口径写,跟今天的 16 位机器对不上。另外书页 260 上还有一句顺带提及,那是习题里的话。所以这一篇里,命令的意思只能去翻 GDB 自己的文档和 man 页,现象只能自己跑。

自己跑出来的东西,收在两行 `xxd` 上。调试器在这个回路里替咱们看了几眼,该下的判断还是咱们自己下。`'K'` 换成 `0x51`,是笔者动的手。偏移 4 的字节换成 `51`,是重编重链以后长出来的。两行摆在一起,哪一处跟着笔者动了,它自己就显出来了。
