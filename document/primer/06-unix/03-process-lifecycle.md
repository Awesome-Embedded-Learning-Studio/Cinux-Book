# 03 · 进程生命周期:内核手里的那张花名册

上一卷咱们把进程说成花名册上的一行,`pid` 是我、`ppid` 是谁生了我。这一篇要问的问题比那一行大一点:同一条命令,凭什么在不同场合下变成几个不同身份?咱们来看一台机器上的小现象。

笔者把自己手头机器的底细交出来,因为下面好几个读数会被它改掉。当前 uid 是 1000,没有 root,`/` 挂的只读。这儿还有一份自己的 PID 名字空间,`ps -e` 拉出来只有四到六条进程,所以下面那些个位到三位的号,您那边多半一屏拉不到头。跟这一篇关系最近的是最后一条:**本机默认没有控制终端**,`tty` 直接答 `not a tty`,想要真终端,得当场用 `script` 现开一个 pty。三条约束一变,下面那几个读数就跟着变。

同一份脚本,咱们让它在两个场合各跑一遍,问的是同一句话:我是谁?脚本一共四行,存成 `identity.sh`:

```bash
echo '$ tty'
tty
echo '$ ps -o pid,ppid,pgid,sid,tpgid,stat,comm -p $$'
ps -o pid,ppid,pgid,sid,tpgid,stat,comm -p $$
```

两个 `echo` 不是多余的,它们负责把“接下来这行是我敲的”补到屏上,底下两屏里 `$ ` 打头的行都是这么来的。脚本里只留了 `tty` 与 `ps` 两问,原脚本后面还接着读 `/proc/$$/status` 里那几个号、再挂一条后台作业看 `jobs`,那两屏这一篇用不上,没搬过来。两个场合各跑一遍:

```bash
bash ./identity.sh
script -qec "bash ./identity.sh" /dev/null
```

没有终端的那个场合,笔者机器上读到的是这样:

```text
$ tty
not a tty
$ ps -o pid,ppid,pgid,sid,tpgid,stat,comm -p $$
    PID    PPID    PGID     SID   TPGID STAT COMMAND
    236       3       0       0      -1 S    bash
```

同一串命令挪进 `script` 现开的伪终端里,咱们看同一句 `tty` 换成了什么:

```text
$ tty
/dev/pts/0
$ ps -o pid,ppid,pgid,sid,tpgid,stat,comm -p $$
    PID    PPID    PGID     SID   TPGID STAT COMMAND
    246     245     246     246     246 Ss+  bash
```

两遍跑的是同一份脚本,差别只在场合。这里那个 `script` 命令来自 util-linux,它的作用是给您现开一个伪终端,再把后面的命令放进去跑。没有终端的那一遍,就是本机默认的样子。

| 格 | 没有终端 | 现开一个伪终端 | 怎么读 |
|---|---|---|---|
| `tty` | `not a tty` | `/dev/pts/0` | 右边那一列才是“您坐在终端前”的样子 |
| `PGID` | `0` | 等于自己的 pid | 右边那一列里,这个 shell 是进程组组长 |
| `SID` | `0` | 等于自己的 pid | 右边那一列里,它是会话首进程 |
| `TPGID` | `-1` | 等于自己的 pid | 右边那一列里,它在前台 |
| `STAT` | `S` | `Ss+` | 小写 `s` 说它是会话首进程,`+` 说它在前台进程组 |

稳下来看的是形状:哪一列会跟着场合变、往哪边变。这里也是笔者机器跟您手边机器差别最大的地方:同样一个没有终端的场合,在您的机器上 `PGID` 与 `SID` 会是真正继承来的号,不是零。

上面几屏里的具体数字与程序名,都是本机此刻读出来的,您那边一定不是同一批。`ps` 不给任何选择条件的时候,手册写着只挑同一个 euid、并且挂在同一个终端上的那些进程(`ps(1)`)。您坐在终端前敲一条 `ps`,表里多半就是您的 shell 和咱们刚敲下去的那个 `ps` 两行,init 通常不在这里面。笔者机器上多出的那几条,来自一个更朴素的理由:本机的进程全都没有终端,于是“同一个终端”一道筛选下来,整份名字空间都被圈了进来。

## 一次调用,两个进程

咱们补上一件上一卷留了个口子的事:花名册上那些行,是怎么多出来的?书里给 `fork` 的说明短得很:`pid_t fork(void)` 在孩子里返回 0,在父亲里返回孩子的 pid,出错返回 -1(APUE 书页 229)。同一条书证里紧跟着的那句才是要紧的:**called once but returns twice**,一次调用、两次返回。两次返回里唯一的区别,就是它交回来的那个数。孩子在返回 0 的那一路接着往下走,父亲手里拿到的是新孩子自己的号。

`fork` 是库函数那一层的入口,落到内核里长什么样,得看您手上这套 C 库。眼下这一版走的是 `clone`,老一点的直接就是 `fork` 那个系统调用,上一篇讲一根竖线底下六个系统调用的那一段末尾,解释的就是这件事。这一篇认的是“一个已经在跑的进程把自己抄成两个”这个动作。

咱们写一支十九行的程序,让两个分支各自把自己的身份打出来,存成 `fork2.c`:

```c
/* fork 一次,回来两次:一行代码,两个执行流 */
#include <stdio.h>
#include <sys/wait.h>
#include <unistd.h>

int main(void) {
    printf("fork 之前:我是 %d,我的父亲是 %d\n", getpid(), getppid());
    fflush(stdout);
    pid_t pid = fork();
    if (pid == -1) { perror("fork"); return 1; }
    if (pid == 0) {
        printf("孩子这一支:fork() 返回 %d,我的 pid=%d,我的父亲=%d\n", pid, getpid(), getppid());
    } else {
        printf("父亲这一支:fork() 返回 %d(孩子的 pid),我的 pid=%d\n", pid, getpid());
        wait(NULL);
        printf("父亲:孩子收完了\n");
    }
    return 0;
}
```

存好之后咱们用 `gcc -o fork2 fork2.c` 编出来,跑一遍:

```text
$ ./fork2
fork 之前:我是 213,我的父亲是 3
孩子这一支:fork() 返回 0,我的 pid=214,我的父亲=213
父亲这一支:fork() 返回 214(孩子的 pid),我的 pid=213
父亲:孩子收完了
```

这里最该停一拍的是中间那两行。同一次 `fork` 调用,两支看到两个不同的数,而它们报出来的 `getpid()` 又各自不同。书里把另一件事也写明了:孩子是父亲的一份拷贝,数据、栈、堆这些结构都被复制一份,打开的文件也跟着复制,而每个进程有自己的 pid(APUE §8.3)。所以在您自己的机器上,上面那些号一定是另一批,关系却和这一屏一样:孩子的 `getppid()` 等于父亲的 `getpid()`,父亲的返回值等于孩子的 `getpid()`。

至于父子两支谁被排到前面,书里专门有一支程序演示这个竞争(TLPI 书页 526)。这一趟咱们没自己做这个实验,所以这里只留书里的那句话:谁跑在前面是没有保证的。

## 花名册上那七个字段

两支分开之后,内核那边就有了两条记录。看记录的命令是 `ps`,咱们用 `-o` 自己把要的列点出来:

```bash
ps -o pid,ppid,pgid,sid,tpgid,stat,comm
```

这七列是七个问题:我是谁,谁生了我,我在哪个组,我在哪个会话,那个终端的前台组是谁,我现在在干嘛,我叫什么。上一卷讲进程那一篇里已经给过其中四列的口诀,这里补到七列。这一屏是本机此刻读到的:

```text
    PID    PPID    PGID     SID   TPGID STAT COMMAND
      1       0       0       0      -1 S    bwrap
      2       1       0       0      -1 S    bash
      3       2       0       0      -1 S    bash
    215       3       0       0      -1 R    ps
```

前两格看着很正常,`ps` 的父进程是那个 shell,shell 的父进程又是上一个。麻烦在后三格:整张表上 `PGID` 与 `SID` 全是零,`TPGID` 全是负一。这可不是 `ps` 读错了,是笔者机器把继承来的号压平了的结果。想读到真号,得现开一个伪终端,进去再读一遍。书里也有一屏读到这几个号(APUE 书页 307):

```text
$ ps -o pid,ppid,pgid,sid,tpgid,comm | cat1 &
  PID  PPID  PGID   SID TPGID COMMAND
 2837  2818  2837  2837  2837 bash
 5801  2837  5801  2837  2837 ps
 5802  2837  5801  2837  2837 cat1
```

书里那一屏是接到 APUE 自己的辅助程序 `cat1` 上取的。那是随书配的一支小工具,咱们手上没有,这一屏照书引,不必自己复现。三行的后三格全是有意义的真号。并排看下来,被压掉的正好是后面那几个。上面那几个号,您在 `/proc/<pid>/status` 里是找不到的,字段表里根本没有它们。照着 `status` 翻半天,是很容易白花的一趟。它们住在 `/proc/<pid>/stat` 里,叫 `pgrp`、`session`、`tty_nr`,同一个文件里还带着 `tpgid`(`proc_pid_stat(5)` 那段)。

`STAT` 那一列也不只是“在跑还是在睡”。`ps(1)` 给每个字母都留了位置,咱们这一篇只用得上三个:`s` 说这一行是会话首进程,`+` 说它在前台进程组,`Z` 说这是个还没销号的退场进程。剩下那些字母等真用到再查表。

## 盒子里还有盒子:进程组、会话

`ps` 给您的是横着的一排进程,`PGID` 与 `SID` 那两列把它竖着分成了两层。咱们让镜头落到组这一层。

**进程组**是一组进程,它们在同一个 `PGID` 底下。这个号不白给:终端上敲出来的那些键产生了信号,投给谁就是按这个号挑的,挑的是前台那一组。您按一下 `^C`,并不是某一个进程挨了一下,而是整组一起挨。书里给的也就是这一句,同一进程组里的进程收同一路的作业控制信号(APUE §9.4)。

再往外一层是**会话**,书里的定义很短:**a session is a collection of one or more process groups**,一个会话就是一个或多个进程组的集合(APUE 书页 295)。建立这个会话的那个进程叫会话首进程,它同时也是这个会话的控制进程。开头那两屏里,`SID` 那里答的就是“我归哪个会话管”,`STAT` 里那个小写 `s` 是同一件事的另一个面。

咱们拿 `setsid` 开一个新会话,您自己试一遍 —— 它把后面那句命令放进一个新会话里跑,顺带把控制终端摘掉。这儿另外给一份脚本,它头一行自报家门,接着按 `ps`、`tty` 的次序各读一次,存成 `who.sh`:

```bash
echo "谁在跑:$$"
echo '$ ps -o pid,ppid,pgid,sid,tpgid,stat,comm -p $$'
ps -o pid,ppid,pgid,sid,tpgid,stat,comm -p $$
echo "\$ tty"
tty
```

咱们在笔者机器上跑起来是这样:

```text
$ setsid bash ./who.sh
谁在跑:352
$ ps -o pid,ppid,pgid,sid,tpgid,stat,comm -p $$
    PID    PPID    PGID     SID   TPGID STAT COMMAND
    352       3     352     352      -1 Ss   bash
$ tty
not a tty
```

咱们把这一屏和开头那两屏摆在一起看:`PGID` 与 `SID` 都等于自己的 pid,说明它自成一个新组,也自成一个新会话的首进程。可 `TPGID` 那里是负一,`tty` 又报 `not a tty`。这两行指的都是同一件事,新开出来的会话没有控制终端。

## 会话的那一头挂着一个终端

第三层是控制终端。书里在结构图那一页列了一串很具体的事(APUE §9.6,书页 296 到 297),咱们挑几件跟这一篇对得上的说。第一件,会话首进程就是控制进程,咱们在 `Ss` 那个 `s` 上已经见过会话首进程这一半。第二件,按一下终端上的中断键(常常是键盘上那个 Delete,或者 Ctrl-C),中断信号发给前台进程组里的全部进程。第三件,按的是退出键(通常是 `^\`),quit 信号也发给前台那一组。第四件,终端那头要是断开,挂断信号发给控制进程。末一件,哪一组算前台由 `TPGID` 说了算,这一件每一屏都在答。中断键、退出键和真正的挂断这三件,这一篇都没有做现场,只能照书念。

`TPGID` 这一列的读法值得单独说一句。它不问“您这个进程有没有终端”,它答的是“终端现在把哪一组当前台”。所以一个后台进程可以有自己的终端,可以是终端所在会话的成员,`TPGID` 这里却指着别人。在笔者的机器上,这里要么是负一,要么就跟着那个伪终端里的 shell 走,读者那边看到的会是一串真正不同的号。

终端本身是后面篇 5《终端与伪终端》的事。这一篇里真开出来的终端只有开头那一屏,`script` 给咱们现开了一个伪终端。刚刚那一段讲的控制终端,是照书上的结构图说的。`setsid(2)` 与 `setsid(1)` 对新会话与控制终端的说法一样,新会话的首进程不会因此获得控制终端。一个新会话有没有终端,得另说。

## 退场不等于销号

前面讲的都是一条进程活着时候的身份。上一卷讲四象限的那一篇里留过一句,一个进程从生到死经历了什么,那是后面单独一篇的事。接下来要接的就是那一句:它跑完最后一行代码之后会发生什么,咱们在花名册上一样看得出来吗?

孩子退场了,父亲还没把它收走,那一行不会消失。它还在表上,`STAT` 那一列变成 `Z`,名字后面挂一串 `<defunct>`,那一行还在等它的父亲 —— 上一卷讲进程那一篇里咱们已经点过僵尸这回事,这里把现场摆出来。手册对它的说法是,一个孩子退了场,却一直没人来收,它就成了僵尸(`wait(2)` 那一段)。收尸的动作就是父进程调一次 `wait` 那个系列的调用。程序照 `fork2.c` 那样写,孩子拿 `_exit(7)` 立刻走,父亲把它丢在一边,拿 `ps` 看一眼,睡两秒,回头再收。命令行上带了 `w` 这个参数才走到收尸那一步,不带它就在第一张表之后停下:

```c
/* 孩子先走、父亲不收尸:表上留一行 */
#include <stdio.h>
#include <stdlib.h>
#include <sys/wait.h>
#include <unistd.h>

int main(int argc, char **argv) {
    int wait_it = (argc > 1 && argv[1][0] == 'w');
    pid_t pid = fork();
    if (pid == 0) { _exit(7); }
    printf("孩子 pid=%d 已经退出;父亲先不收它\n", pid);
    fflush(stdout);
    char cmd[128];
    snprintf(cmd, sizeof cmd, "ps -o pid,ppid,stat,comm -p %d", pid);
    fflush(stdout);
    system(cmd);
    sleep(2);
    if (wait_it) {
        int st = 0;
        waitpid(pid, &st, 0);
        printf("收完再看一次:\n");
        fflush(stdout);
        system(cmd);
        printf("收尸:退出状态 = %d\n", WEXITSTATUS(st));
    }
    return 0;
}
```

存成 `zombie.c`,用 `gcc -o zombie zombie.c` 编出来,带一个参数跑。表里那四列是 `system` 里那句 `ps -o pid,ppid,stat,comm -p <孩子的号>` 打的,中间那两秒是留出来让咱们看清第一张表的。在笔者机器上,收尸前后各看一次表:

```text
$ ./zombie w
孩子 pid=223 已经退出;父亲先不收它
    PID    PPID STAT COMMAND
    223     222 Z    zombie <defunct>
收完再看一次:
    PID    PPID STAT COMMAND
收尸:退出状态 = 7
```

第二拍的表底下只剩一行表头,`Z` 那一行没了。`COMMAND` 那一列打的是程序文件的名字,表里那个名字是笔者自己给程序起的。笔者当初编出来时用的名字跟这里不一样,别的字都一样,这一行咱们按 `zombie` 写。您那边就是您起的名字。这里还要留意一处:`ps -p <一个已经不存在的号>` 不是“什么也不打”,它照打表头,只是没有任何一行匹配上。咱们要分清:表上少掉的那一行,和终端上少掉的那段输出,是两回事。

那个 `7` 也是可以信的一格,咱们看它怎么来的。孩子是用 `_exit(7)` 走的,收尸的时候父亲取出来的就是它。取状态这件事由几个宏分头负责,`WIFEXITED` 判断是不是正常退出,`WEXITSTATUS` 取出退出状态,`WTERMSIG` 说的是它被哪个信号收掉了(`wait(2)` 那段)。父亲想只等某一个孩子,用的是 `waitpid`,它成功时返回的是那个状态变了的孩子的 pid。

父亲要是比孩子早走一步,孩子并不会跟着消失。书里给这一类进程起了名字,咱们看原文:**a process whose parent terminates is called an orphan and is inherited by the init process**,一个父进程更早退场的进程叫孤儿,它由 init 进程接手(APUE 书页 307)。咱们写的孤儿程序,让孩子报一次自己的号与父亲,睡三秒再报一次:

```c
/* 父亲先走:孩子被谁收编? */
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>

int main(void) {
    pid_t pid = fork();
    if (pid == 0) {
        printf("孩子 pid=%d,第一拍看到的父亲=%d(这一拍可能已经晚于父亲退出)\n", getpid(), getppid());
        fflush(stdout);
        sleep(3);
        printf("孩子 pid=%d,三秒后父亲=%d\n", getpid(), getppid());
        return 0;
    }
    printf("父亲 pid=%d 立刻退出(孩子还活着)\n", getpid());
    return 0;
}
```

存成 `orphan.c`,用 `gcc -o orphan orphan.c` 编出来,在笔者机器上跑起来是这样:

```text
$ ./orphan
父亲 pid=219 立刻退出(孩子还活着)
孩子 pid=220,第一拍看到的父亲=219(这一拍可能已经晚于父亲退出)
孩子 pid=220,三秒后父亲=1
```

孩子三秒后再报一次父亲,报出来的是 1。咱们看第一拍那里,它自己带着说明:那一拍可能已经晚于父亲退出,所以它看到的也许是旧的号。

常被当成“1 号就是 init”的前提,在笔者机器上不成立。这一趟 `/proc/1` 上写着的是别的看守程序,不是 init。书里说 1 号通常是 init,而且**The init process never dies**(APUE 书页 228),这是正常机器上的样子。这样的差别得放在明处,咱们别把它当成错。

还有一件事跟收尸连着:进程号会被重复使用。书里的说法是,**Although unique, process IDs are reused**,号是唯一的,可进程退场之后它的号就成了候补,后面起来的进程可以再拿它(APUE 书页 227)。这一点值得留心:您手上存着的一个号,过一会儿指的可能是另一个进程。

## 一个 `&` 之后,shell 那边多了什么

上面这些讲下来,镜头一直在内核那一边。咱们把镜头转到 shell 这一边,同样的东西换了个名字,叫作业。

咱们起两条后台命令,再把 shell 手里的作业表摆出来看。下面这一整块是一次运行读下来的:把屏里那些 `$ ` 打头的行按次序存成一支脚本 —— 存成 `jobctl.sh`,那个 `$ ` 只是记号,别抄进文件里 —— 交给 `bash` 跑一遍。作业控制那个开关,交互式 shell 与非交互式 shell 的默认值不同,所以别在交互式 shell 里一行一行敲,那样读到的是另一个状态:

```text
$ set -o | grep -E "^(monitor|pipefail|errexit)"
errexit        	off
monitor        	off
pipefail       	off
$ ps -o pid,ppid,pgid,sid,tpgid,stat,comm -p $$
    PID    PPID    PGID     SID   TPGID STAT COMMAND
    227       3       0       0      -1 S    bash
$ sleep 30 & sleep 40 &
$ jobs
[1]-  Running                    sleep 30 &
[2]+  Running                    sleep 40 &
$ ps -e -o pid,ppid,pgid,stat,comm | grep -w sleep | grep -v grep
    231     227       0 S    sleep
    232     227       0 S    sleep
$ wait -n; echo "wait -n 退出码=$?"
wait -n 退出码=0
$ kill %1 %2 2>/dev/null; wait; echo "清完了"
清完了
```

书里对作业的定义是,咱们每敲一条管道,shell 就给它配一个作业。同一条管道里的所有进程,属于同一个作业(bash 手册 JOB CONTROL 那一段)。`jobs` 打出来的方括号里就是作业号,从 1 起。`[1]-` 与 `[2]+` 后面那个 `-` 和 `+`,是“上一个作业”与“当前作业”的记号。

咱们看 `wait -n` 等的是谁,它等的是下一个结束的作业。现场里它返回 0,可返回什么别当成规律来记,它交回来的是那个结束的作业自己的退出状态,这一次碰巧是 0。

`kill %1` 里那个 `%1`,是 shell 认的作业名,不是给内核看的号。咱们得标清楚这是 bash 才认的行为,换成 `sh`、`dash` 那些 shell,它们未必认得出 `%` 这一手。

最后咱们交代 `monitor` 那一行,看看它为什么是关着的。它在本机是 `off`,因为这里跑的不是交互式 shell,这个开关默认只在交互式 shell 里开着。同一屏里那两行 `sleep` 的 `PGID` 也是零,跟 shell 一个样。即便这样,`jobs`、`wait`、`kill %1` 都照常能用,所以别把“没有作业控制”当成“`monitor` 关着”的同义词。屏里那两行 `pipefail` 与 `errexit` 不用管,`pipefail` 是前一篇管道里见过的老名字,`errexit` 这一篇用不上。

至于后台作业有没有自己的进程组,这一趟在笔者机器上看不出来。您在自己机器上起两条后台 `sleep`,再敲 `ps -o pid,ppid,pgid,comm` 列一遍,把 shell 那一行和 `sleep` 那两行挑出来比组号。作业控制开着的时候,后台作业的组号跟当时坐在前台的那一组不是一个,也就是跟 shell 那一行不是一个。手册给“后台”下的定义就是这个,组号与终端当前的前台组不同。这里笔者补不出来,得您那边落这一眼。

## fork 的次序,和留给终端篇的 nohup

有几样东西笔者这一趟没有做,这里如实交代,免得您照着上面的说法往外推。

您手边普通机器上的 `PGID`、`SID`、`TPGID`,笔者机器都读不到真值,只能在现开的伪终端里看它们长什么形状。您那边一读就是真号,它们会跟这一篇里的零和负一完全不同。书里那一屏就是您那边的样子。

`fork` 之后父子谁跑在前面,书里那句“没有保证”就是这一篇给出的全部,咱们自己没跑出过现场。整个进程组被孤儿化之后 POSIX 怎么处理,同样是空的,咱们连书里那一句都没往下引。

`nohup`、`disown` 跟挂断信号之间的实际效果,这里也没做。那需要一个控制终端真的消失的过程,笔者机器上没有可控的那一幕,把这一件留到讲终端那一篇去记。

## 双视角锚点:我起了个后台程序

**应用程序员那一边**,这件事一句话就说完了:命令行尾巴上加一个 `&`,它就在后台跑着,我还能接着敲下一条命令,不想要了就用 `kill %1` 收掉。中间发生了什么,不必知道。

**轮到写内核的人**,同一个 `&` 要翻成好几笔记录。咱们得给它一个号,记下谁生了它,把它挂进一个进程组,再把这个组挂进一个会话。如果桌面上还有一个终端,还得记清楚这个终端现在把哪一组当前台。它退场之后,事情也没有立刻结束。号还挂在表上,等它的父亲来收。父亲收走的状态码是它自己 `_exit` 带出来的那个数。收完之后那个号才回到候补名单里,等着被下一个进程再用一次。

往下的篇 4《信号》,咱们去问另一个问题:您按下的那一下 `^C`,是怎么从键盘上的一个字节,变成某个进程身上的一次中断。那件事要把终端这边和信号那边接起来,咱们到时候看同一个字节在两个地方的两副命运。
