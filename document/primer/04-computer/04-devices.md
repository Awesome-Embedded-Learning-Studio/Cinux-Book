# 04 · 设备怎么碰:一块内存地址、一排门牌号、一声敲门

咱们按下电源之后,机器做的事里,有一大类跟前面几篇都不一样:前面咱们盯着 CPU 自己搬数、自己算地址,这一回要问的是,它怎么跟 CPU 以外的东西说话。这一篇前面几节那些机器行为,都是本机模拟器演出来的,加上它自带的 SeaBIOS。后面查设备表的两节,用的是咱们开发它的电脑。凡是 `as`、`ld`、`objdump`、`xxd` 给出的屏,那是咱们开发它的电脑上的工具,跟模拟出来的机器无关。咱们这一篇用的全是 512 字节的裸扇区,没有一样是现成的镜像,您照前面几篇那套法子,自己就能把每一枚搓出来。这一篇里的调试口、寄存器、地址地图这些读数,都是问模拟器问出来的结果。

## 设备装作内存

有一件事,咱们在前面几篇的屏上路过好几次,却一直没停下来看:显存。`0xA0000` 那一带在模拟器的地址空间里明明白白挂着模拟出来的显卡。VGA 文本模式的文本缓冲区,按 OSDev 那页的说法,**线性文本缓冲区位于 `0xB8000` 的物理位置**。咱们往那儿写一行字,往 `0xB8000` 送这一行字的那段循环里没有一条 `out` 指令,只有把字符和属性装进 `ax`、再用 `movw %ax, %es:(%di)` 一格一格送进去。`0x0A00` 除以一行 160 字节,落在第 17 行。模拟器停下之后,咱们在它的控制台上敲一句 `screendump build/vga-shot.ppm` 存一张图,再用 `xp /48xb 0xb8a00` 按字节看同一块地方:

```text
# 让模拟器停下,存一张屏,再按字节看 0xb8a00 那一块
000b8a00: 0x30 0x1e 0x78 0x1e 0x42 0x1e 0x38 0x1e
000b8a08: 0x30 0x1e 0x30 0x1e 0x30 0x1e 0x20 0x1e
000b8a10: 0x49 0x1e 0x53 0x1e 0x20 0x1e 0x52 0x1e
000b8a18: 0x41 0x1e 0x4d 0x1e 0x2d 0x1e 0x4c 0x1e
000b8a20: 0x49 0x1e 0x4b 0x1e 0x45 0x1e 0x20 0x07
000b8a28: 0x20 0x07 0x20 0x07 0x20 0x07 0x20 0x07
# 调试口上吐出来的那一行
V0013
```

调试口上只落下来一行 `V0013`。它是程序自己算出来的:19 个字符连属性一共 38 个字节写进显存,再按内存一个一个读回来,比的是那 19 个字符字节,`0x0013` 就是相符的字符数,一个也没差。那 19 个字符连起来是 `0xB8000 IS RAM-LIKE`,屏幕上也真的出现了这一行。**把字符送进显存这一步只有 `mov`,没有哪一条指令点名过设备。**咱们把 `0x30 0x1e` 这一对分开看,`0x30` 是字符 `'0'`,`0x1e` 是它所在格子的属性:低 4 位 `0xE` 是前景黄、高 4 位 `0x1` 是背景蓝,屏幕上那行字正是这个颜色。**字符在偶地址,属性在奇地址。**文档在这儿跟实测对不上,咱们照实写:OSDev 的 *Text UI* 那一页写着,**第一个字节分为两个部分,前景色和后彩。第二个字节是要打印的字符的 8 位 ASCII 值**,您把这两句拿去对咱们手上的屏,顺序正好反了。往后写显存代码,咱们按实测这一套来:一格的字符落在 `(行 × 80 + 列) × 2` 这个偏移上,属性在它后面紧挨着。

最后一个证人不用咱们费劲。咱们那 19 个字符连着属性一共 38 个字节,只盖住了第 17 行前 19 格,再往后那几对 `0x20 0x07` 不是咱们写进去的,那些格子还留着固件当初写下的值,属性浅灰,正是 SeaBIOS 自己在用的颜色。本机模拟器上,固件在这块地方画过东西,咱们的程序接着用,两边都没打招呼。

## 另一扇门:端口

同一块显存,咱们用 `mov` 就写进去了。可设备上要读要写的那些寄存器,并不都在内存地址上。机器另开了一排号,叫端口,进去只用 `in` 和 `out` 两条指令。咱们随手挑几个号问一问,看看谁答应。这一枚裸扇区只做一件事:按表把端口一个个 `in` 回来,读到的字节顺着调试口吐出去,模拟器再把调试口接成文件,也就是咱们开发它的电脑上落下来的那个 `build/ports-console.txt`。它跟后面那几屏不是同一枚镜像,咱们一屏一屏说。

```text
# 上面那枚裸扇区读端口的结果,逐字吐在调试口上
0008=04
000a=00
000d=00
0021=b8
0061=30
0060=fa
0081=00
01f7=00
c040=00
c042=00
c044=00
0300=ff
0777=ff
00e9=e9
.
```

那枚读端口的镜像里带着一张十四项的端口表,头一项 `0x0008`、末一项 `0x00e9`,中间还夹着总线主控的三个 `0xc04x`,程序按表一个个 `in` 回来。`0x0300` 和 `0x0777` 是咱们故意挑的两个没人认领的号,读回来都是 `0xFF`。`0xE9` 却读回 `0xE9`,**在本机模拟器上**,这个号后面确实坐着东西。您把 `0x0300`、`0x0777`、`0xE9` 这三行并排看:端口不是内存里的某块地,它是个门牌号,敲过去有人应,这个设备才算存在。有数的那些行也值得看一眼,它们的值是固件初始化到此刻的偶然值,换块固件就变,咱们要认清的只是这一排号上确实坐着东西:`0x21` 是 8259 主片的中断屏蔽字,`B8` 的低位是 0,意思是 IRQ0 占用的那一号开着,这件事接下来还要用上。`0x08` 是 8237 DMA 的状态寄存器,`04` 表示它在。`0x0A` 是同一个芯片的单通道屏蔽寄存器,那是个只写口,读回来的 `00` 不带信息。

您把两个动作放在一起看。`mov` 到 `0xB8000` 是“把这段东西送出去”,`outb` 到 `0xE9` 也是“把这段东西送出去”。走的却是两条完全不同的路。书上把两条路摆在一起讲,也交代了没有哪一边压倒另一边:内存映射的写法好在不用新指令,端口的资历更老,今天两种都还在用。

`0xE9` 到底是个什么东西?它的正式名字叫 debugcon,**它是模拟器自己开出来的一个口**。咱们在本机模拟器上加一个 `-debugcon stdio`,往这个口每写一个字节,咱们的终端上就多一个字符。不想让它上终端,就把它接成文件,比如 `-debugcon file:build/ports-console.txt`,写进去的字节落进那个文件,后面那些“调试口逐字”就是这么留下来的。OSDev 那页还提了一句。原话是 `the debug console is one-way – you can only output`。您把这一句拿去对前面那行 `00e9=e9`,就能看清:读回 `0xE9` 是 QEMU 自己这么实现的,它不表示 debugcon 能读出自己写进去的东西。这个口咱们不是头一回碰,它还是前面几篇用来报信的那个调试口,只是这一回咱们看的是它在端口上这件事。它只会往外送,读它读不出您写进去的东西。

## 设备是怎么被发现的

显存和调试口,咱们都是自己知道号、直接去敲的。一台机器上插着的东西远不止这两样,谁去告诉内核,这里有个显卡、那里有块网卡?x86 给的答案是一对端口:`0xCF8` 和 `0xCFC`。咱们把配置地址写进 `0xCF8`,再从 `0xCFC` 读回那个双字:

```asm
    movw $0x0cf8, %dx
    outl %eax, %dx
    movw $0x0cfc, %dx
    inl  %dx, %eax        /* 读回那个双字 */
```

送进 `0xCF8` 的那个 32 位地址里装着四样东西:要找哪条总线、哪个设备、哪个功能,还有要问这个设备的哪个寄存器。最低 8 位是寄存器偏移,再往上 3 位是功能号、5 位是设备号、8 位是总线号,**位31是一个使能标志**。咱们把这枚裸扇区放出去,让它在总线 0 上把设备 0 到 31 挨个问一遍,回来的是这么一张表:

```text
# 换一枚裸扇区:补扫多功能设备的功能之后,它把结果吐在调试口上
00:00 8086:1237 0600 B00000000
01:00 8086:7000 0601 B00000000
01:01 8086:7010 0101 B00000000
01:03 8086:7113 0680 B00000000
02:00 1234:1111 0300 Bfd000008
03:00 8086:100e 0200 Bfebc0000
.
```

咱们逐格读这六行。头一格是设备号和功能号两样,中间那个冒号把它们分开,`01:01` 就是设备 1、功能 1,总线咱们固定在 0 上,所以没有印出来。往后一格是厂商号和设备号,再往后一格是这个设备属于哪一类,最后一格是它的 BAR0。这六行报出来的东西,按顺序是主机桥、ISA 桥、IDE 控制器、一个桥、VGA 控制器、以太网控制器,机型配了什么,表里就是什么。**咱们那 512 个字节,把机器上的显卡和网卡都问出来了。**

### 头一版少了两行

上面那六行不是咱们头一版拿到的。头一版只把每个设备的功能 0 扫了一遍,回来的是四行:

```text
# 调试口逐字:头一版只扫了每个设备的功能 0
D00V8086D1237C0600B00000000
D01V8086D7000C0601B00000000
D02V1234D1111C0300Bfd000008
D03V8086D100eC0200Bfebc0000
.
```

您拿它去对上面那六行的表,少的正是 `01:01` 的 IDE 控制器和 `01:03` 的桥,它们跟 `01:00` 住在同一个设备号上。这不是扫漏了总线,是漏了功能:多功能设备上只有功能 0 回答得齐全,别的功能藏在后面。判据写在配置空间偏移 `0x0E` 那个 header type 字节的**第 7 位**,文档的原话是:**如果设置了此寄存器的位7,则该设备具有多种功能**。原页紧接着还有半句,**否则,它是单功能设备**。咱们补上第 7 位判断,把功能 1 到 7 再扫一遍,六行才齐。这两版的差别就在源码本身。头一版是只扫功能 0 的那个文件,第二版换成会读 header type、再决定要不要补扫功能 1 到 7 的那个文件,两条 `as` 加 `ld` 各出一枚镜像。您自己复现的时候,这套比对值得留着:拿只扫功能 0 的那版输出跟 monitor 的 `info pci` 对一遍,看哪个设备号底下缺了功能,再回去改判据。

### 末一格那串十六进制

`1234:1111` 那一行最后一格是 `Bfd000008`。您别把它整串当地址:最前面那个 `B` 是程序自己打上去的栏位标记,后面 `fd000008` 才是八位十六进制,而且**它末 4 位是标志**:bit3 表示这块空间可以预取,bit0 是 0 表示它是内存空间。把 `fd000008` 的低 4 位抹掉,剩下的才是基址 `0xfd000000`。文档里管这一步叫屏蔽较低的位,给内存 BAR 的写法是 `(BAR[x] & 0xFFFFFFF0)`。咱们要拿这个地址去读写设备,得自己把低 4 位摘掉。咱们打听配置空间用的两个端口,在模拟器的地址地图里也有名有姓。地址地图与设备表,咱们到后面“两栏对照”一节并排看。

## 谁主动:设备发起,CPU 响应

到这儿为止,都是 CPU 主动:它去敲端口,它去读 BAR。可机器上大多数时候是反过来的,设备才是那个开口的一方。咱们让定时器敲一次门试试。要做的事分三步:咱们把中断向量表里第 8 项换成自己写的处理程序,实模式下 IRQ0 就落在它在表里的位置。接着咱们给 8254 定时器设个分频,让它慢一点。再把 8259 主片上 IRQ0 对应的那一号放开。然后主程序 `sti`、`hlt`,坐在那儿等。处理程序里每数到 16 次,就往调试口报一声:

```text
# 这一枚的调试口输出文件 build/irq-console.txt 收到的前九行
IT0001
T0002
T0003
T0004
T0005
T0006
T0007
T0008
T0009
```

同一趟里,咱们还给模拟器挂了 `-d int -D build/irq-trace.log`,让它把自己的每次中断投递记成一份日志 `build/irq-trace.log`。这一枚的调试口也接成了文件,就是上面那块标题里写的 `build/irq-console.txt`。这两样东西都是咱们自己跑模拟器时留下的:指令里写的是相对路径,落在**当前工作目录**下的 `build/` 里,那个目录得提前建好(`$ mkdir -p build`),不然 QEMU 会直接报一句打不开文件然后退出:

```text
$ grep -c "Servicing hardware INT=0x08" build/irq-trace.log
149
$ grep -c "Servicing hardware INT=0x0e" build/irq-trace.log
4
$ grep -n "Servicing hardware INT=0x08" build/irq-trace.log | head -3
423:Servicing hardware INT=0x08
424:Servicing hardware INT=0x08
425:Servicing hardware INT=0x08
```

调试口那一串是咱们自己报的。`I` 是 `sti` 之前打出来的,从那以后每 16 次滴答多一行,数到第九行。模拟器那边也记了它自己的一份日志,`Servicing hardware INT=0x08` 出现 149 次,149 除以 16 大约是 9.3,跟九个 `T` 对得上。这个计数随这一趟跑了多久变,换个时长就不是这个数。**两边各记各的,数出来说的是同一件事。**咱们再回头看停下那一刻的机器状态。咱们启动模拟器的时候就把它的 monitor 接在了手边,这会儿停住它,再把 `stop` 和 `info registers` 递进去:

```text
EIP=00007c43 EFL=00000286 [--S--P-] CPL=0 II=0 A20=1 SMM=0 HLT=1
CS =0000 00000000 0000ffff 00009b00
IDT=     00000000 000003ff
CR0=00000010 CR2=00000000 CR3=00000000 CR4=00000000
```

咱们从这三格读到的是同一件事:`CS=0000`、`CR0=00000010`、`IDT= 00000000 000003ff`,它还在实模式里,这会儿的中断表就是那本向量表,跟保护模式里的门不是一件东西。同一份日志里还有 4 条 `INT=0x0e`,那是 IRQ6,软驱,启动时 BIOS 读扇区留下的。日志里的中断不全是咱们的,这四行留着反而好,它说明设备不止一个。

敲门的是 8254 定时器,转达的是 8259,CPU 只是照表跳过去。**谁主动这件事在这儿是清楚的,设备动了,CPU 才动。**咱们的处理程序末尾,还欠 8259 一句话,咱们把它去掉看会怎样:

```text
# 同源的另一枚:处理程序末尾不写 EOI,再看调试口
调试口逐字(只有 'I',一个 'T' 都没有):
0000000   I
0000001
```

处理程序末尾还写着两句:`movb $0x20, %al` 加 `outb %al, $0x20`。这一对的名字叫 `EOI`,意思就是告诉 8259“这一趟处理完了”。咱们拿 `--defsym NO_EOI=1` 把这两句去掉,调试口上就剩下一个 `I`,连一个 `T` 都等不到。因为 8259 没收到“这一趟处理完了”,第二次中断根本没来,计数器停在 1,那个每满 16 次才报一声的判断再也轮不到。这一对 A/B 就是中断处理必须收尾的现场,不需要再讲道理。

## DMA:只到看见引擎

设备自己动这件事,还有一层走得更远的做法,叫 DMA,让设备跟内存之间直接搬,不劳 CPU 一个一个字地转。咱们这一篇只做到一半。端口那边确实有引擎,咱们 `in` 一次 `0x08`,8237 的状态寄存器答 `04`,它在。PIIX3 那块总线主控 IDE 的窗口是 `0xc040` 到 `0xc04f`,这个范围是模拟器自己报出来的,您在 monitor 里问一句 `info pci` 就能看到。咱们问过的、跟 DMA 有关的那几格读回来是这样:

```text
# 这些行就在那张端口表的结果里,咱们手上那份叫 `build/ports-console.txt`
$ grep -E "^0008=|^c04" build/ports-console.txt
0008=04
c040=00
c042=00
c044=00
```

`0xc040` 是命令寄存器,`0xc042` 是状态寄存器,`0xc044` 是 PRDT 地址的低半,它们全读成 `0`。**咱们手上本机模拟器里,从开机到现在,那块总线主控 DMA 一次都没动过。**往后那一段,咱们手上没有现场,只能引书上的口径。OSTEP 第 36 章书页 7 说,DMA 引擎就相当于系统里一件专用的设备,它能在设备和主存之间安排搬运,不需要 CPU 怎么插手,接下来那段大意是这样:OS 把数据在内存的哪里、要搬多少、搬给哪个设备告诉引擎,配置完就去做别的事了,引擎搬完抬手敲一次中断,OS 这才知道搬完了。同一页还给了一张改版的时间线图,三段分别是 CPU 配置的 `c c c`、DMA 自己搬的 `2 2 2 2 2 2 2 2`,最后交回 CPU。PIO 为什么费 CPU,上一页讲了:大批数据一个一个字地从 CPU 手上过,CPU 全耗在这件没什么意思的活上。

咱们没有让本机模拟器上的 DMA 搬过一次数据。没给 8237 设过通道地址和计数,没给 PIIX3 写过 PRDT,也没挂一块真的块设备走完 IDE 的读写时序。这一段留给往后写设备驱动的时候。还有一句边界要说清楚:设备寄存器出现的地方为什么不能让缓存随随便便吞掉,涉及缓存一致性和内存屏障,那是教科书那一层的事,不在这几篇的范围内。咱们在这儿只把这根线头露出来,不往那儿走。

## 两栏对照:谁在查设备

前面几节那些屏,全是模拟出来的机器给的。接下来咱们换一台机器,回到开发它的电脑上,用宿主的工具再查一遍。`lspci` 后面加上 `-nn`,它才会把厂商号与设备号一并印出来,不加就只印名字:

```text
$ lspci -nn
1786:00:00.0 System peripheral [0880]: Red Hat, Inc. Virtio 1.0 file system [1af4:105a] (rev 01)
2079:00:00.0 3D controller [0302]: Microsoft Corporation Basic Render Driver [1414:008e]
5582:00:00.0 SCSI storage controller [0100]: Red Hat, Inc. Virtio 1.0 console [1af4:1043] (rev 01)
60f0:00:00.0 3D controller [0302]: Microsoft Corporation Basic Render Driver [1414:008e]
```

您看这四行,四位十六进制的域号排在最前面。咱们在模拟器里枚举出来的是 `1234:1111` 的显卡、`8086:1237` 的主机桥、`8086:100e` 的网卡,这里一个都没有,换成了四个 virtio 和微软的合成设备。**宿主上查设备、模拟器里查设备,是两张完全不相干的表。**对照的另一栏,咱们得进模拟器里面去查:

```text
# 从模拟器自己报的地址地图里,挑出与前面几张表对得上的那几段;行号是 `grep -n` 加的
$ grep -nE "vga\.vram|e1000-mmio|e1000-io|pci-conf-idx|pci-conf-data|vga-lowmem|pc\.bios" build/pci-raw.txt | head -12
47:  00000000fd000000-00000000fdffffff (prio 1, ram): vga.vram
48:  00000000febc0000-00000000febdffff (prio 1, i/o): e1000-mmio
...
67:  00000000000a0000-00000000000bffff (prio 1, i/o): vga-lowmem
...
169:  0000000000000cf8-0000000000000cf8 (prio 0, i/o): pci-conf-idx
172:  0000000000000cfc-0000000000000cff (prio 0, i/o): pci-conf-data
```

咱们看 `info mtree` 报出来的这几段,它是模拟器把模拟出来的地址空间怎么切,一段段报出来的。这里的两段出自同一趟:模拟器起来之后,咱们把 `stop`、`info pci`、`info mtree -f` 这几句依次递给 monitor,整趟的输出重定向进 `build/pci-raw.txt`,行号是合起来数的——上面印的 `grep` 读的就是这个文件,手上没有它,`grep` 会直接报一句打不开文件。您单问一句 `info mtree -f`,行号会从 1 起,对不上这里。还有一层:上面那些行号出自某一次运行留下的文件,同一台模拟器、同一句命令再跑一遍,`info mtree -f` 报出来的次序会换个样子,行号也跟着变。所以您自己跑一遍,数出来的行号八成和这里不同,行上的文字还会是这几行。它头一行那个地址,正是前面 PCI 里读到的显卡 BAR0。`vga-lowmem` 那一行也认得出来,`0xA0000` 到 `0xBFFFF`,咱们写的那 19 个字符就落在它里面。宿主 `/proc/iomem` 这一手本来也值得看,本机上它走不通,咱们试过了:

```text
$ head -6 /proc/iomem
00000000-00000000 : Reserved
00000000-00000000 : System RAM
00000000-00000000 : Reserved
00000000-00000000 : System ROM
00000000-00000000 : ACPI Tables
00000000-00000000 : System RAM
```

每一格都被打成 `0`,咱们滤掉它们以后什么都不剩。所以在这一篇里要看真实映射,看的只能是模拟器的映射,也就是上面 `info mtree` 给出的表。

## 双视角锚点:同一块地址,两种读法

**应用程序员那一边**,设备是别人替他包好的东西。您读一个文件、往显存里塞两个字节、按一下键盘,拿到的都是同一个形状:要么是一个数,要么是一段字节,您不需要知道那块地址后面坐着的是一块内存条还是一张显卡。而且在这一边,动手的永远是您和您写的代码,机器只会答话,不会反过来找您。`0xB8000` 在您眼里就是一块能写的内存。**轮到咱们这些写内核的**,同一个 `0xB8000` 就得分成两件事来看:它是一条地址,可以像内存一样读写,它后面却坐着一个设备,收到写就改屏幕,这就是设备装作内存的那一层伪装。换个动作,同样是“把字节送出去”,咱们可以选 `mov` 到 `0xB8000`,也可以选 `outb` 到 `0xE9`,两条路的规范完全不一样,走哪条得自己拿主意。再往深一层,咱们还得认一件事:**大多数时候不是咱们在动。**定时器到点会来敲门,搬完数据的引擎会来敲门,咱们写好的那段处理程序,是在设备开口之后才被拉起来跑的。您看这一层与上一层正好反过来:咱们要安排的是被叫醒以后干什么,至于什么时候被叫醒,那件事握在设备手里。

## 这一篇没碰的几样

这一篇里的机器行为,咱们全是在本机模拟器上演出来的。换到真正的机器上,咱们一样也没验过,而这一篇里有几件事,恰恰最可能不一样:`0xE9` 能读回 `0xE9`、没人认领的端口读回 `0xFF`、PCI 上有哪几个设备、`-d int` 记下的两个计数,都是模拟器这一趟的样子。CPL=3 执行 `out` 不被拦那件事,现场在前面那一篇,不是这一篇演出来的。

DMA 只走到看见引擎闲着这一步,没搬过数据,QEMU 的 monitor 里也没有查看某设备 DMA 状态的命令,monitor 里的 `info qtree` 和 `info pci` 只报设备与 BAR。显存本身的用户态权限咱们也没试。PCI 只扫了总线 0,PCI-PCI 桥和往 BAR 写全 1 再读回来求大小这一手都没做。真实块设备、`int 0x10` 一类 BIOS 服务,还有缓存一致性和内存屏障,都不在这一篇的范围里。
