# 鞋码写在鞋盒上

上一节结尾咱们把问题撂在那儿:船该往哪儿开?内核住多大的房子、从哪个门进,boot 凭什么知道?咱们这就打开鞋盒看。这些数 boot 自己一个都不该定——住址是内核的家事,身材是内核的身材,门牌是内核的门牌。所以这一遍的做法,是让内核的镜像在盘上躺成一只鞋盒:开头几十个字节是一张自述的标签,鞋码、住址、门牌全盖了章写在盒上。boot 要做的只有三样:读标签、验标签、照标签办事。

标签的住处在 `kernel/boot/image_header.hpp`,七个字段咱们挨个过一遍:

```cpp
struct [[gnu::packed]] ImageHeader {
    uint32_t magic;
    uint16_t version;
    uint16_t header_size;
    uint64_t load_paddr;
    uint64_t file_size;
    uint64_t mem_size;
    uint64_t entry;
};
```

魔数 0x5A4B4E43 管的是身份,盘上头四个字节按字符一读就成了 CNKZ。version 和 header_size 是留给将来的。头要是加长了、字段要是变了义,拿旧版本说话的装载器对不上号,可以体面地拒载,而不是把新盒当旧盒读串。load_paddr 是物理的住址,而 entry 是门牌。当中的一对尺寸,是标签上最有讲头的两个字段,咱们单独说。

file_size 数的是文件里的真内容,mem_size 是内核要求的全部地界,两个数为什么不相等?内核的镜像里有一截 BSS:那些只声明、不带初值的全局变量,链接的时候占了地址,写进文件的时候却不占字节。咱们拿这一版内核把数读出来:file_size 是 0xA35,实打实的 2613 个字节,而 mem_size 是 0xC40,3136 个字节的地界。多出来的 523 个字节里,512 个是 BSS 的院子,剩下 11 个是段与段之间为了对齐垫的缝:.text 的尾巴没收在 16 字节的整边上,链接器就在它和 .rodata 之间垫了 11 个零,后一段才落到了整边上。这 11 个零躺在文件的中段,而头里的 file_size 是四个段各自的尺寸加出来的,数的时候没带上它们。可摆渡从镜像的头一个字节起顺着搬,鞋盒报了多少、它就搬多少,缝躲在报上来的字节数里,也就跟着文件一起过了河,落进内存还在那个对齐的位置上。真正留在盘上的,是镜像末尾的 11 个字节:盘上的文件拿 ls 数是 2624 个字节,比 file_size 多出来的正是它们。好在咱们这一版的运气不错,它们恰好挑在了零上——少搬的只是同一趟里的 11 个字节、谁也没伤着。真要是哪天 .rodata 的尾巴上住了数据,它们可就悄悄留在盘上了。BSS 在这儿失去了特殊地位:boot 根本不知道什么叫 BSS,它眼里的世界只有两个数:盘上读多少、内存里占多少。多出来那截院子归谁扫?咱们记下这桩事,讲到内核出生的时候再还。

标签上的数,不是哪个人手抄的,是链接脚本算出来的。咱们去 `kernel/arch/x86_64/kernel.ld` 里看正主,它就躲在起手的几句里:

```text
ENTRY(KernelEntry)
SECTIONS
{
    . = 0xFFFFFFFF80200000;
    __vma_start = .;
    .image_header : AT(0x200000) {
        KEEP(*(.image_header))
        . = ALIGN(16);
    }
```

同一个内核倒是背着两个地址,咱们把两句各念一遍。`.` 起手那句把世界观定在了高半:0xFFFFFFFF80200000。AT 里的 0x200000 把肉身的家定在物理 2MB。VMA 说的是内核以为自己住哪儿,代码里的一切取址都按这个世界观来。LMA 说的是装载那天,这些字节真正落进物理内存的哪儿。为什么是 2MB?咱们不找什么深奥的道理,就是挑了一块谁都不争的好地:头 1KB 是实模式向量表的遗址,BIOS 的数据区挤在 1MB 以里,0x10000 起是咱们的暂存窗,栈和表盘各有各的主——2MB 往上干干净净。对了,表盘说的就是三张页表,咱们后头都这么叫。顺带交代的还有一处旧规划:咱们在问内存那一卷的地图上给内核圈过一块 0x20000 起的中转宅基地,标的是一处留给内核启用的占位。这一版用不上了——装载的窗就开在它脚下,内核从盘上直接落到了 2MB。

脚本的尾巴上还有三行,链接器拿它们把标签的数算平,咱们一行一行念:

```text
    __file_end_lma = __lma_start + SIZEOF(.image_header) + SIZEOF(.text) + SIZEOF(.rodata) + SIZEOF(.data);
    __mem_end_lma  = __lma_start + (__vma_end - __vma_start);
    __entry_lma    = __lma_start + (KernelEntry - __vma_start);
```

file 尺寸是四段尺寸加出来的和,mem 尺寸是 VMA 的全程,entry 是门牌的换算——`KernelEntry` 在高半世界观里的地址,减去世界观的基址,加上物理的家,算出来的正是 0x2001B4。这些名字在链接完成的那一刻由链接器填成真数,咱们用不着手工抄一遍、再对一遍。

可字段是标签的字段,链接符号是链接器的私产,怎么把后者铸进前者?咱们看 `kernel/arch/x86_64/image_header_data.cpp`——整个文件就一段:

```cpp
asm(".section .image_header,\"a\"\n"
    ".global kImageHeaderRaw\n"
    "kImageHeaderRaw:\n"
    "   .long 0x5A4B4E43\n"
    "   .word 1\n"
    "   .word 32\n"
    "   .quad __lma_start\n"
    "   .quad __header_file_size\n"
    "   .quad __header_mem_size\n"
    "   .quad __entry_lma\n"
    "   . = (. + 15) & ~15\n"
    ".text\n");
```

后缀挂的是 .cpp,里面却是一段 asm 字符串——您别当这是炫技,这是没法子的:头要引用链接符号,而链接符号到链接那一刻才存在,C++ 的初始化器里写不下它们,能把名字变成字节的只有汇编器。于是标签成了链接脚本的孩子:前三个数是身份和礼数,后四个 quad 引用的是链接符号,等链接器落了锤,真数就铸进了镜像的开头。`.image_header` 是链接脚本里的头一个输出段,objcopy 剥成了裸字节,标签正好落在文件偏移 0——boot 从盘上把内核的第一扇区读回来,开头的字节就是标签本身。

构建那头的大事,咱们在本卷开头预告过,现在落到地上:内核是第五户编译世界。它和当年那 68 个字节走的是同一条老路,自家的一条链、剥成裸字节。待遇的差别,咱们开头也比过了。真正的新东西是链上的几样专属配置。`-mcmodel=kernel`,告诉编译器地址全住在最高那 2GB 的窗口里,咱们的高半世界观恰好就是这个圈。`-no-pie`,地址在链接期就定了死数,往后谁也挪不动了。末了 objcopy 剥裸字节,dd 到盘上第 32 号扇区起——盘面上的次序,咱们顺一遍:MBR 占的是 0 号,stage2 打 1 号起住——扇区预算从上一卷的 12 个放宽到了 28,如今它要装的东西多了,摆渡的船、九判、装载的活全在身上,眼下的实测是 26 个扇区,余量是留给它长个子的。内核的镜像打 32 号起住。顺带还有一笔搬家:当年那 68 个字节的 blob 挂在 stage2 镜像的尾巴上,尾巴长了,住址跟着从 0x9300 挪到了 0xB000。

鞋盒做好了,数也铸进去了。可您翻过盒底一想:这些数全是内核自己报的。报错了呢?鞋码报得比窗还大,住址报在别人家的院子里,照单全收的下场是什么?咱们下一节把它验明白了再动手搬。
