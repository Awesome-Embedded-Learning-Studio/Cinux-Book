# 丢了又找回来的八字节

ttydemo 的实弹,头一枪就死了。死相与从前的段错误都不一样:一声一般性保护异常,寄存器里 rip 落在程序自己的入口里,离 main 还有十万八千里的路。咱们把带符号的副本翻出来,用 addr2line 对了一回,出错的那一行是入口里的一条 movaps,十六字节的 SSE 存储。程序刚落地、一行逻辑没跑,就死在自己家的门口,这一案值得咱们写整个一篇。

死因咱们从头推。x86-64 的调用约定说,call 指令落地的瞬间,栈顶除十六余的是八,因为 call 压了八字节的返回地址。编译器给裸入口排布栈帧的时候,认的就是这个形态:程序的入口被当成一个刚被 call 进门的函数来对待,哪怕没人真的 call 过它,栈顶也该按 call 刚落地的样子铺。它算好了减多少之后,SSE 的落点恰好十六对齐。而咱们的内核交程序进场,栈顶是内核自己给的:execve 铺好画像,把栈顶放在一个常量的偏移上,偏移按十六对齐算出来的余数是零。就差了八格,SSE 指令一出手就挨了一记保护异常。咱们拿反汇编逐条数入口里的对齐,一笔一笔地对清,数出的余数确实是零,案定在了偏移上。

可这个故事最扎心的地方在考古。懒到家那一卷的验收里,咱们交过一模一样的学费:装载器的实弹第二枪,程序的栈顶除十六错了格,movaps 当场就炸了,修法是把进场栈顶改成了减八。那一卷连道理都写明白了:约定的进场栈顶,除十六该余的是八。这还不是上古的旧闻,往前数上几卷就是它了。开门迎客那一卷给 execve 的画像立新常量的时候,三版的眼睛全落在字符串与指针的布局上,栈顶的偏移按整页的整数重新立了个数,老的那八字节,丢了。init 直拉与 execve 两条路走的是同一个常量,一处丢了,两路就一起错了。

修的就是一行:常量从 0x100 改到 0x108,两条路的三处用点一次全对。可修完的这口气咽不下去,咱们得把两笔疑问问到底。头一笔咱们问 busybox:它是 1.2M 的大个子,天天在同样的栈顶上跑,它怎么不炸?翻了它的入口:库自家的启动代码进门头一件事就是把栈顶对齐校正一遍,不指望内核给的那八字节。它是穿着救生衣下水的。第二笔咱们问 hello、mapper 这些老演示:它们也吃着同样的错格栈顶,怎么也不炸?咱们反汇编对过:盘上这些二进制都是后来重编过的,mapper 从前炸过 movaps 的旧身子早就不在了,重编之后优化恰好没把清零缓冲的活编译成 movaps,错格的栈顶上从来没落过一条要十六对齐的指令。ttydemo 的 termios 记录,是自家演示里头一个被编译器向量化的大缓冲,头一个较真的,当场就引爆了。

这一案的教训咱们记两条。头一条说的是回归不挑时间:修好的东西没锁进断言与常量,重构的时候它就是会丢,炸点专挑最不起眼的客人。另一条说的是三个不炸各有一层侥幸:库的校正,优化的选择,还有压根没人用到的指令。这三层侥幸挡住的都是眼下的客人,错格本身是没有修掉的,咱们要是留着它不修,下一个用上向量化大缓冲的,还会死在同一条 movaps 的手里。栈顶对了,演示的秘密问答这才跑通,上一篇欠的实弹在这里补齐。开关有了,接下来该给终端造影子了。
