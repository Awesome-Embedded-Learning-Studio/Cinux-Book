# 消失的那通 call

上一节留的那桩公案,本节咱们来办。案情复述一遍:扩容那案要验的是“100KiB 的大请求把堆顶顶上去了”,章程很朴素——咱们在分配前后各记一次 top,断言后一次的 top 更高。首版跑下来的结果,断言稳稳地红,两次的 top 一字不差。堆的算术上一节刚在长凳上验过六案,进货的代码也就二十来行,咱们盯着它看了半天,怎么推都推不出“顶不涨”。直到有人提议别看 C++ 了,咱们看汇编去。objdump 打开的那一瞬,真相在光天化日之下:测试的汇编里,operator new[] 的 call 根本不存在。不是调错了,是被编译器整个删掉了。请求删了,分配这样的事自然没发生,顶的高度自然没涨,断言自然就红了。

咱们把编译器的脾气说全,因为它值得每个在内核里写测试的人刻在脑门上。C++ 的标准许了编译器一件事:程序的可观测行为之外的东西,它可以随意地重排、随意消灭。什么叫可观测?写文件、打印、volatile 的读写,跨过编译单元边界的调用——数得出来的这几样。new 出来的那块内存,您要是只在测试函数里写它、读它、拿它比大小,漏到外面去的字节一个都没有,那这次分配连同后续的读写,在编译器眼里就是一场可以取消的戏:结果没人看得见,戏就不用演了。咱们平时写用户态程序感觉不到它的脾气,是因为 new 出来的东西总归要交给别的函数,总是要逃逸的。而测试恰恰反着来:测试就是终点站,值到了这儿就该变成断言,哪儿也不去了。

咱们当时的爬梯有三层,一层一层地摆出来,每一层都是一次自以为修好了。头一层的断言里原本有指针比较,拿新块的地址跟旧地址比大小。GCC 拿内存模型的公理把它折叠了:分配器发的新块,跟已释放的旧块必然不重叠,两个不相干地址的大小关系,编译期就能给出一个编好的答案,比较连同它盯着的分配一起删。咱们的对策是把指针转成整数再比——整数没有内存模型,公理的牙咬不动它,这一层算是爬过去了,解决了问题的一半。第二层更隐蔽:比较是整数化了,可这个整数值流进的是哪?还是断言。断言表达式是编译器最容易整体求值的对象,值进的只有断言,所以值还是哪儿都没去,new 还是照删了。爬到这儿咱们才把病根看清:问题从来不在比较怎么写,而症结在于值没有出路。第三层的活,是给值修一条真正出去的路:把它交给一个编译单元之外看得见的边界。测试内核里现成的边界就是串口——Println 是跨翻译单元的调用,编译器证明不了它没有副作用,也就删不了它,而它吃进去的每个参数都必须是真算出来的。于是扩容案把 top 的前后值和块地址原样印了出去,顺手印出的这行字,成了常驻的证据:

```text
[ktest] heap grew: top FFFF808000011000 -> FFFF80800002B000, block FFFF808000001020
```

您拿这行真跑出来的数字对一对数,还能白捡一层踏实:起手的 0x11000,是 64KiB 的底货加 4KiB 保护页。涨到了 0x2B000,多出的正好是 0x1A000——26 页,上一节说的那一页余量,在这儿是看得见摸得着的。从那天起咱们就把一条判别法写进了案牍:ktest 里凡是断言“分配前后世界状态”的用例,动手的第一件事就是反汇编,看的就是那通 call 在不在。断言绿了不算数,算数的只有 call 在场。

这行证据行的本业是防折叠,可它后来又立了一功,立在谁也没想到的地方。收官前咱们重排测试代码,挪动之间弄丢了一个 delete——free 洞复用那案,kFirst 还了出去,kThird 本该落进 kFirst 的洞里。断言看的是两个指针相等,重排之后代码变了形,编译器对这一段的处置也跟着变,断言还抓得住么?看的全是运气。证据行的眼里没有这些,它只管把真话印了出来。机器跑了一趟,serial 上就是白纸黑字:first 一个地址,third 另一个地址——洞明明还了,新块却落在了洞外。咱们顺着这行字回代码里一翻,丢了的那句 delete 当场归案。您体会一下这件事的分量:一条为了让编译器删不掉而添的打印,到头来连写测试的人丢没丢 delete 都看得出来。值印出了编译单元,而编译器删不掉它,写测试的人也瞒不过,一行字把两头都管住了。

咱们补一句尾巴。本节说的是 GCC 删 new,可脾气是全编译器通用的,而且它删的也不止 new——任何“结果未逃逸”的计算都在射程里。往后咱们的测试要是再出现“断言红得没有道理”的案子,别急着怀疑被测的代码,该怀疑的是测试本身有没有被编译器看穿。
