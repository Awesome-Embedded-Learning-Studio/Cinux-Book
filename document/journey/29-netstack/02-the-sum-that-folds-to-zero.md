# 折得到零的和

网络各层的协议,从 ICMP、IPv4 到往后的 UDP 与 TCP,守的是同一门算术:互联网校验和。RFC 1071 说的法子,咱们一句话讲完:字节两两配成大端的十六位字,咱们一路加过去,进位不丢而是绕回去补进低位,加完了按位取反。收的人把同样的活再干一遍,连校验和字段本身也加了进去,和折到了零,这一段字节就算过了关。只要一个字段出了差,答案就折不到零了,这门算术逮的就是它。

为什么用这么别扭的反码,数一数好处就清楚:反码的加法不挑次序也不挑切法,一段字节从什么地方切开、分几段加,答案是一样的,这对往后要把头与载荷分开求和的协议是白送的礼。反码的零有全零与全一两张脸,所以校验和字段里出现全一不是病,是零的另一身衣裳。真要留神的是协议拿全零字段当暗号的场合:往后 UDP 的协议条目里,字段为零表示的是这一段压根不带校验和,那算出了零就得发全一,免得好意算出的和被当成没算。这个特例归协议管而不归算术管,咱们把它写在件的注释里立成边界,算术件只管它自己的算术,协议的暗号协议自己认。

件落在了 base,做成的形态是一个累积器。add 把一段字节折进累加中的和,再 add 再折就是了,value 把答案报了出来,报完了不清零,所以还能接着加。设计里有个讨巧的细节:奇数个字节进来,落单的那个在累积器里等着,与下一段的头一个字节配成字。咱们实在要答案了,它还没等到自己的伴,就当它是高半、低半补的是零,这正是 RFC 自己规定的处理。所以这个件不挑调用方怎么切缓冲,切在奇数的边界上也不怕,奇尾巴它自己就收留了。

件内部咱们不打裸的移位。字节两两配了对,两位各存进了比特区间。进位绕了回去:低十六位加高十六位,加到塞得进十六位了才算完。按位取反这一步用的是掩码按位与。全走 base 的位词汇,一件词汇件自己用的也是自家的词,家法是咱们过目时亲手点下的,当场就照办了。

长凳上考了六个案子,咱们挨个点。头一案是 RFC 自己的例子:八个字节 00 01 f2 03 f4 f5 f6 f7,和取了反是 0x220d。第二案把这答案接在了末尾当第九、十字节,整段重新算了一遍,折到了零,这就是接收方的全部考试,也是这一件存在的意义。第三案三个字节的奇段,输入用的就是 00 01 f2 三个字节,答案报的是 0x0dfe,落单字节补零的路径走过。第四案把同一段字节从第三个字节切开了,分了两次 add,答案还是原来的 0x220d,分段是不改答案的,这一案里验了个正着。第五案全零的输入,取反得出的是 0xffff,零的两张脸在这一案里见面。第六案连着问了两次,输入就是头一案那 RFC 例子的八个字节,两次提问的中间不 add,两次的答案是同一个字,累积器不因提问而清零。六案全过了,这门算术进了 base 的家底。

这一卷里它有两处消费者:IPv4 判的是头,ICMP 判的是整段,判的都是折不折得到零。构包的那一头也用它:校验和字段铺零,整段加完了,答案写回了字段。发与收用的是同一件,这正是它该住 base 的理由,协议的代码里,咱们从此不必再手搓一遍折叠。
