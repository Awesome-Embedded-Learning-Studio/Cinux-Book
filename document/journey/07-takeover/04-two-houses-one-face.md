# 一份脸面,两户人家

上一节末尾咱们留了个悬念:私有一律进 .cpp,为什么内核行、boot 不行。咱们要答这题,就得从一份吃了两卷的红利说起。上一卷咱们交代过:console.hpp 住在 kernel/boot/,boot 和内核 include 的是同一份头,console 的实现躺在头文件的 inline 里。每个编译世界各拿一份自家的实例化,16 位的世界用 16 位的,64 位的世界用 64 位的,谁也没跨界、各过各的。靠的就是它,第五户世界落地的头一天,就能整行整行地打字,咱们一个字都没多写。

红利吃到咱们这一卷,就到了头。内核的 console 脚底下有了真驱动,serial 换成了 .cpp,寄存器连同初始化表全藏进了里头,console 自己退化成了一层薄脸面。好在内核是一个纯 64 位的世界,这一头咱们不担心。可 boot 那头怎么办?最顺手的想法您都能替咱们想到:boot 也 include 内核的头,链接的时候把 serial.cpp 一起链进来不就齐了——声明是一份的、实现是两组的、链接期各归各,怎么听都是正路。

咱们真这么试了,然后吃了这一路最闷的一次亏。串口实现进了 .cpp、链进 boot 的链之后,pm 那个 32 位的世界一跳过去,就没声息了。没有异常的影子,没有面板的遗言,连一句日志都没有——机器安安静静地卡死在 THRE 的等待循环里。这样的死法比三重故障还欺负人:三重故障好歹会复位,而它连动静都不肯给。

毛病出在哪儿?出在 boot 镜像的构造上。它一张镜像里混着 16 位、32 位、64 位三种模式的代码,C++ 的调用约定倒是压根就没承诺过什么“跨模式调用”——您翻遍标准,也找不到这么一句话。SerialPutChar 让 16 位的链编了,32 位的世界隔着 extern 去叫它:名字是链接器认的。可两边的代码对栈面、对调用约定的理解根本不是一套。您可能会问,那摆渡不是天天从 16 位跨到 32 位吗?摆渡那两下能跨,是因为它们从头到尾是咱们手写死的 asm,模式的舞步一步一拍都排好了——那是手艺活才有的特例,普通函数是沾不上这个光的。再看 header-inline 为什么两卷都没出事:函数躺在头文件里,每个世界都在自家的模式里白拿一份实例化,16 位的世界叫的就是 16 位的实现。红利护着的,就是互不跨界的下半句。

所以 boot 只能自成一家。`boot/early/` 里住进了 console.hpp 和 print.hpp 两份自足的拷贝:实现躺在头文件的 inline 里,boot 的每个世界各拿一份实例化,不欠任何人的。这不算新发明——当年 MBR 的输出件就是这么过日子的,自家的头、自家的 inline。只是那会儿咱们把它当穷办法,如今算是把它认成了正式章程:boot 是独立的世界,要抄咱们就大大方方地抄两份。

抄的时候还遇上一个目录陷阱,咱们顺手记下。引号形式的 include,起跑搜索的地方,是写着这句 include 的文件自己所在的目录——祸就藏在它的连锁里。boot 顺手把内核的 print 也引了进来(路径写全了,编译的关也过得去),可这个 print 的头顶上,偏偏有一句引号的 `console.hpp`:它从自家的 kernel/boot/ 目录起跑,一步逮回来的,是内核家的 console。boot 自家的 console 这时也在链上,同一张脸的两份定义,当场爆给咱们看。解法倒不稀奇:咱们不往 -I 里玩注入魔法,boot 干脆带足自家的家当——early/ 的 print 引 `console.hpp`,从自家目录一步就逮到自家的拷贝,天然就闭合了。

等咱们装好之后,串口的初始化在 Stage2Main 的头一行:InitConsole(),七张条子递了出去,UART 就编好程了。后头的 pm、lm 两个世界谁也不必再碰它了。端口 IO 跟 CPU 处在什么模式,是一点关系都没有的——保护模式的那一卷,咱们亲眼看着整行的字跨过模式照打不误,如今换了真串口,这话原样地成立。一个编好的 UART 摆在那儿,咱们哪个世界去递字节,它都是照单全发的。

家分完了,工程里就有了两条 console:boot 的 early 家一条,内核的 driver 家一条。可您把它们俩的脸摆在一起看:InitConsole、PutChar、PutString、Halt——同名同形,连名字空间的落款都是同一个 cinux::console。这就是咱们说的一份脸面、两户人家:脸的形状,就是两户人家共享的全部约定。写代码的人对着同一组名字调用,不必知道自己脚下踩的是哪一份实现。实现各住各的树,链接的时候各归各,谁也不会混进对方的镜像。

体面是拿第一遍的教训换的。考古箱里翻出来:当年串口写了三遍。boot 侧一份实模式的汇编,小内核里的一份 C++,大内核进了场,又重抄了一份。咱们在装载那一卷给这段历史下过判词:同一件事写了好几遍,病根在接力的结构,而不在人。这一遍咱们没有接力,可咱们的边界要是没画直,重抄是一样会找上门来的。头一回就把两户人家的墙砌直:boot 抄自家的,内核养的是真驱动,两份实现共用的一张脸——将来谁翻这段代码,一眼就看得出哪份归了谁。

咱们还剩一户没交代:MBR。您可能想着,它也配一条串口?咱们算过开销:串口连人带表装进 MBR,要多花约 60 个字节——而 512 字节的红线您在引导扇区那一卷就见过,是一根都松不得的。所以 MBR 回它的本行,当的是纯装载器:一句话也不说,报错走 BIOS 的老 teletype,往真正的屏上打。报错的长相就三个字符:

```cpp
void bios_teletype(unsigned char character) {
    unsigned short teletype = 0x0E00 | character;
    asm volatile("int $0x10" : "+a"(teletype) : : "memory");
}

[[noreturn]] void boot_failed(unsigned long status) {
    char const* hex = "0123456789ABCDEF";
    bios_teletype('E');
    bios_teletype(hex[(status >> 4) & 0xF]);
    bios_teletype(hex[status & 0xF]);
    park();
}
```

打头的是一个 E,后面跟两位十六进制的错误码,机器停在 hlt 里睡死了。咱们在卷首卖过关子:面板头部的 `Ready to call bios` 和 `Jump to Stage 2` 两行,从本卷起没了,起居序列的头一行改由 stage2 打——数就是这么算的。代价咱们不藏着:QEMU 是 `-display none` 开的,是没有屏的。MBR 阶段要是真失败了,三个字符咱们看不见,串口日志的头一行也从 stage2 才开始。可真正的开发板上有屏,int10 的字打得上去,口径上是一分不损的。而 QEMU 里 MBR 那几行字,说到底是给咱们看的热闹,机器自己其实一个字都用不着。咱们是舍得花 60 个字节买热闹,还是把字节牢牢地留着保命,这道题您说难选吗?

两户人家的墙砌直了,MBR 也回了本行。咱们万事俱备,把 QEMU 的参数换一换,开机——下一节还有一场静默的官司等着咱们。
