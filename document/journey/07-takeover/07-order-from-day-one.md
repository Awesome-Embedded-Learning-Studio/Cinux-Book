# 接口一次作对

册子造好了,接下来咱们看怎么取用。取页的接口,咱们起手就摆了四个名字:一对分配的 allocate_page 和 allocate_pages,一对归还的 free_page 和 free_pages。您看着可能会想,两页的活儿配四个名字,是不是摆阔了?咱们把里头最不起眼的两个实现摆出来,您就明白谁是谁的特例:

```cpp
[[nodiscard]] PhysAddr allocate_page() { return allocate_run(1); }

void free_page(PhysAddr phys) { free_pages(phys, 0); }
```

单页是什么?就是连续的一页,order 为零说的也是只此一页。四个名字其实是一套语义的两档便捷写法,真正的正主是 allocate_pages 的那个参数:order。它说的是 2 的幂——allocate_pages(9) 要的,是物理上首尾相挨的连续 512 页。为什么偏偏封在 9?您算算:512 页乘上每页 4KiB,合起来正好是 2MiB 的块头。这个数您太熟了——开两扇门那一卷,PD 里一颗条目盖的就是 2MiB 的大页。往后虚拟内存当家的日子,咱们想给一张大页备料,来要的就是这么一整块,而接口当年要是只认单页,等大页要用料了再改签名,所有调用方都是要跟着返工的,这笔代价咱们起手就算清了。

位图怎么兑现“连续”?靠扫描:find_clear_run 在册子里从头找一段够长的空位,找到的就整段记上、首地址原样交出来。扫描谈不上什么聪明,可咱们现在拢共三万多页,扫就扫了,其实快得很。拒绝也走接口:order 出了 [0, 9] 的圈,或者册上已经凑不出那么长的一段,交回来的都是零地址。零当的是“没有”,这在一本册子上是一点不歧义的——低 1MiB 整块圈起,分出去的页永远不会落在零上。还有一条还页的本分得交代:free_pages 的 order 参数,当初用什么 order 拿的,就用什么 order 还。还错了档,册子就坏了。咱们把约定写在脸面上:这是调用方的责任,不是册子替您兜底。进出册子的地址,一律是 PhysAddr——base 家底里这一卷新添的强类型,一个把裸整数抱在怀里不肯撒手的类型:裸整数想冒充地址,编译期就拦下了。它全身上下只留了一个叫 raw 的口子,想取它怀里的裸整数就必须从 raw 走,每一次越界咱们都看得见。

代码的家当怎么摆,咱们照例有分工,而且是三份文件三个家:

```cpp
inline constexpr int kMaxOrder = 9;

inline constexpr unsigned long kLowMemoryTop = 1_MiB;

inline constexpr unsigned long kPmmMaxPhys = 16_GiB;

inline constexpr unsigned long kPmmTotalPages = kPmmMaxPhys / cinux::arch::page::kSize;

inline constexpr unsigned long kPmmBitmapWords =
    cinux::base::bit::Bitmap::words_for(kPmmTotalPages);
```

画出来的这段住在 `pmm_config.hpp`:所有的事实和旋钮(顶有多高、低内存切在哪儿、order 封到几)全写在这一页,咱们改一个数都不用满树找。`pmm.hpp` 扮的是公告面:对外只有声明,外加开头看过的那两行便捷写法,真正的活计全藏在 .cpp。`pmm.cpp` 是干活的:io 和 serial 家立下的“私有进 .cpp”的章程,在 mm 家也原样地适用。旋钮、脸面、活计分了三个家,各守各的——您回头看看鞋盒和交接单,boot 和内核 include 的都是同一份头,里头的数字永不漂移,是同一个立意的另两次落地。

现在说一句要紧的话:位图只是这本册子的第一个后端。为什么这么讲?咱们去考古箱里把当年 PMM 的编年史翻出来,它前前后后改了三回。头一回是出生:小内核里的位图分配器,吃的是 E820,跟咱们今天这本形态相仿。第二回是大内核的重写——大内核进了场,把小内核的家当整个重抄了一遍。这样的病,咱们在装载那一卷见过,当年的判词到今天还作数:概念没变,代码也重来了一遍。而这一遍没有接力,病根已经除了。第三回发生在第一遍的后期:位图换成了伙伴系统 buddy。而那一回不是病,算是一次有动机的进化,它的动机是碎片化:用着用着,空闲页全碎成了零星的单页,连续的大块凑不出来了,位图式的扫描开始吃亏。第一遍的终态里,allocate_page 一家的四个名字一直活着。换 buddy 的时候,新代码注释里的原话长这样:

> 咱们照录:`Replaces the PMM's flat bitmap`
> ——咱们替换的只是扁平位图后端,而不是接口。

所以这一遍“一次作对”,对的是接口和出身,而不是把 buddy 提前搬来。您想,今天咱们总共三万多页,碎不碎的问题根本谈不上。buddy 那套切块合块的机关,没有碎片化的病,就没有它出场的理由,真提前请来也只会平白地多讲一层。等哪天咱们真见了那个病,空闲页剩了不少,大块却凑不出来了,那时候咱们再换后端,接口的一个名字都不用动,调用方的一行都不用改。换后端不换接口的路,第一遍当年就跑通了,咱们这一遍,只是把 order 从第一天就写进了接口的签名。

咱们在本站还顺手办了一件小事,性质跟把话说诚实是一路的,咱们办完这件就收尾。上一卷讲门的时候留过一句话:一张 PD 满打满算 512 颗,一颗盖住的是 2MiB,门实际盖到的顶就是 1GiB。可九判里报的那道顶,一直报的是 4GB——那是摆渡 32 位平坦段的射程,不是门的。鞋盒要是把家报到了 1GiB 到 4GB 之间,九判是放行的,装载也是成功的,可门偏偏开不到那儿,而 CPU 一进门,前头就没了路。这一卷把检查的顶收到门真正盖到的地方:它的名字叫 kHandoffDoorTop,数值定在了 0x40000000。拒辞也从当年的 `beyond 4G ferry reach`,换成了 `beyond handoff doors`——门盖到的高度,咱们的话就说到多高。test_image 替咱们看住了四处。头一处看的是常量,kHandoffDoorTop 的值必须是 0x40000000。第二处看的是压线:尾巴恰好压在 1GiB 顶上的,是放行的。第三处看的是越线:尾巴越过顶一个字节的,测试当场就拒了。第四处看得最远:把家报到 4GB 之外的,同样当面拒了。至于压线为什么算够着,道理在 ValidateImage 那半开区间的判法里,它判的是 kEnd > max_paddr,尾巴恰好落在顶上的不算越线,越过去了才算过。门要加高的那一趟,归往后虚拟内存当家的卷,咱们在这儿,把话对上嘴就算完工了。

四个名字定了落位,门顶的数也对上了。咱们剩下一件事——开机验收,把数好好地对一遍。
