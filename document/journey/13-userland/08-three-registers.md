# 只烧三个寄存器的承诺

咱们给 hello 的成绩数一数:合同上写的是两行字,串口上只数出了一行。无声丢掉的是第二条 write,exit 倒是照常把任务排干,把 Main 还了回来。咱们想等一句报错,结果一句都没等到:hello 压根不检查 write 的返回值,这一丢就丢了个干干净净。单发单收的 syscall 全都正常,坏消息是藏在连发里的:头一行字与退场之间的那一段,夹着一次没人看见的失败。

咱们要在破案之前把两份合同摆上桌。头一份在用户那边:C 的调用约定把寄存器分成了两族。rbx、rbp、r12 到 r15 是 callee-saved 的,函数保证的是原样奉还。rdi、rsi、rdx 这些参数寄存器是 caller-saved 的,保它们的事归调用者自己,被调的随便用。第二份合同是挂在门上的,内容就是 Linux 对用户态的公开承诺:咱们在包装里向编译器许过的,也正是它——过门烧掉的只有 rax、rcx 与 r11 三个,再没有别人了。咱们把两份合同一叠,编译器的算盘就打响了:过门不烧 rdi 的话,fd 的 1 就可以一直驻在 rdi 里:两次调用,装载的只有一次。

然后咱们上反汇编。寄存器被毁的案子,汇编才是终极的现场。咱们把 hello 的二进制摊开,两连写长的是这个样子:

```asm
mov    $0x1,%edi
mov    $0x19,%edx
mov    %rdi,%rax
mov    %rsp,%rsi
# —— 中间几拍在栈上拼字符串,与寄存器无关 ——
syscall
mov    $0x1f,%edx
mov    %rdi,%rax
lea    0x20(%rsp),%rsi
syscall
```

您看第一次调用之前,rdi 里装的是 1。第二次调用之前的 edx 是重装过的,装的正是第二个长度。rsi 也重装了,装的是第二串字。连编号那一拍用的都是 mov %rdi,%rax:编号是从 rdi 里派生的。唯独 rdi 自己是从头到尾没再动过的。编译器其实不是偷懒,它拿着咱们的 clobber 清单在办事:rdi 不在名单上的话,它就认定 rdi 是保值的。

内核这边呢?rdi 恰恰是 C 约定里排头的那个参数寄存器,caller-saved 的身份,挨的活也最多:InvokeSyscall 收编号走的路,头一个走的就是 rdi,后面一路的 C++ 想怎么用就怎么用。而第一版的出口,只还原了 callee-saved 的 rbx 与 rbp,加上硬件自保的 rcx 与 r11。rdi 出门的时候是什么,全看内核最后一段代码留下了什么。后来咱们复盘这一案,给柜台的拒收路径补了一行印再跑:第二条 write 进门的时候,编号栏里躺着 0xFFFFFFFF8028A6E0——一个高半区的内核地址,内核哪一段代码留下的指针(链接布局挪一挪的话,这个数是会跟着挪的,可它的高半区身份不会变)。编号远远越过了表长,柜台照 -ENOSYS 把它拒收了——整整齐齐,也是悄无声息的。exit 为什么幸免?看它开头那两拍:0x3c 进了 eax,0x2a 进了 edi。编号的 60、参数的 42,跟 fd 的 1 不是同一个常数,编译器老老实实把 rdi 重装了一遍。它这回活了下来,靠的是代码形状、不是正确性。换个程序、换个常数的话,倒下的就是它。

咱们要做的修法,就是把那句承诺兑现回来——出口把六个 caller-saved 从帧里还原了回去:

```asm
movq 32(%rsp), %rdi
movq 40(%rsp), %rsi
movq 48(%rsp), %rdx
movq 56(%rsp), %r10
movq 64(%rsp), %r8
movq 72(%rsp), %r9
```

十二槽收的本来就是客人的全部身家——要还的东西,帧里是一件不缺的,缺的只是出口肯不肯还。六拍补上了,承诺也就兑现了,咱们再跑一遍,串口上两行就都到齐了:

```text
[user] hello from ring 3
[user] two writes, now exiting
```

这一案有位当年的姐姐,咱们开考古箱把她请出来,两张面孔像得您会笑。当年 shell 也演过一回:回显是正常的,命令全失效了。echo 没了输出,clear 也不清屏了。trace 打到了最底下,line 成了空串,len 只剩了 1。反汇编里见了真凶:read_line 内联之后,写入的位置 pos 驻在 rbx。而当年的入口汇编拿 rbx 暂存返回值,释放帧的时候又不恢复,callee-saved 就这么被毁了。pos 每转一圈就被返回值的 1 压回原处,每个字符都写进了 line[1],行首的 line[0] 从出生起就没人碰过,末了收了尾,剩下的就是空串。修的路子也像:返回值挪去了 gs:16,rbx 从帧里还原了回来。今天咱们帧布局的断言群里,给 rbx 留的备注写的还是这桩旧案,教训压进了编译期,一直留到了今天。同根的地方在于:两案烧的都是 ABI 的约定,而硬件只救 rcx 与 r11,剩下的全凭内核的自觉。不同的枝在于:当年是入口亲手毁了 callee-saved,这一回是内核的 C 代码碾过 caller-saved、出口没还。其实当年出口同样没还 caller-saved,只是当年 shell 的代码形状恰好躲开了这一类寄存器——同一个病,两遍各疼了一次。当年留下的四条教训,咱们一条条数过来,四条放到今天都是活的:ABI 的约定是双向的,内核正是兑现的一方。硬件救的只有 rcx 与 r11。一串功能全体失效的话,头一个该疑的就是基础设施。末了,终极的手段还是反汇编。疑基础设施的教训,这一回咱们得倒过来读——病是在基础设施里的,症状却只在一个程序的第二次调用上露头。教训是两头都要记的。

承诺补齐了,通道这才算真的通:写出去两行,收到的也是两行,退场也不拖泥带水了,连发也不再失忆了。可这一卷的更早处还压着一桩旧案:在柜台施工的那几天,GS 的那头出过一次翻案,咱们当时看在眼里的全是真的,断出来的却是错的。
