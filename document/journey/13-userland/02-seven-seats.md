# 七个座位与一口备用锅

咱们给 GDT 添座位,添完是这么一张表。咱们把新次序报一遍,您对着 gdt.hpp 里的 KernelGdt 数,一个槽的出入都不会有:

```text
槽 0    空槽                  选择子 0x00
槽 1    内核代码段            选择子 0x08
槽 2    内核数据段            选择子 0x10
槽 3+4  TSS,十六字节占两槽    选择子 0x18
槽 5    用户数据段            选择子 0x28,客人手里是 0x2B
槽 6    用户代码段            选择子 0x30,客人手里是 0x33
```

表的长度是 56 字节,坐满了七个座位。客人那两行的次序有讲究,不是随手排的:SYSRET 下楼时,拿基值加 8 得到的是数据段,加 16 得到的是代码段,所以数据段必须排在前头。客人那两行的写法还各有两个,也不是排版犹豫:选择子的低两位是 RPL(请求特权级,持证人此刻的身份),选择子一旦带上了 3,等于递名片的时候就报了客人的身份。0x28 是槽 5 的裸值,0x2B 是它带上 RPL 3 的样子,客人真正递到 CPU 手上的永远是后者。这个差别不是凭空来的,底下藏了一桩旧案,咱们稍后就讲。

客人的两个座位怎么编码,咱们照家里的老办法从词汇表拼。SegmentAccess 里添了 kRing3,内核代码段的 access 是 0x9A,把特权两位从 00 抬到了 11,就是客人代码段的 0xFA。数据段走的是同一条路,0x92 换成了 0xF2,别的字节一个不动。长模式下段寄存器的 base 和 limit 早被硬件架空,描述符剩下真正管事的,就是 access 字节里写着的特权级,所以客人的座位和自己人的座位长得几乎没差别,差别只在坐的人。host 侧的长凳照例全数复检,test_gdt 十七件:56 字节的表、user 半边的 0xF2 与 0xFA、词汇表拼出来的字节与位拼出来的一一相符、TSS 的 base 拆分、槽位互锁,一案一案地对过去。

七个座位里段占了四个,连成一对的槽 3 和槽 4,坐的是那口锅:TSS。x86 早年的设计里有一套硬件任务切换,TSS 是那套机制的档案袋,长模式废掉了这套机制,只给它留了一条尾巴,咱们也从没走过硬件切换——它今天挣这双槽的座位,图的就是一件事:rsp0。客人跑在楼下的时候,中断来了,CPU 得把自己挪到 ring0 的栈上才开始办事,而挪到哪个栈,看 TSS 的 rsp0。TSS 的本体是 104 字节,布局是架构写死的,偏移不归咱们挑:rsp0 住在 0x04,而七口 IST(中断栈表,给指定中断另配独立栈用的表)从 0x24 起。咱们只填 rsp0 一个消费位,IST 七口全零——那是刻意留着的未来,不是忘了。头文件里的一排断言把每个字段按架构偏移定住,谁改了布局,编译器第一个就知道了。

TSS 的描述符为什么占两个槽?说穿了是装不下。普通的描述符是八字节,装完了 limit 和 access,base 的 64 位装不进,只好拆成两截:低 32 位跟 limit 挤的是头一个槽,高 32 位独占的是第二个四字,第二个四字剩下的位置按 ABI 必须为零。access 的取值是 0x89,咱们一位一位地读。亮着的最高位,说的是它在场。特权两位写的是 0,它坐的正是 ring0。余下的类型码把它归进了系统型,拼到底是一个可用的 64 位 TSS。limit 填的是 103,是拿 104 字节减一得来的,单位用的是字节,不开 4K 粒度——一口 104 字节的锅,够不着 4K 的刻度。还有一处您得看清:编译期造表的时候,TSS 的双槽故意全零。Tss 实体落在内存哪个地址是运行时的事,编译期的手里没有这个数。所以 LoadOwnedGdt 在 lgdt 之前现场编码:把实体的真地址和 limit 填进双槽,然后咱们才装表、压代码选择子、远返回换 CS、挨个重载数据段寄存器。接线的三行是这样的:头一行装的是 GDT,第二行让 ltr 把 0x18 装进了任务寄存器,末一行管的是给 GS 安家——这一行的讲究,到了下一节再讲。

ltr 这一步自带一道白送的验收。您别把它当哑巴指令:装任务寄存器前,CPU 当场就把描述符校验了,槽位、access、limit 有一样错的,装的那一下直接异常。所以您在面板上读回 tr=0x18,本身就是一场考试过了。面板为此添了一行:

```text
[kern] tss loaded tr=18 gs base FFFFFFFF80289630 efer 500
```

gs base 后头那串地址每次链接都要挪窝,您自己机器上跑出来跟书对不上才是正常的。efer 的 500 也请您记着,下一节咱们拆它。这一行是摆桌当时的原样,这一卷后头把系统调用的门拧开,所以 efer 会翻成 501,到了那儿再对数。

咱们在 rsp0 上多站一会儿,因为它往后要伺候的路有两条。打楼下上来的 syscall,栈从 GS 那块里的 kernel_rsp 里拿,那是下一节安的家。ring3 正跑着的时候中断进来,栈从 TSS 的 rsp0 里拿,那是咱们刚装好的锅。两条路一个源头:都是当前任务的内核栈顶。将来切到用户任务的时候,两个数的更换得绑在一起,同源而不同径,落了哪一条都不行。这口锅眼下还是空的,咱们还没把客人请进门。

座位次序里藏着一只旧年的拦路虎,咱们把当年的案子讲一遍,您看证据是怎么一段一段收紧的。SYSCALL 和 SYSRET 进出用的段不写在指令里,写在一格叫 STAR 的 MSR 里:SYSRET 下楼拿 STAR 的高位当基值,加 8 算的是 SS,加 16 算的是 CS。咱们当年第一遍,这个基值写的是 0x20。shell 好不容易进了 ring3,刚打完了招呼,头一次时钟中断就吃了一记 #GP,整台机器躺了,报的错误码是 0x28。

第一步咱们把崩溃的 RIP 用 addr2line 对回源码:落在时钟中断的桩里,反汇编出来看了一下,出事的是 iretq 这一拍,它管的差事在回程上,进门的那一段没事。第二步咱们分解错误码。#GP 的错误码在这里就是 CPU 正要装载的那个选择子:0x28 右移了三位,得到的是槽 5 的用户数据段。TI 位说的是它住在 GDT。RPL 记的是 0。iretq 回 ring3 要重装的,正是中断来时压进栈里的用户 SS——也就是说,shell 住在楼下的那段时间,SS 一直是 0x28:槽位是对的,身份位是缺的。第三步咱们在时钟的处理器里加打印,专打中断帧的 CS 和 SS:内核态的 tick 一路 CS=0x10、SS=0x18,值都是干净的。这一对数您拿今天的表去对会对不上,因为当年的表编号跟今天不一样,内核代码段坐的是 0x10,数据段坐的是 0x18。今天的两个号,一个给了数据段,一个给了 TSS,按当年的表一换算,正好落回自家内核段的座位上。而 shell 下去之后的那一次,CS=0x33(对的,RPL 3 也带上了),SS=0x28(错的)。第四步咱们排空两个嫌疑人:回读 STAR,与写入的值分毫不差。再 dump 一下 GDT 的第 5 槽,读出的 access 是 0xF2,DPL 的位置标着 3,两处也对上了。到了第五步,嫌疑人就只剩 SYSRETQ 自己了。按手册的说法,它装 SS 的当口会顺手把 RPL 摆成 3,可这件事各家 CPU 有各家的做法,当年的模拟器干脆不摆——SS 就带着 0x28 下了楼。而中断一来一回,iretq 重装了 SS,装着 0x28 回 CPL 3 的地方,CPU 拒收了,当场报了一次 #GP。

修法一行:咱们把基值从 0x20 改成 0x23,RPL 也直接编进了基值。您自己加一遍:0x23+8=0x2B,0x23 加上 16 得出的是 0x33,而不管 CPU 摆不摆身份位,加法的结果天生带着 RPL 3。Linux 也是这么写的。那一回救火的笔记,记了两百来行。而这一遍,0x23 打从第一天就编在了 kSysretStarBase 里,后头四条 static_assert 把 +8、+16 两个落点和槽五、槽六两个座位全锁住了——谁想动基值,编译那一秒它自己就招了。

七个座位一口锅都备齐了,断言全数过了,面板替咱们作证。不过客人要跨进跨出,光有座位不够:SYSCALL 和 SYSRET 的门轴开在 MSR 那排暗格里,而咱们连打开暗格的工具都还没有。
