# 蹦床,和它欠下的退场

照片的架子有了,本节咱们把照片拍出来。咱们要让一个新任务上 CPU,就得替它答好这么四道题:栈在哪、从哪条指令起跑,跑完了去哪、拍出来的照片交给谁。答这四道题的活分两层:纯算术的一层叫 PrepareTaskContext,给它地址它就能办,所以长凳上直接可测。真分配的一层叫 TaskBuilder,页的来处是名册、对象的来处是堆,这层的活只有内核自己能干。这个劈法您看着眼熟:内存当家那一卷的堆把算术半边和页半边劈开,是同一次经验的再版。

咱们看任务本身长什么样。Task 的身子很薄:一副 CpuContext、一个 state、一个 tid、一个名字,末尾的是 stack_base。stack_base 这个字段咱们单独说一句:释放栈的时候,要交还的正是整段分配的起点,它记的就是这个起点。任务一旦跑了起来,rsp 的取值千变万化,只存得住 rsp 的话,退场那天就找不着家门了。咱们要的字段就这些,没有一样是多出来的,也没有一样是缺着的,将来要用排序权重、要用地址空间的字段,等它们的消费者进门再添,这是咱们立过的家法。

咱们把 StartPlan 的五个地址递进去,把照片填出来的就是 PrepareTaskContext:

```cpp
void PrepareTaskContext(cinux::arch::CpuContext& ctx, const StartPlan& plan) {
    cinux::base::SetBytes(&ctx, 0, sizeof(ctx));
    plant_clean_fpu_image(ctx);
    auto* const kBottomWord = cinux::base::PtrAt<unsigned long long>(plan.stack_bottom);
    *kBottomWord            = kStackMagic;
    ctx.rsp                 = plan.stack_top;
    ctx.rip                 = plan.trampoline;
    ctx.r12                 = plan.entry;
    ctx.r13                 = plan.exit_hook;
}
```

头一行写的是全零,第二行给零里种上干净的浮点出厂态,后面的六行,五处是在往照片里填值:rsp 的落点是栈顶,rip 的去处是蹦床,入口函数的地址进了 r12,退场钩子的地址进了 r13,魔数埋进了栈底。剩下的一处干的是取址,到栈底拿回地址,好让魔数有地方落笔。咱们倒着说。魔数 0xDEADC0DE 埋在栈的最底一个字上,它是溢出的验尸材料:栈往下长,长过了自己的 16KiB,头一个被改写的就是它。咱们得把它的能力说准:它不拦住任何人,踩穿了它才会变——它是事后检测,而不是护栏,真到崩溃转储的那天,栈底这个字还是不是原来的值,能替咱们指认死因。栈顶这边 rsp 落在 16 的倍数上,这不是洁癖:调用约定要求函数入口处的栈按 16 步点站好,咱们马上会看到蹦床的第一个动作就是 call,压一个返回地址进去,拍子正好就合上了。

干净浮点映像里也有一个字:出厂的 x87 控制字 0x037F、SSE 的 MXCSR 0x1F80,两处种对了,新任务头一次做浮点运算才不会继承一堆别人的舍入脾气。这里咱们如实记一笔首版的错:MXCSR 那个字,咱们头一回种在了 512 字节映像的第 24 字节上,而 FXSAVE64 的布局里它住在第 32 字节。错在哪?24 这个数不是凭空来的:32 位 FXSAVE 的老布局里,MXCSR 的家就安在第 24 字节,FXSAVE64 把它挪到了 32。照着旧布局或者 32 位时代的旧资料写,种下去的位置会精确落在第 24 字节上,首版踩的就是它。长凳上的 test_context 拿断言一验,FCW 是对的,MXCSR 却是错的,当场就按住了。这类错在机器上死不了人,可哪个任务的头一次浮点异常被种错的控制字吞了,查起来要绕多大的弯,您想想就知道断言值多少钱。

本节的正主,这回轮到蹦床了。咱们连着它要防的那桩旧案,一起看它的三个动作:

```asm
TaskTrampoline:
    sti
    call *%r12
    jmp *%r13
```

新任务的照片里 rip 指着这儿,ContextSwitch 的最后一跳跳到这儿。蹦床的头一个动作是 sti,把中断总闸拉开——为什么必须在这儿开?开在照片里行不行?这里头有个次序上的讲究,搁到讲抢占的时候再回头看,您会看到它埋得有多深。接下来 call 入口:入口是个普通的 C++ 函数,`void entry()`,它该跑什么跑什么。末一跳是 jmp 退场钩子:入口函数 return 了,call 压在栈上的返回地址把它送回蹦床这一行,蹦床随即跳进统一的退场。咱们这三行汇编,藏了两处心眼。头一处讲的,是 call 与 jmp 的分别。当年的头一遍,咱们用的是裸 jmp 直接跳进入口函数,栈顶还压了一个假返回地址当保险。入口函数老老实实地跑完 return,CPU 从栈顶弹出的就是那个假地址,一跳就跳了过去——假地址就是栈底魔数一类的值,RIP 指向了 0xDEADC0DE,取指当场翻了车,结果一声 triple fault。call 与 jmp 的全部区别就在一个返回地址:call 压了,而 jmp 不压。用 call 的话,入口的 return 有家可回。用 jmp 的话,return 弹到的就是栈上恰好躺着的随便什么值。那一年的教训,这一遍落在了蹦床的三个动作里。

第二处的心眼,是咱们让退场只有一个。入口正常返回的时候要退场,将来显式自杀的时候也要退场,全都汇到 exit_hook 的一条路上:钩子里的实现是 `Scheduler::self().exit_current()`,把任务标成了已死、发起切换,把 CPU 让给了下一个人。万一调度器把控制权还了回来(这在不该发生的路径上),收尾的一句 Halt 兜底,机器停下而不是乱跑。

末了是真分配那层,TaskBuilder 的 build():入口没设,直接空手而归。名册 allocate_pages 拿的是 4 页连续物理页,凑成的一副内核线程栈有 16KiB。地址经直接映射的窗换算成虚拟门牌,栈就立在 direct map 的地界上。然后咱们 `new Task{}`,再由 PrepareTaskContext 把照片填好了。分配的两步之间有次序,就有失败组合:页到了手、new 却空了,咱们的章程是把页原样还给名册再空手而归免得留下半件行李。分配的次序里还有一个为什么:栈为什么走 direct map,而不在堆窗口里切?内存当家那一卷挂在墙上的地图,给 vmalloc 与内核线程栈预留的门牌立了,可它的分配器还没影。direct map 是现成的路,每个进来的物理页自带门牌。真到栈要搬去预留门牌的那天,得有立起来的分配器,这笔搬家的事咱们记在册上。

任务会造了,照片会拍了。四道题答完了三道,还差最后一道:照片拍完了交给谁、谁说了算该谁上 CPU。那是调度器的事。可在咱们请它出场之前,来了一位不速之客——咱们得赶在前面还一笔上一卷的旧债。
