# 第三扇门

上一卷收工的时候,面板上的字全走的串口——屏幕黑着,点火的日子还没到。配屏那一卷切好的画布,参数在交接单上躺了几卷:物理地址、行跨度、六个颜色位域,咱们一笔都没让它丢,就是没等来取的人。这一卷的头一件事,咱们就是把第一位消费者请出来。不过请出来之前,咱们得答一问:那块画布,门够得着吗?

自然是够不着的。咱们为这事临时打过一回点,把单子上的地址报出来看过,验完就撤了:显存的物理地址是 0xFD000000,跑到了第四个 GiB 里头。而咱们手里只有两扇门:PML4 的第 0 项和第 511 项,底下通到的是同一张 PDPT,再往下垫的是一张 PD,页页是 2MiB 的大页,门到 1GiB 就到头了。这个顶咱们在内存名册那一卷还专门把话说诚实过:门盖到多高,咱们的话就只说到多高,门顶 kHandoffDoorTop 定的就是 0x40000000。显存离门顶差了将近三个 GiB,中间一整段都是没开过路的野地。

为什么这件事排在一切画图之前,咱们把话立在头里:映射在前、画图在后。显存驱动写像素——写的就是内存,可地址没过表就去解引用,CPU 走到了那儿一查门,门是空的:页错误起步,坏处叠坏处就是连遗言都没有的三重故障。好在咱们如今有会疼那一卷立的桩,真出了事,转储里的 cr2 会把肇事地址一字不差地报出来。不过转储是事后的验尸,而不是免死牌。画面不亮的时候,十回里倒是有九回,路压根就没通——像素算错的,只占剩下的那一回。

开门的活在 boot 建表的函数里,门那一卷立的 BuildHandoffDoors,咱们这次添的是设备门那一段。规划门的是个纯函数:

```cpp
constexpr DoorSpan PlanDeviceDoors(uint64_t physical, uint64_t bytes) {
    DoorSpan span{.first_index = physical >> kHugePageShift, .count = 0};
    if (bytes == 0) {
        return span;
    }
    uint64_t const kLast = (physical + bytes - 1) >> kHugePageShift;
    span.count           = kLast - span.first_index + 1;
    return span;
}
```

输入一份区段——物理地址加字节数,输出的是首门号加门数。显存这头要的字节数,咱们按行跨度乘高来算:4096 乘 768,得的就是 3MiB。端点是往外扩的:区段要是骑着 1GiB 的边界,两头都取整到了门上,一段也漏不了。咱们代进去算:首门号是 0xFD000000 右移 30 位,得的是 3。末字节也落进了同一扇门,所以门数是 1——一扇门就够了。

多粗的门,当时咱们摆过两版。一版是 2MiB:在 PDPT 和显存之间再垫一张独立的 PD,咱们把索引按 9 位截取,只盖显存那 4MiB 的地界,图的就是精确。另一版是 1GiB:PDPT 的 3 号项直接写成一颗大页,中间不再垫表——PDPT 的条目头一回自己当页,而不是当指路牌。1GiB 的豪爽是有代价的:整个第四个 GiB 从此敞开了可写。可咱们对照 E820 的图谱看过,圈进来的一个 GiB 里压根没有 RAM,本就是个纯粹的空洞,骗不了人。顺手还把 APIC 那一带 0xFEE00000 的未来 MMIO 也盖进了门里,省了往后再开的工夫。2MiB 的精确也不是白来的:得添一页新表、多记几处布局上的事实,而且现成的 PD 不能复用——它同时还是低 1GiB 门的本体,咱们若把它复用,低区里一段真 RAM 就成了显存的别名,名册将来要是发了那些页,事就来了。咱们定了 1GiB。到了建表那边,咱们把规划接上,boot 在还没递出执行流的时候,从交接邮箱里读出存着的单子,把门一扇一扇填进了 PDPT:

```cpp
    auto const&    frame = cinux::base::PtrAt<const cinux::boot::BootInfo>(
                               cinux::boot::LoadWord(cinux::boot::kHandoffMailboxInfo))
                               ->framebuffer;
    uint64_t const kFrameBytes =
        static_cast<uint64_t>(frame.pitch) * static_cast<uint64_t>(frame.height);
    auto const kDoors = PlanDeviceDoors(frame.physical, kFrameBytes);
    for (uint64_t door = 0; door < kDoors.count; ++door) {
        uint64_t const kIndex = kDoors.first_index + door;
        kPdpt[kIndex]         = MakeHugePageEntry(kIndex * kHugePageSize, kWritable);
    }
```

咱们让内核那头拿单子上的物理地址原样当门牌用——恒等那扇门,高半那边也就不另发牌了,写显存的手感跟写自家数组一个样。长凳上 page 那件添了三根哨兵,分别管真区段、骑界端点的外扩和零长度。

门这一章还欠着一段没结的官司,咱们整个记在这儿,因为它就是门的事。第一版走的其实是 2MiB,而且立门的时候门后头一个消费者都没有,验不了真,只能等驱动立了起来。等画面那几件都立齐了,头一笔真往显存里写下去的时候,开机当场页错误:cr2 报的正是 0xFD000000,桩把现场接住了。咱们的第一反应是打印门表自证:读回来的三项全对。接着就滑向了怀疑环境:咱们跑在嵌套的虚拟化里,EPT 的大页跟 MMIO 会不会有说不清的交互?换 1GiB 门一试,全链通了。眼看就要结案成环境问题了,复盘把案子整个翻了过来。

翻案的是一笔换算,咱们把它摊开:0xFD000000 右移 21 位,得的是 0x7E8,它是 2MiB 页的页帧号,却当不成 PD 里的索引。而在四级页表里,每级的索引都是 9 位,PD 的索引得再按 0x1FF 截一道:0x7E8 截完是 0x1E8。首版把 0x7E8 当成了下标,kPd[0x7E8] 一写就写出了表页:表页在 0x5000,0x7E8 乘 8 的积是 0x3F40,算出来的落点是 0x8F40,表页之外的空白 RAM。所以写不炸,还读得回——连临时打印去验都是对的。而 CPU 真正去查的 kPd[0x1E8] 住在 0x5F40,里头从头到尾是零——亮的 P 位一个都没有,页自然也就不存在了,跟错误码里报的逐位吻合。

这段官司咱们慢慢结,咱们把三条教训条条入册。头一条:每级的索引 9 位,页帧号和表内的索引是两个数。最险的地方在于,PD 的索引 (va>>21)&0x1FF 和 PDE 里的物理字段 va>>21 同源:同一笔右移 21 位,首版在填字段那头用对了,在当下标这头用错了,而且错得特别有底气。再一条是关于自读自证的:自读自证不算证据。验证读的地址必须独立推导,跟写入共用的是同一套算法,读回来的只是自己错误心智的回声——咱们打印门表三项全对的时候,读的正是 0x8F40 那个错误落点自己。末一条:哨兵的金位不能跟实现共享心智。长凳上立的那根哨兵,把 0x7E8 断言成了期望值——测试和实现用同一颗脑袋想错同一件事,互证互绿——红是永远不会来的。

另有一句关于诊断次序的话,跟三条教训一样值钱:咱们停在疑自己上太快,滑向疑环境的时候又太顺。打印只对了一回,就奔着虚拟化去了。正序是把自家每一步运算摊开重验:咱们乘回去对一对,截的位验一验——换个数再算一遍。这些都过了,再动环境的念头。这一回环境是清白的,判词就落在这儿了,给往后的日子长记性。

门定成了一颗 1GiB。2MiB 那版把索引修对了之后,实测同样是绿的,咱们把两版的对照记在这儿,代码里留下的是 1GiB——下一卷虚拟内存接管的时候,4KiB 的精修自然会来。不过门后头眼下还是一片黑,咱们要有字,得有字的模样打底。下一节的活,是把一盒字模装进内核的镜像。
