# 真实负载的一串修复

立目标那一章的话音刚落,头一轮真负载就跑散了架。散架的方式很老实,哪里的件没造齐,响的便是哪里。咱们把响过的地方挨个记下,归成了三摞、头一桩案子单讲,它的名字叫 freestanding。

其实内核自己,就是一种不靠任何运行库过日子的程序。想在自家盘上把它编出来的话,躲不开的还有一只更小的问题。盘上的 GCC,编一只无库的程序,编得出来吗?答案一开始是编不出来,咱们一层层剥,剥出了五样毛病。头一样在脚本自己的身上,它偏偏没带状态标记,跑到哪一步停的都说不清。第二样是盘挂错了,启动镜像被当成了 AHCI 数据盘挂上座。第三样在串口的那一头,行缓冲只认得下百十来个字符的样子,长命令得拆成短的,驱动还得等提示符真回来了再发下一条,时序抢了拍,两条命令就搅在了一起。第四样是文件系统的:append 与 truncate 压根没办过,`>>` 拼不出该有的接龙,`>` 也清不掉旧的内容。藏得最深的是第五样,发行版的 GCC 默认开着栈保护,检查失败时要喊的那声呼救(`__stack_chk_fail`)住在运行库里,无库的程序叫不应它。

五样毛病咱们一样一样治。

治齐了,验证的家什是一只最小的程序。五条 echo 把源码一行一行地拼进 `/free.c`,咱们看着它拼。

```sh
echo 'static long sys(long n,long a,long b,long c){long r;' > /free.c
echo 'asm volatile("syscall":"=a"(r):"a"(n),"D"(a),"S"(b),' >> /free.c
echo '"d"(c):"memory","rcx","r11");return r;}' >> /free.c
echo 'void _start(void){const char m[]="freestanding on Cinux\n";' >> /free.c
echo 'sys(1,1,(long)m,22);sys(60,0,0,0);}' >> /free.c
gcc -ffreestanding -fno-stack-protector -nostdlib -no-pie -o /free /free.c
```

您看头两行,syscall 的直写被摆进内联汇编,一号干的是写,六十号干的是退场。那句 `freestanding on Cinux` 带上了换行,数出来的是二十二个字符,命令里的 22 说的就是它。编出来跑了一遍,串口上回的正是这一句。旗子里的 `-fno-stack-protector`,咱们把口径分开说。它关的是发行版默认塞给无库程序的那层检查,内核自己的编译命令里明写着强栈保护,守卫的值由内核自己供给,那一侧照旧是开着的。当然谈不上谁特殊,各守各的门。

案子里的第四样归到头一摞,咱们顺着它把文件系统这摞摊开。append 真办了,取当前文件尾与提交的这两步,都关在后端的那把写锁里,两个写的人同时追加,后到的老老实实接在前到的后面。truncate 也办了,数据块收了回来,直接块清了零,尺寸与块数也归了零。open 带 O_TRUNC 的次序立了章程,描述符到了手才动刀,分配要是失败了,人家的文件一根毫毛都不能少。

文件名的上限也放宽到 ext2 格式认的二百五十五字节,Python 的扩展模块这才载得进来。目录的洞咱们这会儿还没看见,它要等全量真跑起来的时候才开口,案子的收尾压到这一章。

第二摞是在内存的,唱主角的是 brk。懒到家那一卷里四个号开窗的那一章给 brk 立过的脾气,您翻回去还能读到,目标对齐到页的边界,落在界外的夹回边界,回的也是页边的数。壳里那点用法是过得去的,glibc 的分配器可不认,它把堆顶当的是字节刻度,断点被抹到了页边,它记下的家当与内核给的对不上,cc1plus 编到一半 free 一个指针的时候,自己都认不出来了,喊出的就是一声 `free(): invalid pointer`。修好了之后,咱们把册子里各记各的两位请出来:

```cpp
    heap_.end   = kWanted;
    heap_break_ = target;
```

页的边界照旧按页记,断点是自己按字节记的,量的是同一段堆,两把尺子各量各的。问询回的也是字节值,咱们把长凳的案卷念一行,0x101234 这样的目标进去,回来的还是 0x101234。0x101FFF 是在堆里的,0x102000 已经在堆外了。非法的目标,断点原地不动,内核不再把越界的请求偷偷夹成合法值。缩堆交还的是整页,再长回来的时候,补零按的是匿名页。munmap 在堆里打洞的话,断点是不走的。

第三摞管的是号码与寿命,咱们挨件过。pipe2 认得了 O_CLOEXEC。close_range 学齐的是三种读法:关一段的,只标记 close-on-exec 的,或者把表克隆成自家独用再动手的。要它的是机内的 Python:起孩子之前把描述符收拾得干干净净的。fsync 与 fdatasync 从分发门外的明说不办变成了真办,描述符与类型验过了,根文件系统的缓存也冲了,设备的 flush 等回来了。机内的编译开工之前,脚本拿一只小文件试过了 fsync,通了才敢往下走。

咱们再把号码座上的一处按正本改过来。假文件与真终端的那一卷里,给 nanosleep 和 tgkill 补号的那一章,给 tgkill 记的座是二百,可 Linux 的表上,二百是 tkill 的座,tgkill 自己住的却是二百三十四。两位各归了各座,送字的时候还要核对,目标是不是咱们要送的那一组。mremap 与 epoll_create1 照旧是明说不办的,用户库自己有回退的路,咱们不冒称实现了它们。

三摞都修齐了,咱们把全量重新跑起来,这一轮是还没通炉子的基线:前 138 个编译单元磨过,墙钟记下的是 834.685 秒,到第 139 个编译单元的时候,目录满了,就停在了那儿。盘上空闲的块还有的是,目录自己不长新的,洞当场看清了,补法跟块缓存同一批落地,目录没有空槽的时候,新分的数据块就记在父 inode 的名下,双间路上新领的内层表,块数也补齐了。长凳上咱们再读一遍,十五 KiB 的目录带着子目录,卸载了重挂,读回的尺寸一字不差,该在的块一个都没有少。死结解了,慢还蹲在原地,咱们该给炉子通通风了。
