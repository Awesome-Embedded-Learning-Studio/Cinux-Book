# 重启的证明

机内的活干完了。串口报完了最后两行,QEMU 也关了机,256 MiB 的源码卷安静地躺在宿主的盘上。卷里的 /src/out 下面,装着这一轮做出来的货:一只启动镜像,一份链接完的内核 ELF。内核本体是 590656 字节的,上一章念过数的那轮完整构建,交的就是这个尺寸。机器自己喊的完工不算数,这一卷的章法从来如此,自报的不算,亲手核过的才算。咱们把货掏出来当面验。

机内还留了字据。咱们把构建驱动脚本末尾那几行请出来,它给自己刚写完的镜像留了一份指纹:

```python
        target.flush()
        os.fsync(target.fileno())
    digest = hashlib.sha256(image.read_bytes()).hexdigest()
    print(f"[kernel-selfhost] IMAGE_SHA256 {digest}", flush=True)
```

您留意算指纹的时机,数据真写进了盘、fsync 做完了,哈希才开算的,取样的对象就是刚写进去的镜像本尊。给 busybox 立进料册的时候咱们就领教过它的脾气,内容变了一个字节,整串十六进制就换了一副面孔。机内把这串数打进了串口,等于在单子上签了名,我造的货,长的就是这个样。

掏货换到了宿主这边,咱们用的还是生态那一卷烤盘的老家什 debugfs。那会儿它是往 ext2 镜像里一件一件地写货,这回反了过来,掏货是往外走的、盘也不挂的。掏出来的镜像整个重新过一遍哈希,验货的就两行:

```python
    if hashlib.sha256(product.read_bytes()).hexdigest() != digest:
        raise RuntimeError("extracted boot image differs from guest hash")
```

宿主算出的得数,与机内记下的那串逐字核对,打头的是 377dc9f1,64 个十六进制字符一位一位全对上了才算过,差一位的话,脚本当场就报错走人了。有朋友可能要嘀咕了,掏个文件出来的工夫,犯得着再算一遍哈希吗。咱们不赌这个。出了机器门的字节,还要过 debugfs 的手、过宿主文件系统的手,一路上谁都不许悄悄给它动一个字节的,这一遍哈希验的就是路上清白不清白。

哈希只证了货没被人换。还有一层疑心咱们得单独排:凭什么信内核真是机内从头编的,而不是宿主提前塞了半成品进去?立目标那一章划输入清单的时候,边界早就摆在了明处,宿主给的只有配置、命令、工具链、Python、引导器,咱们这一轮没有重新编译 GCC 与引导器。剩下的清白,就得源码卷自己来作证了。卷里的源码与当前的源码树逐文件对哈希,一份一份全对上了。带进卷里的内核对象,咱们数了数,数出来的是 0。咱们的装料脚本 `scripts/prepare-kernel-selfhost.py`,在宿主上把命令清单装进了卷,出工的时候自己报过行:

```python
    print(f"[kernel-selfhost] exported {len(commands)} source compilations + kallsyms; no kernel objects")
```

带进卷的只有源码与编译命令,现成的 .o 一个没有。镜像里那两段引导器倒是宿主构建的正身,随卷带了进来,清单上是写得明白的,咱们不冒领。从头到尾的整只内核,咱们从一次次编译、kallsyms、两轮链接一路做到镜像封装,全是机内做出来的。

货验明白了,该上最后一击了。掏出来的镜像换个身份,不当数据盘、当上了启动盘,再开一台全新的 QEMU、从它引导。源码卷照旧当数据盘挂在了旁边,咱们的 /hello.c 就住在里面。开了机,串口上新内核一行一行地报出来、`Cinux up`,提示符也拉了起来。刚才那一轮里它还只是卷里的一堆源码,现在它坐在内核的位子上,给咱们当机器。

接下来敲的,还是咱们自举的老戏码。驱动脚本喂进串口的是两条命令:

```python
        output = guest.command("gcc /hello.c -o /reborn; echo REBORN_CC_$?", "REBORN_CC")
        output += guest.command("/reborn; echo REBORN_RUN_$?", "REBORN_RUN")
        if not re.search(rb"\r?\nHello from GCC!\r?\n", output):
            raise RuntimeError("new kernel failed the compiler/runtime check")
```

咱们在自家造出来的内核里,用盘上的 GCC,把 /hello.c 编成了 /reborn、再跑。判据就写在了脚本里,输出里必须有 `Hello from GCC!` 这样的一行,两条命令的退出码都得是 0。同一轮的整份串口记录还要再筛一遍,任何一条装聋的 syscall、任何一次内核异常,都让这一轮作了废。念名单那一章立的零装聋口径,验师傅的时候管用,验刚出炉的新内核,一样是管用的。

`REBORN_RUN_0` 报了出来,咱们等的那一行紧跟着就到了:`Hello from GCC!`。造出来的自己开得了机,也干得了活了。

这一发实弹的分量,值得您停一拍细看。/reborn 是盘上 GCC 的默认产物,PIE 的身子,ET_DYN 的形态。您看它能在新内核里跑起来,靠的是座位认得 ET_DYN 那一章安的座位,那个座位如今安在一只由 GCC 自己编出来的内核里。加冕那一章咱们拿 od 逐字节核过三个 PIE,验的是 STL 与异常的成色。交活的还是同一具编译器,这一回交的是整只内核。

收官的大戏有三层,到这里合了龙。头一层是串口壳里的 ./hello,咱们看着它由盘上工具链编出来、跑起来。第二层是 g++ 把带 STL 与异常的 C++ 编出来、跑通。压轴的第三层就是方才这一场:咱们机内从空对象目录做出整只内核,重启了、开机了、再编一只 hello。编译自己的四个字,写到串口的这一行输出上,才算落地。

咱们该把全卷的成绩单合在一起念了。收卷的活,就留给下一章了。
