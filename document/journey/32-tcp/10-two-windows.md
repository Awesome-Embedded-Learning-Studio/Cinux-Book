# 两扇窗

重传把丢接住了,可还有一场灾没接:淹。咱们把两种走法都摆开看看。一种是最保守的停等:发一段,等一声认,认了再发下一段。不会淹,可一条腿走路,往返多长,每一段就多耽搁多长,回环上一毫秒的路,真线上是一百倍的量级。另一种是敞开了发:发方痛快,收方遭殃,收件箱就那么大,涌进来十倍的字节,装不下的全白丢,还得发方一笔一笔重传。窗口就是这两头之间的折中:发,但欠着的在途字节不许超过一个数。这个数不由发方定,由收方通告。

咱们看收方的那扇窗,算法一行就说完:

```cpp
uint16_t TcpModule::receive_window_of(const Connection& connection) const {
    const unsigned int kHeld = connection.inbox.count();
    return static_cast<uint16_t>(kTcpReceiveWindowBytes - kHeld);
}
```

咱们念这一行:四千零九十六,减收件箱里躺着的,剩多少,窗就开多大。这个数不另走一条路通告,每一个出站的段,头里的窗口字段答的就是它:数据段带,纯应答带,握手的手也带。收方读走几个字节,下一声应答的窗就宽几个字节的口,通告就这么搭车走了。

咱们再看发方的那扇窗,两把尺子取小:自家固定的一扇四千零九十六,与对端最近一次通告的数。对端还没通告过,默认的数顶着用,握手的手里带着,一趟就换上真数。发送的闸门照原文念:

```cpp
    const uint32_t kInFlight = connection->snd_nxt - connection->snd_una;
    const uint32_t kCeiling =
        std::min(static_cast<uint32_t>(kTcpSendWindowBytes), connection->snd_window);
    if (kInFlight >= kCeiling) {
        return static_cast<size_t>(0);
    }
```

在途的字节够着上限了,一个都不再收,send 答零,门上翻译成 would-block,客人自己决定等还是再来。上限之内,大块写按一个最大段的体量切着发,发多少、环里存多少、笔尖推多少,三笔同步走。这里咱们要跟客人讲清一件事:流式的发送短写是常态,不是异常,窗就那么宽,一口气递来一万字节,窗内的收下,剩下的下回再来,字数的答话如实报,不装一口吞下。

零窗之后是重开,这一步的写法有个讲究。对端把窗缩到零,发送侧停。收方读走字节,窗其实已经开了,可发送侧怎么知道?人家的章法里有周期探活一门,定时戳一戳。咱们不做,理由挂在明处:这一卷的两端都是自家栈,收方排空了箱子会主动说话。主动到什么地步,咱们看收件的那一段:

```cpp
    const bool    kWasShut = receive_window_of(*connection) == 0;
    ...
    if (kWasShut && taken != 0 && receive_window_of(*connection) != 0) {
        transmit_segment(*connection, kTcpFlagAck, nullptr, 0, connection->snd_nxt);
    }
```

取字之前记一笔,箱满过吗。取完再看一眼,开了吗。满过、取了、开了,三个条件齐,顺手补一个纯应答,把新窗通告出去,不用对端来问。这是收方的自觉,咱们拿自觉换探活,划算的前提是对端讲理。对端要是不讲理,窗死锁,发不出去也收不着。这个场景咱们不护短,登记在案,负测全家来的时候也没法替一个不讲理的自家栈演这出戏,真到了对外的那天,探活得补。

收件的路数在这一章顺手讲齐。段进来,起点的号比期待号老,尾巴却伸进了新地界,这是骑线的重传段:头部跳过,老的那截不重复入箱,新尾巴照收。收多少还要看箱子的余量,满了截着收,截掉的等对端重传。每收一笔,期待号推一笔,到货的铃响一声。长凳一案专考两扇窗的配合:对端通告的窗缩到小,发送的闸门跟着缩,读空之后窗重开,字节接着流。这一案笔者还踩过一个小教训:自环上灌满一整窗,一口四千零九十六字节,期望到货的铃响一声,长凳上响的是三声,一个最大段的体量切三段,每段各鸣各的,断言改按三声数,数对上了。
