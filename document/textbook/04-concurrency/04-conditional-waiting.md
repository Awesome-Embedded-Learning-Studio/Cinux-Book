# 04 · 条件等待:三步,一扇窗口,三句口径

4.3 收卷的话还贴在门口:睡觉那一路,4.1 立谱系时押给《条件等待》的票还押着,票面写的是睡觉的正戏。叫醒丢了是一桩,两颗核一起睡沉是又一桩,咱们把病名记在票背上,点到为止,案卷下一章开门。今天咱们开门摊卷。叫醒丢了,名下两份卷宗:一份在词上的等待那边,首版唤醒只醒一个人,能叫的那声喊完了,另一个还在睡,QEMU 里安安静静地挂死。另一份在完成件这边,通知发了,却被中断例程的尾巴当垃圾扫走。两颗核一起睡沉,是后一份的现场:全员睡熟,就绪队列里没有活可派。病名是 4.3 点的,案卷咱们一份份翻。

本章的活,咱们数下来还是三样。头一样,认睡觉的身子:三步怎么走,两把锁怎么睡,窗口怎么敞,前科怎么挨的刀。再一样,立口径:三句话把窗口在结构上关死,顺带把 4.2 押下的那笔裁断答了,两步分家,谁粗谁细。末一样,看叫醒的一侧:唤醒即转移,单位直达,判决同拍,叫醒幂等,末了还有唤醒侧自己的一场次序案。

量法还是三条。码,实况锚仍是 r26_smp:sync.cpp,263 行,4.2 与 4.3 都量过,本章取睡觉那几段,scheduler.cpp 的睡觉动词,futex.cpp 的词上等待。老身不另开克隆,老代码印自正文卷:互斥锁的老身抄自《轮流当家》那一卷,词上等待的老身抄自《同一副身家,各一条栈》那一卷,引时注卷。屏,4.2 印过的 test_sync 九案屏不重印,本章回着看。机内几桩案子没有屏,咱们不造。书,xv6 第 9 章头一回进教科书层,页码从 81 起单独记,本章引六页。第 7 章的旧页上添一句 72。原话一律整句摘,页号写明,您对着书核。

> **老三拍的每一步,单看都清白:挂队没错,放锁没错,切栈也没错。您想:窗口的病,到底生在哪?**
>
> 病不在哪一步里,在步与步之间的缝上。挂上了队,锁放了,人还没躺下,这道缝敞着:叫醒的人恰好从缝里跑一遍,随后睡的人自己把状态按回阻塞,而唯一会叫他的人已经走了。所以药方不是改哪一步,是立一条口径,管住一件更根本的事——把状态翻成阻塞的那一拍,锁在谁手里。

## 三步:睡觉是个准确的动词

4.1 的押票,头一张今天兑,谱系那一段的原话:等得久的活,等一件还没生产出来的货,转圈就是烧电,睡觉才是正路,那一路的正戏归《条件等待》,本章只立名。正戏开演。睡觉在咱们的机器上是个准确的说法,不是修辞。正文《轮流当家》那一卷《让出去,还能被叫醒》一篇的段首就有这句,咱们把后半句补齐:把自己从就绪的队列里摘下来,挂到某个等待的队列上去,状态标成了 kBlocked,然后发起一次切换,调度器从此跳过您,直到有人把您叫醒,重新塞回就绪的队列里。

摘下、挂队、叫醒三步,归《条件等待》,咱们到此收手。4.1 说这话的时候,正文那边的三步早就落成了:摘下、挂上、叫醒的这三步,落在调度器的新动词上,block_current 和 unblock。咱们看睡这门动词的真身,scheduler.cpp 的 :374 到 :383:

```cpp
void Scheduler::block_current() {
    const arch::IrqGuard kGuard;
    base::safety::Check(DefaultSpinLedger().depth() == 0, "task parked while holding a spinlock");
    park_current();
}

void Scheduler::park_current() {
    prepare_to_wait();
    schedule_blocked();
}
```

block_current 这一关,4.1 领您进过,原话是进门头一件事就是查登记簿:深度不是零,说明还有人揣着门闩,Check 当场叫。响亮地叫,总比挂了强一万倍。门后调用的 park_current,身子是连写的两步,前一半 prepare_to_wait,后一半 schedule_blocked。切栈这个词今天头一回正用,配句白话:把当前任务连同它的栈换下来,让下一个任务上。正文说的发起一次切换,行话就叫切栈。这两步连写还是分家,4.2 押了裁断,咱们到三句口径那里再判,这里只记一笔:门里的家法,一步没改。

等待队列这件家具值得半段。咱们没往堆里 new 节点,节点长在任务自己身上:Task 继承了 base 家的 SelfNode,自个儿身上带一根链,等待队列拿这根链把人串成一条,行话叫侵入式链表。好处正文数得实,咱们抄两条:头一条,睡觉的路径上一分钱分配都不花。要不然,睡前还提心吊胆地去 new 一个排队节点,堆要是正好满了,这觉就睡不成了。另一条,错门天生防得住,每个任务名下的节点只有一根,同时排在两条队里的事在物理上就办不到。

## 两把锁:老身的样子

4.1 还有半张票:Mutex 是睡觉那路的家什,柜子的槽表就是它押的。3.6 柜前露过半张脸的家什,今天看全身。睡觉的两把锁都出生在正文《轮流当家》那一卷:互斥锁 Mutex 护一段长活,信号量 Semaphore 护一堆货。咱们把互斥锁拿锁的老身整段抄来,卷内原样:

```cpp
void Mutex::lock() {
    Task* const kSelf = Scheduler::self().current();
    {
        const SpinGuard kGuard(spin_);
        if (owner_ == nullptr) {
            owner_ = kSelf;
            return;
        }
        waiters_.push_back(*kSelf);
    }
    Scheduler::self().block_current();
}
```

双层结构您一眼看得出来:里层一把自旋锁,只护两样家当,现在的主人是谁、等待队列长什么样。外层才是真正的竞争。锁空着,当场改了名易了主,三两步完事。锁有了主,干的事只有一件:在自旋锁的护短下把自己挂上等待队列,放掉自旋锁,睡觉。次序正文点过精细:挂队完成之后才放手里的自旋锁,睡觉发生在自旋锁的外面。持自旋锁入睡的红线,这里是一步也不越的。挂上队,放了锁,锁外才调 block_current:入队,放锁,切栈,老三拍就这么个拍法。

放锁那一侧是这把锁最有戏的地方。有人排队,锁不放空,直接把队头改成本锁的新主人,叫醒他。这一手正文起了名:唤醒即转移。被叫醒的人睁开眼,锁已经划到了自己名下,重新排队、重新抢的功夫全省了。为什么这么设计,正文备了反例:要是 unlock 放空锁再叫醒,队头醒来还得再走一遍拿锁的路,从恢复执行到真正拿到锁的那一段里,新来的谁都可以插进来抢走,睡了一觉醒来发现还得再睡,运气差的话睡到天荒地老,饿死,行话这么叫。信号量的 post 同一个心思,也起了名:单位直达。有等人的人,货不进仓,计数不加,直接越过柜台交到队头的手里。没人等,才把计数加一存进仓。零构造的家规在这一件上不是将就,而是语义本身,这也是正文原话,咱们不展开。

## 敞着的窗口:单核踩不着,双核天天敞

老三拍在单核上太平了好些站,病藏在三拍的次序里。正文《请第二颗脑子上线》那一卷《睡前与叫醒的口径》一篇讲得最清,案情咱们照卷摘:三拍之间有一条敞着的窗口,叫醒的人恰好趁窗口开着跑了一遍,把状态改成了就绪,塞进了就绪队列,自顾自走了。然后等的人不紧不慢走到切栈那一步,切栈的代码不管三七二十一把状态按回阻塞,人躺下了,而唯一会叫他的人已经走了。这一觉没有下一幕了。

**停一停,老三拍在单核上跑了那么多站,叫醒的人一回也没钻进来过。您推一推:窗口在单核上是不存在,还是存在,只是没人钻得进?**

窗口一直在,不是关得严,是窄。那篇的原话:叫醒的人要与等的人共用一颗核,中间还隔着一次实打实的调度,几百万次的运行里没有一次交错。到了双核,叫醒跑到了另一颗核上,与等的人真并发,窗口天天敞得大大的。同一副身子,单核上没事,双核上天天出事,差别只在叫醒的人跟不跟您共用一颗核。

病真发过,前科记在正文《开门迎客》那一卷《画像三版,窗口三处》一篇,挨了两刀。两刀的贼都是本核的中断,不是另一颗核,而且记前科那阵,第二颗核还没上线。窗口的形状,却是老三拍里就全须全尾的。第一刀在入睡侧,原话摘:把自己挂进等待名单,与真正的泊车之间,隔着的是几步活。泊车是老卷的叫法,说的就是把自己停进睡眠、交出处理器那一拍,今天的话叫切栈。一家两代名字,咱们引老卷时用老名,自己的话用新名。那几步活被一个崩溃循环逼出了原形,修法原话:把置阻塞的那一步挪进自旋锁的临界区。第二刀更深:光挪进锁里,放了锁、还没泊车的几步里,本核的中断还插得进脚,修法原话两片,各片逐字,拼在一起念:从关中断的那一步守到泊车提交为止,窗口整个关上了。互斥锁、信号量、完成件三处统一穿上的那件守卫,就是您马上要在新身子里见的 kParkGuard。

## 三句口径:新身子与那笔裁断

药方正文立成了三句话,咱们整段照念。第一句管的是把入队与置阻塞收进同一把锁:等的人在持着等待锁的临界区里,查条件、挂队列、把状态标成阻塞的三件事,一口气办完了才放锁。第二句管的是真正切栈放在放锁之后:持着别人的锁睡觉是不许的,轮流当家那一卷立下的就是它,卡口到今天还守在原来的地方。第三句管的是叫醒幂等:叫醒的人也进同一把锁,看见的要么是还没入睡的,条件已经变了,要么是已经标了阻塞的,叫醒了他,把状态置成了就绪,塞进了就绪队列。叫了两声也只醒一次,因为第二声看到的已经是就绪,幂等保证了多余的叫不产生多余的队列项。口径这个词前几章当口语用过,这里把它立成术语,配句白话:提前说定、全内核照办的做法。三句合起来,窗口在结构上就没了。

咱们看新身子,r26 的 Mutex::lock 全身,sync.cpp 的 :142 到 :157:

```cpp
void Mutex::lock() {
    // Release the spinlock before switching, but keep IRQs masked until
    // park_current() has committed the task's blocked state.
    const cinux::arch::IrqGuard kParkGuard;
    Task* const                 kSelf = Scheduler::self().current();
    {
        const SpinGuard kGuard(spin_);
        if (owner_ == nullptr) {
            owner_ = kSelf;
            return;
        }
        waiters_.push_back(*kSelf);
        Scheduler::self().prepare_to_wait();
    }
    Scheduler::self().schedule_blocked();
}
```

与老身对读,动的只有一处:老身在锁外调 block_current,新身子在锁内多了一句 prepare_to_wait,把状态标成阻塞的那一拍,从锁外挪进了锁里,口径第一句的载体正是这一句。挂队、置阻塞一口气在自旋锁的临界区里办完,放了锁,才调真正切栈的 schedule_blocked。头一行的 kParkGuard 您认得,前科第二刀的那件守卫:中断从进门掩到泊车提交。这一来,叫醒的人进的是同一把自旋锁,要么赶在挂队之前,那时条件已经变了。要么落在置阻塞之后,那就是正经的叫醒。缝还在,病没了。

4.2 押的裁断,咱们现在答。头一件,把押下的裁断票念一遍票面:注释念的名字 park_current,说的是连着的两步。门这边早改成分家的走法,注释旧,身子新,谁粗谁细,归《条件等待》。咱们的判词:分家是对的,细的赢。锁里那半是细活,查条件、挂队、置阻塞,几条指令,闸一落全办完。锁外那半是粗活,真正切栈,重。可它自带干粮:schedule_blocked 进门自备护甲,护甲记在 scheduler.cpp:386,进门还查一遍登记簿(:390),不劳调用人替它张罗。整存的老写法没死,还立在调度器上:block_current 门后连着的 park_current 就是它,宿主长凳的案子今天还在走 block_current。内核的锁家,连同词上的等待与等孩子退场,全走分家的新道。那句注释呢,意思没记错,中断确实一直掩到泊车提交,可名字落后了,念的是化石。判词补半句:身子照分家的走,注释欠一次改名。

这套口径不是互斥锁一家的。全查的名单正文如实报过:互斥锁、信号量、完成件、词上的等待,四家用的是同一个形状,挨个改齐了。第五家管的是等孩子退场,形状略不同:扫描名册、挑僵尸、入等待册、置阻塞,这几步都在共享的调度锁里办完,真正的切栈在锁外,同口径对得齐齐整整。完成件这一路还有前科,正文有记,当年修的是入睡那一侧,这一回轮到的是唤醒那一侧。那桩案子,咱们到被吞的通知一案里翻卷。

## 叫醒的一侧:转移,直达,同拍,幂等

睡觉的口径立完,咱们过河到叫醒那一侧。头一档,互斥锁的 unlock,r26 真身,:159 到 :171:

```cpp
void Mutex::unlock() {
    const SpinGuard kGuard(spin_);
    cinux::base::safety::Check(owner_ == Scheduler::self().current(),
                               "mutex released by a non-owner");
    Task* const kNext = waiters_.pop_head();
    if (kNext != nullptr) {
        owner_ = kNext;
        Scheduler::self().unblock(*kNext);
        return;
    }
    owner_ = nullptr;
}
```

验手那声 Check,4.2 念门闩放锁时您听过这门功课:放这把锁的必须是持有者本人。这里是 Mutex 版的同一门功课,不是主人不许放锁。看正戏:有人排队,owner_ 直接改成队头,unblock 叫醒,return,锁不放空。唤醒即转移的身子,老身以来没变过,变的是它如今跑在三句口径的世界里。第二档,信号量的 post,单位直达,真身,sync.cpp 的 :206 到 :214:

```cpp
void Semaphore::post() {
    const SpinGuard kGuard(spin_);
    Task* const     kNext = waiters_.pop_head();
    if (kNext != nullptr) {
        Scheduler::self().unblock(*kNext);
        return;
    }
    count_++;
}
```

有人排队,货不进仓:摘队头,递货,叫醒,return,计数一格没动。没人等,才 count_ 加一进仓。咱们跟 unlock 的转移对一对,一个心思:那边把锁划到队头名下,这边把货直接递到队头手里。第三档,完成件的 finish,判决同拍唤醒,到被吞的通知一案里细看。第四档,词上的唤醒,到词上等待那里看。四档叫醒,末了都落在同一个动词上:

```cpp
void Scheduler::unblock(Task& task) {
    const QueueGuard kGuard(*this);
    if (task.state != TaskState::kBlocked) {
        return;
    }
    task.state = TaskState::kReady;
    base::safety::Check(task.sched_class->enqueue(task), "ready queue full at unblock");
    local().notify_pending = true;
}
```

幂等的机关就在开头两行:task 的状态不是 kBlocked,直接返回。头一声叫醒把状态置成就绪、塞进就绪队列。第二声再来,看见的已经是就绪,什么都不做。多余的叫不产生多余的队列项,口径第三句的代码面就在这几行。您再留意一层:unblock 自己进的是调度队列的锁,而真正让睡的人和叫的人错不开的,是外头各家的那把门锁。睡的人和叫的人,进的总是同一把。

窗口里还藏着一桩妙事,正文原话咱们照卷引:如果叫醒恰好发生在放锁之后、切栈之前,那个被叫醒的人此刻状态已是就绪,人已进了就绪队列,而他自己还站在自己的栈上。切栈的函数会去挑下一个任务,挑选的条件里本核握着的任务可取,他偏偏挑得中自己。挑中了自己,函数发现下一个恰好是当前的自己,直接返回了事,一次切换的功夫都不用,他就这么接着跑了。真身就三行,scheduler.cpp 的 :402 到 :404,挑出来的 next 与手里的 kPrev 是同一个。窗口里的叫醒不但不丢,还省了一趟切换,这是《睡前与叫醒的口径》那篇的收话,咱们原样收来。

## 醒来必须重查:判决要自己读

叫醒了,不等于知道结果。咱们看 Completion::wait 的全身,sync.cpp 的 :229 到 :245:

```cpp
bool Completion::wait() {
    const cinux::arch::IrqGuard kParkGuard;
    Task* const                 kSelf = Scheduler::self().current();
    {
        const SpinGuard kGuard(spin_);
        if (state_ != State::kPending) {
            return state_ == State::kSuccess;
        }
        waiters_.push_back(*kSelf);
        Scheduler::self().prepare_to_wait();
    }
    Scheduler::self().schedule_blocked();
    {
        const SpinGuard kGuard(spin_);
        return state_ == State::kSuccess;
    }
}
```

门内的身子您已经认得,与 Mutex::lock 同一个形状,四家里的第三家。新鲜在醒来那三行:schedule_blocked 返回,人重新进锁,把判决再读一遍才答话。为什么必须重读?头一个缘故,叫醒声里不带内容:unblock 只说一声有了结果,结果是成是败,写在判决书上,您得自己进锁去读。醒来直接报成功的人,判词若是 Failed,他就把败案念成了胜诉。再一个缘故是门外的通例,咱们按 xv6 书页 84 转述,不是原句:它家的唤醒语义允许不相干的醒,名目叫 spurious wakeup,假醒,所以 sleep 的调用总裹着重查条件的循环。咱们的唤醒有同锁同拍与幂等把关,假醒进不来门,可重查这个习惯照旧立着:醒来的人,永远自己进锁读一遍判决。

## 一次性判决书:一辈子只宣判一回

Completion 这件家什,4.2 的屏上点过三案,案名点到为止,正戏归《条件等待》,票现在咱们来兑。它的脾气,正文《两种等待》那篇一句话说尽:一次性的判决书,一辈子只宣判一回。出生时是 Pending,finish 一到,落成 Success 或者 Failed,从此改口不改判。finish 第二回来,原话奉还,判决不动。宣判那一下还替睡觉的人办事,finish 真身,:216 到 :227:

```cpp
bool Completion::finish(bool success) {
    const SpinGuard kGuard(spin_);
    if (state_ != State::kPending) {
        return false;
    }
    state_            = success ? State::kSuccess : State::kFailed;
    Task* const kNext = waiters_.pop_head();
    if (kNext != nullptr) {
        Scheduler::self().unblock(*kNext);
    }
    return true;
}
```

咱们看:状态翻成终态的同一拍,摘队头,叫醒,判决同拍唤醒,叫醒那一侧的第三档。门内头一句,状态不是 kPending 就答 false 退回,这就是改口不改判的代码面。翻页另有一个动词,rearm,:257 到 :261:

```cpp
void Completion::rearm() {
    const SpinGuard kGuard(spin_);
    cinux::base::safety::Check(waiters_.empty(), "rearm with a waiter still parked");
    state_ = State::kPending;
}
```

翻页有条件,开头那行 Check:还有睡客没醒,翻页当场炸。道理正文讲了,咱们把原话摘来:人家睡得正香,等的正是自己的判决,您把判决抽走重写,人家醒来读到的就是别人的案子。所以翻页之前,总得看清睡客都走了没有。

这套手艺伺候的是任务。开机那会儿调度器还没开工,手里只有主流程一条执行流,wait 想睡也没处睡,另一条路,正文在那篇里也给咱们备了:进一个死循环,关中断查一回判决,没到,睡到下一回中断,醒来从头再查。睡觉那一下的真身,一共两条指令:

```cpp
void EnableIrqAndHalt() {
    __asm__ volatile("sti; hlt" : : : "memory");
}
```

开中断,然后睡。为什么必须挨着写,分成两笔就不行?正文讲了个硬件的善意:STI 指令一执行完,处理器不马上收中断,还憋着一拍,这一拍叫 STI shadow。`sti; hlt` 挨着写,开中断之后的头一件事就是睡觉,于是“醒”与“睡”之间不存在缝:中断来了,处理器从 hlt 的下一拍接着跑,睡就是原子的一步。原子这个词,咱们书里至今攒了三口锅,各是各的意思,不许一口替三家背:4.1 那口,test_and_set 把检查与写捆在同一拍指令里。这一口,硬件把开中断与睡觉之间那道缝封死。词上的等待还有一口,查词与进哈希桶收进同一把锁,靠的是锁,不是指令。至于指令与内存的次序,那口深锅归《内存序与缓存一致性》,咱们一句交棒,不展开。

两条禁令正文写在明处,咱们照录。头一条,持着自旋锁的时候别调它:锁在手里,人睡了,别人来拿锁,转圈,能放人的人也得拿这把锁,也转圈,一条锁拴住一串人。第二条,别自作聪明把它展开成恢复中断、再睡两笔,那道缝就是这么来的。这两笔,咱们头一遍搓内核的时候都真踩过,脚印还在注释里。还有半句:醒来必须重查条件。能把 hlt 拍醒的,不止您要等的中断,时钟每 10 毫秒响一回,谁的线开了它都拍得醒,所以循环长那个样子:查,没到,睡,再查。醒来就当判决到手的人,拿到的常常是时钟的问候。这句问候,就是假醒在咱们机器上的真身。

睡觉这门手艺后来还伺候了块设备的值班队列,家法两句,正文《一张块脸,一间值班室》那篇的:占了的格,地址不搬家。绝不过设备命令,绝不过睡眠。前一句让睡在格子里的判决永远等得着地方,后一句给值班室划了界,锁不越设备命令,不越睡眠。咱们一句带过,全本在那卷里。

## 被吞掉的完成通知:唤醒那一侧的次序

完成件的前科,咱们现在翻卷。案发在双核实弹:头一回确实绿了,回头复跑,间歇性地停住,崩溃是没有的,画面安静得像下班了。正文原话:首绿跟复跑打了架,这本身就是案情:窗口型的病踩不踩得着,看的全是时序,跑得越多越藏不住了。现场按规程采回来:两颗核都停在睡觉的原语上,就绪的队列里没有活可派,唯一的叶任务,一个普通的进程,阻塞在完成件的等待上,调用链从完成件的等待,经盘驱动的读块、块设备的值班队列,一路念到文件系统的路径解析。全员睡熟,两颗核一起睡沉,4.3 点的第二桩病名,现场就在这儿。

病机在唤醒那一侧的次序里,咱们从头看。盘驱动的中断服务,从前的次序两步:头一步唤醒等待者,然后再清设备的状态。等待者醒在另一颗核上,手脚飞快:把完成件复位回未决,布了下一条命令,发了出去,新命令的完成位亮起。而这颗核的服务例程才走到第二步,把状态位照单全清,清掉的那串名字里,就有新命令刚刚亮起的完成位。新命令确实完成了,完成的通知却被旧例程的尾巴当垃圾扫走了。

修好的次序,正文记成四拍:取判定,清设备状态,回读确认,最后才是唤醒。头一拍取的是判定,成败在这一拍已经算清。清完了回读一次,确认真清了,回读是给设备的承诺落了地。唤醒放在最后,等待者醒来去布置新命令的时候,旧例程的手已经从设备上收回来了,新完成位亮起来之后,再没有人会碰它。您要是想问,加个轮询的兜底岂不省事,等了一会儿没等到就再查一遍。正文答了,咱们照录:兜底会把病盖住,复跑是不再停了,病根还是原来的病根,它在等下一次的时序。所以不加轮询,不删完成件的检查,只把次序摆回了正位,病根才是真的没了。

同一场风暴里还连着修了一批双核才现形的缺陷,咱们挑与睡觉接边的一桩:管道文件尾的接力。两个读者都睡了,最后的写者只发一声,头一个醒的拿走了文件尾,第二个还睡它的觉。修法正文原话:醒来的一个发现自己拿到的是等来的文件尾,就把手里的接力棒递给下一位,两位都读到零才算清了场。这一桩在双核实弹里单独成案,是个独立实核,案名 test_smp_pipe.cpp:54,all_parked_readers_receive_eof。两颗核都入了场,名册上确认两位读者都阻塞了才关写端,末了两位都读到零。

## 词上的等待:第四家,丢唤醒怎么关死

口径四家的末一家,睡得最远:不在内核的对象上,在用户世界的一个词上。咱们提一句白话,正文《一个词,二百五十六只桶》那篇开的头:这个词还是这个值,你就把 CPU 交出来睡,有人把词改了,他来叫你。这套握手行话叫 futex,咱们照 Linux 的门牌开门。门面名目(系统调用号、操作码、错误码)一句带过,clone 与线程身份归第 5 部,点名即止。

丢唤醒的经典形状,那篇讲得最干净,咱们照卷引:等的人查了词,值对上了,打算睡了,可叫的人赶在他挂上队列以前跑了一遍唤醒,队列里没有他的名字,白叫了,他这才安心睡下了,从此没人再叫了,这一觉睡到天荒。防它的办法只有一种形状,原话:查词的那一拍和进桶的那一拍,必须是原子的,跟唤醒看见的那一拍,锁的是同一把。这就是原子的第三口锅,白话再配一遍:几件事收进同一把闸的临界区里一口气办完,谁也插不进脚,靠的是锁,不是指令。老身的等待侧,卷内原样,咱们整段抄来:

```cpp
base::KernelError WaitOnUserWord(unsigned long long uaddr, unsigned int expected) {
    Task* const kSelf = Scheduler::self().current();
    FutexTable& table = shared_table();
    {
        const cinux::arch::IrqGuard kQuiet;
        const SpinGuard             kGuard(table.gate);
        auto const* const           kWord = reinterpret_cast<volatile const unsigned int*>(uaddr);
        if (*kWord != expected) {
            return base::KernelError::kWouldBlock;
        }
        kSelf->futex_uaddr = uaddr;
        table.buckets[FutexTable::bucket_for(uaddr)].push_back(*kSelf);
    }
    Scheduler::self().block_current();
    return base::KernelError::kOk;
}
```

您对着三句口径读它:读词、记地址、进桶三件事住在括号里,可置阻塞那一拍,block_current,在括号外头。挂上了桶,闸放了,还没标阻塞,窗口敞在这两拍之间,跟互斥锁的老身同一个病。r26 的真身把这一拍挪了进去:futex.cpp 的 :74 到 :76,记地址、进桶、prepare_to_wait 连住在同一把表闸里,:78 的 schedule_blocked 才在闸外切栈。等待与唤醒掀的是同一把闸。桶只管把搜索收窄,二百五十六只桶,真正认人的是等待者自己揣着的那个精确地址,同桶不同词的,一个误醒的也没有。于是那篇的收话在这儿成立:等的和叫的谁也错不过谁,这个窗口在结构上就没了。

词上等待这一路还压着 4.3 病名的头一份卷宗。首版的唤醒人手里只有一面停泊旗,叫了一声,旗翻了一下,收了工。可词上等的可能是两个人,叫的人明明白白递了二,他只醒了一个,另一个还在桶里睡得好好的,而能叫醒他的那一声已经喊完了。实弹一跑,QEMU 当场挂死,一点声音也没给咱们。正文原话:丢唤醒的凶处就在它的安静里,它没有崩溃的响动,没有断言的字样,它只是让一部分人永远地睡下去,所以它逼着咱们把窗口的结构想透,想透了还不够,还得数着人头一笔笔地清点。修法是把唤醒改成清点:进桶沿链走,地址对上的摘链、唤醒、计数,数够了才收工,一面旗的懒办法退场。

## 对照:同一件事,别的机器怎么做

xv6 第 9 章,教科书层头一回进,咱们从书页 81 记起。这门学问它家的名目,原词摘:sequence coordination or conditional synchronization mechanisms,条件同步,《条件等待》这个章名的学名就是从这儿来的。原语也是一对:sleep 睡在一个条件上,wakeup 把等这个条件的全叫醒。

窗口病它家也治,书页 82 到 83,药方与咱们不同方。它家的 sleep 要调用人递一把锁进来,这把锁有专名,原话摘:“That lock is called the condition lock.” 进门之后,放这把条件锁与把自己挂进等待册,两件事在另一把锁的护下交接,图 9.1 的题名原话摘:“Overlapping locks to avoid lost wake-up”,两把锁搭着手,把丢唤醒的窗口搭没。咱们的方子您认得:挂队与置阻塞收进同一把锁,切栈放在放锁之后。同一种病,两副药:一副靠两把锁交接,一副靠一把锁收拢,治的都是同一件事,把状态翻成阻塞的那一拍,不许叫醒的人看不见。

书页 84 的假醒,咱们在重查那里按页转述过了。书页 87 有一段史,与咱们前科第一刀是同一个故事,原话整句摘:“The original Unix kernel's sleep simply disabled interrupts, which sufficed because Unix ran on a single-CPU system. Because xv6 runs on multiprocessors, it adds an explicit lock to sleep.” 白话接着说:最早的 Unix 睡觉就是关中断,单核上够用。xv6 要跑多处理器,就给 sleep 加了明确的锁。咱们单核窄到踩不着、双核天天敞的那扇窗口,它家一句话把两头都说完了。

书页 88 两件,咱们只点名:条件变量这门设计的唤醒分两只手,唤醒一个与唤醒全体,行话 signal 与 broadcast。用户世界还有一路信号能把睡着的人拍醒,回话带一个 EINTR。那是《信号》那章的桥,过桥再引。第 7 章的旧页添一句,书页 72,按页转述:睡眠锁的临界区里可以再拿自旋锁,自旋锁的临界区里不许拿睡眠锁,与咱们持自旋锁入睡的红线同一条心,短的住里层,长的住外层,睡觉只能睡在最外层。

Linux 那头,这回有一门实打实的亲:futex 这个名字、等待落在用户词上、桶加精确地址的形状,咱们就是跟它学的,正文里照它家的门牌开的门。它家的桶有几只、路径怎么走,咱们没翻过源码,比不了的就是比不了,认亲不比深浅,留给将来的书。

## 练一练

三道题留给您:一道推演,一道回望,一道读屏。

**题一,推演。** rearm 开头那行 Check 撤了,翻页翻得自由了,您推一遍:双核的时序里,受害的是谁?他醒来读到的又是什么?

**题二,回望。** 叫醒丢了名下两份卷宗,一份在词上的等待,一份在被吞的通知。您说说:两份的病灶各在哪一侧,为什么第二份的现场是两颗核一起睡沉?

**题三,读屏。** 回 4.2 的九案屏。第四案,有存货的信号量不停车。第六案,stocked completion 进门不停车。您答:两个不停车,验的东西差在哪儿?再答一问:三句口径的第一句,拿哪一件的身子当载体?

### 参考答案

题一:您推到的受害者,是还睡在等待册上的睡客。另一颗核上有人把判决抽走重写、布了新案,他醒来进锁一读,读到的是别人的案子,正文《两种等待》那篇的原话,一步不差。要是新判决迟迟不来,他就抱着别人的未决接着睡,又是一场安静的挂死。

题二:词上的卷宗,病灶在叫的人手里:唤醒清点没做全,叫了一声就收工,该醒的两个只醒了一个,错在叫的那侧的数目。被吞的卷宗,病灶也在叫的那侧,错的是次序:唤醒在前,清状态在后,旧清理吞了新完成位。两份都在叫醒一侧,一份错在少叫,一份错在次序。至于现场,咱们一样一样摆:唯一会派活的叶任务等在完成件上,通知被吞,它不醒。其余任务全在等孩子退场,没人退场。两颗核的就绪队列都空了,没有活可派。叫醒丢了的后果,长成的就是这个现场。

题三:两个不停车,差在条件。信号量的存货是计数大于零,货还在,取一个走,读的是数目。完成件的存货是判决已落,一辈子只宣判一回,进门读的是已定的终态。载体那一问,咱们答:互斥锁的新身子,挂队与置阻塞收进同一把自旋锁,sync.cpp:154 那句 prepare_to_wait 就是第一句的载体,信号量、完成件、词上的等待同款。
