# 01 · 一条指令的一生:PC 指哪,机器念哪

写程序的时候,咱们一行一行往下读,心里踏实:上一行做完,才轮到下一行。这样的踏实,咱们多半记在编译器或操作系统头上,其实它来自机器底下一套极老实的循环。这一章咱们贴着它走一遍:一条指令从被取走到做完,机器身上发生了什么。

您在前置卷里已经见过它落在肉眼上的样子:单步十次,`eip` 一格一格往前挪,每一步的跨度正好是上一条指令的长度。观察是前置卷的活儿,这一层咱们换一副脑子,把看到的现象收进一套带得走的模型:机器承认什么,机器怎么花它。

## 凭什么敢把“一条做完才轮到下一条”当真

> **咱们凭什么敢把“一条指令做完,才轮到下一条”当成真的?**
>
> 前置卷给过您两屏看着打架的证据。单步调试那屏,`eip` 一步一步往前挪。QEMU 翻译日志那屏,一口气把几条指令并作一块翻,断口还都落在指令边界上。《深入理解计算机系统》书里还说,真处理器肚里更热闹,流水线上几条指令各占各的工位,同时往前挪。乱成这样,程序凭什么还活得像一条一条?这一章追的就是它。

## 机器承认的家当:架构状态

咱们有一本要常常引的书,《深入理解计算机系统》,行话里叫 CS:APP,咱们引的是第二版。它的书页 161 给内存下过一个定义,咱们在前置卷引过:机器码眼里的内存,就是“a large, byte-addressable array”,一大串能按字节寻址的字节。没有类型,没有变量,没有函数,字节挨着字节,别的什么都不是。

光有内存,机器转不起来,它还得有几样贴身的东西:寄存器。通用的 AX、算地址用的段寄存器、记状态的标志位,各司其职。最要紧的一格,咱们得单独点名:PC,程序计数器,指着下一条指令。

指令集把这些东西全数承认下来:程序每执行一步,哪些格子是什么值,白纸黑字,说到做到。被指令集承认的这套家当,学名架构状态(architectural state)。在 x86 实模式里,PC 长得别扭:它拆成 CS 和 IP 两半,真地址要按“段乘十六加偏移”折出来,这套算术咱们在正文里算熟了。正文指的是导航上“教程”那一层,整套书的主线叙事:作者一行一行手搓这套系统,为什么这么写,来龙去脉都记在那儿。咱们这一层讲模型,常从它那儿借来由。

缓存里存的副本、流水线上的工位、模拟器攒出来的翻译块,这批东西也真实在场,指令集却不认,咱们写的程序永远观察不到,摊得着的只剩快慢。它们住在哪一层,这一章往后自会交代。

## 取指循环:一拍三件事

机器怎么让指令一条一条活起来?CS:APP 2e 书页 9 的说法直白:从上电到下电,处理器反复执行 PC 指着的指令,再把 PC 更新到下一条。咱们管这个反复叫取指循环。伺候完一条指令,循环正好转一圈,咱们管这一圈叫一拍:节拍器响一下,机器交出一条做完的指令。一拍里干三件事:按 PC 去内存取字节(取指),把字节认成指令(译码),照着执行(执行)。您留意一件事:PC 自己也是架构状态,循环每圈读它,也每圈改它,它既是循环的输入,又是循环改写的对象。

咱们把前置卷捏过的五个字节再请出来当题干:`b8 00 7c cd 10`。那边咱们用 od 和 objdump 两双眼睛读它,这边眼睛收起来,只让循环自己跑。起步时确定的只有一样:PC 指着第 0 个字节,机器按 16 位实模式的口径译码。

**别急着往下翻,您猜一猜**:五个字节里,有没有哪一个,写着“到这儿,一条指令算完”?

第 1 拍伺候头一条:译码器从字节 0 读起,认出 b8 打头的是“往 AX 里装一个十六位立即数”,连吃 `b8 00 7c` 三个字节。执行,AX 里躺进 0x7c00,PC 前进三格。第 2 拍,PC 指 3:`cd 10`,译码出 int 0x10,执行,PC 又进两格,控制权顺着中断向量表交了出去。五个字节,两条指令,循环给咱们转了两圈。

答案有点冷:没有哪个字节写着边界。指令占几格,要等译码那一刻才知道。PC 前进几格,是每条指令用自己的编码说了算的。内存里只有字节,连“哪儿是指令的开头”都全凭 PC 一指:它指哪,机器念哪。边界拿不准会怎样,前置卷里 `/bin/true` 那一屏已经给过您脸色:换十六位那副眼睛,切出来的指令从此全线错位。

于是 PC 的走法拢共三种。省事的:执行完加上本条长度,接着取下一条——顺序执行。横一点的:被跳转类指令整个写掉——远跳、近跳、条件跳,待会儿实况里咱们见真的。第三种:被中断或异常拐走,顺着向量表进别人的代码,办完事回来。每拍必居其一,机器没有第四种。

## 实现可以乱来:ISA、微架构与 as-if 顺序

您读到这里怕是要拍桌子:还一条做完才轮下一条?QEMU 一次翻译并进好几条,前置卷里您亲眼看过。真处理器那头更热闹,书里的说法是流水线上几条指令各占各的工位、谁也不等谁,咱们手上的模拟器看不那么深。可咱们单步的时候,机器偏偏一步一个脚印。两屏都是真的,拿什么缝起来的?

拿两层缝。CS:APP 2e 书页 10 把它们分了家:描述每条指令什么效果、程序员拿它推理的那一层,叫指令集架构(Instruction Set Architecture,ISA)。处理器实际怎么实现的那一层,叫微架构(microarchitecture)。把模拟器也归到微架构名下,是咱们自己引申的,书页 10 只说了处理器。QEMU 怎么攒翻译块,和流水线深浅一样,是实现自己的事,程序一样看不见。

哪样东西归哪层,咱们也嘀咕过:缓存?翻译块?判法其实就一条,问程序看不看得见。咱们数过的每一格家当、取指循环的每一拍,全住 ISA 这层,它们是规格,是承诺。流水线多深、缓存几级、QEMU 把多少条并作一块,全住微架构那层,它们是自由,程序看不见,只摊得着快慢。

两层之间拿一句话接住。书页 160 说,大多数 ISA 描述程序行为的方式,是“as if each instruction is executed in sequence”,好像每条指令都挨着条顺序执行似的。咱们把“好像”两个字看住:架构没有答应实现真在排队,它答应的是程序观察得到的结果与顺序模型一分不差。随便停在哪个指令边界上,架构状态都和“一条条老老实实跑”算出来的值对得上。

所以咱们敢。敢单步:GDB 停在哪一点,机器就恰好是顺序模型里那一点该有的样子,拿笔算得出,拿寄存器对得上。敢照顺序写代码、写内核:推理全按顺序模型来,不必过问流水线答不答应。反过来说,哪天程序真看见了流水线,那是实现自己越了界。

> **笔者摔过的一跤:call 跳进了没加载的内存**
>
> 引导扇区拢共 512 字节,BIOS 也只肯加载头一个扇区。有一回,一个公共模块被整个链进了引导镜像,512 字节装不下,镜像胀了出去。机器照样起跑——BIOS 只认 510 偏移处那两字节 55 AA 签名,签名后头装的是什么,它才不操心,对上了就交棒嘛。代码顺顺当当跑到一处 call,目标地址排在 512 字节开外,那一片内存压根没被加载过。取指循环不知道,也不问:PC 指过去,它就念,念的是上一任住户留下的随机字节。机器一条条执行垃圾,结局要么死机,要么三重故障带着复位重启,再错一遍。事后拿 objdump 量出镜像真身,才对上案发现场,解法也直白:引导镜像只链它自己要的,再把大小检查挂进构建。取指循环对字节不问出身:是咱们链进去的代码,还是没加载过的空地,它一律照念。待会儿实况里那声 `call MbrMain` 响起来,咱们正好看着它跳去哪。

## Code: Cinux 实况:从交棒到交棒

往下咱们换真码走查。实况锚:r01_mbr——下面所有行号都按这一版的 `boot/mbr.cpp` 数,咱们拿 `git show r01_mbr:boot/mbr.cpp` 把它调到眼前,想在编辑器里翻就 `git switch --detach r01_mbr`,看完 `git switch -` 切回去,新克隆的仓回到的是 main。这段代码为什么长这样,正文里动机讲得很细,咱们不重叙,换一双机器层的眼睛:每条指令落在循环的哪一拍里,动了架构状态的哪几格。

起点是交棒。BIOS 把头一个扇区读进 0x7C00,远跳到 `boot/mbr.cpp:24 @ r01_mbr` 的 mbr_start——从这一拍起,取指循环念的是咱们的字节。交棒那刻的家底,正文里盘点过:CS:IP 指着咱们,DL 里揣着启动盘号,其余寄存器全是没定义的值。**停一拍,您掂量掂量**:在这么一片黑的世界里,机器下一拍念什么,靠什么定?

只靠一样——PC。别的格子是黑是白,循环一概不看,下一拍念什么,全凭 PC 眼下指着的地址。咱们顺着执行顺序往下过。

`mbr.cpp:25`,头一条就是远跳 `ljmp $0x0000, $mbr_real_start`,五个字节,编出来是 `ea 05 7c 00 00`,咱们反汇编量过。PC 的第二种走法,头一回在这儿登场:CS 和 IP 一次写齐,这一拍改的正是循环自己的输入,下一拍取指,读的已经是新地址上的字节。

前置卷里 SeaBIOS 上电的头一条也是远跳:复位那一下 CS 的口径是特殊的,固件得靠远跳拉回寻常算术。咱们头一条与它互为镜像。您在 QEMU 里跑会发现 CS 本来就是 0,这一跳看着像白跳:它写进 CS 的还是 0,写进 IP 的还是下一条的地址。它的活在于,不管 BIOS 交棒时两半各是什么,远跳一次都写成咱们指定的数,不沿用交棒留下的那套。想动 CS,只有连 IP 一起动的路,远跳干的正是这个。

`mbr.cpp:26` 是个标号 mbr_real_start。请您留意,标号一个字节都不占——PC 走过它像走过空气,架构状态里没有标号的户口,它是写给汇编器和咱们看的。`:27` 是 `xor %ax, %ax`,两个字节:AX 归零,标志位 ZF 顺手置 1。您看,连一个标志位都是架构状态,串指令往哪边走、条件跳转跳不跳,全拿它当依据,而 BIOS 退场时它是什么值,同样没人承诺过。

`:28` 到 `:30` 三条 mov,把刚归零的 AX 搬进 DS、ES、SS——三拍,每拍两个字节,PC 按指令长度直线往前。`:31` 是 `movw $0x7c00, %sp`:三个字节下去,SP 有值,栈在架构状态里立起来了。笔者这一趟单步,写它之前 SP 里还揣着 BIOS 留下的 0x6f18,写完,才是咱们说了算的 0x7c00。

栈往哪长、占哪块地的讲究,正文里铺得细,咱们机器层接着用:SS:SP 从没定义,变成了有定义。往后 push 有地方压,call 压下去的返回地址有处可放。

`:32` 是 `movb %dl, g_boot_drive`,四个字节:DL 里的盘号落进内存——寄存器和内存两摞家当,这一拍一边读一边写,写进去的格子按链接器排的地址在 0x7d4c。`:33` 是 cld,一个字节,DF 位清零。一比特也是架构状态,正文里管它叫保险,咱们机器层看得更直白:BIOS 退场时 DF 是什么值没人许过,cld 一声,DF 归了零,往后串指令往哪边走,全听它的。

`:34` 是 `call MbrMain`,又是第二种走法:call 也算跳转类,指令把 PC 整个写掉,外加多留一手,把返回地址压进刚立好的栈。咱们量过,call 本身落在 0x7c15,栈顶压着的返回地址是 0x7c1b。MbrMain 在源码里带着 `[[noreturn]]` 的声明,永不返回,那个地址用不上,call 还是照章法把它压好了。

call 自己还占得宽:整整六格,打头一个 0x66 前缀,把操作数宽度拨到另一套口径。从 `:25` 到这里手写的这一段汇编,咱们管它叫桩:机器一进门,踩的就是它铺的路。桩里是 16 位的习惯,C++ 编译器在同一个世界里保持着另一套宽度的习惯,0x66 就是替它拨宽度的那一下。单步到这儿,PC 一脚从 0x7c15 跨进 MbrMain 的门,这一脚跨得真利落,往后念的都是 C++ 编出来的字节。

接下来是 MbrMain 的地盘,C++ 的世界。串口报平安那几声,正文里陪作者听过一遍了,咱们这回只盯要紧的一拍:`boot/mbr.cpp:66`,int 0x13。PC 第三种走法登场——被中断拐走,顺着向量表进 BIOS 的代码。取指循环不认字节的出身,BIOS 的字节、咱们的字节、stage2 的字节,对它一视同仁。stage2 就是咱们引导的第二段:MBR 把它从盘上读进内存,再把机器交给它。BIOS 办完事,控制权连着装了新值的 AX 一起还回来,循环接着转。前面笔者摔的那一跤,摔的正是这个不问出身:那回 PC 指进了没加载的内存,念出一场事故。这一回 PC 指进 BIOS 的肚子里,办的是咱们请它办的读盘。

尾声 `mbr.cpp:73` 又是一条远跳,把 PC 连人带世界交给 stage2。咱们看着取指循环离开 mbr.cpp,再不回来,可循环自己不歇,换人供字节。桩的差事,到 call 把机器领进 C++ 就算完,后头 `:35-36` 还押着两条保命的:hlt 让取指暂停,机器睡,等中断来叫,叫醒之后接着走顺序的路,不算新走法。jmp 把 PC 写回上一条,两条指令一个环,循环转进自己的尾巴里。BIOS 报错的分支也是同款环,外加一串往 0xE9 端口写字节的指令,boot_failed 的报错就靠它送出去——QEMU 得挂上调试口,人才看得见。

从交棒到交棒,咱们到底看见了什么?中间隔着 BIOS 借道的读盘和串口的折腾,拍数根本数不清。数得清的是架构状态:CS、AX、段寄存器、SP、标志、PC,随便停在哪一拍的边界上,值都与顺序模型对得上。咱们拿 GDB 单步把桩数完,又拿断点接力到 stage2 接棒的 0x7e00,一路对下来,一格都没错过。

## 对照:第一条指令长什么样

同一件开场的事,换一套指令集,长相能差多远?咱们把 xv6 拉来对着看,它也是教学内核,RISC-V 的。下面引的页码都出自 xv6 书的 riscv-rev5 版。

xv6 的开场,书页 25 与 28 是这么记的,咱们照书里走一遍:上电后机器跑只读存储器里的引导加载器,加载器把内核复制进物理地址 0x80000000,然后跳进内核入口 _entry。为什么偏偏 0x80000000?书页 28 给了理由:0x0 到 0x80000000 那段地址住的是输入输出设备,内核住不得。_entry 开门头一件事是立栈:sp 装上 stack0+4096,栈顶,因为 RISC-V 的栈往下长,紧接着 call 进 C 的 start()。

咱们 x86 这边,落地头一条在远跳。xv6 那边,落地头一条在立栈。差别扎在指令集身上:实模式的 PC 是 CS:IP 两半折算出来的,BIOS 交棒时两半口径还不统一,头一条指令得把两半写死,不然下一拍取指的地址没个准。

RISC-V 没有段寄存器这一层,咱们把书页 28 顺带交代的一并搬来:它上电时分页硬件是关的,虚拟地址直接就是物理地址,PC 一根筋,第一条指令就能直奔正事。

复位落点也值得对一眼:x86 那边,Intel 手册把头一条指令写死在处理器最高物理地址往下 16 个字节,出处是 Intel SDM Vol 3A §9.1.4,前置卷拿复位读数逐项对过表。xv6 书里只说引导加载器住在只读存储器,没给复位地址,咱们能引的,也只有书里写了的。

咱们把难处也摆在一起看:x86 把几十年的兼容背在身上,复位后得从 16 位实模式开场,头几条指令常花在修口径上。RISC-V 开场是利索,可内核落点被设备住的地界定住,0x80000000 之下住不得。

咱们得坦白自己不做什么:引导只走 MBR 到 stage2 的两跳,交棒、铺世界、读盘挨个走一遍,是这套教程担的事。BIOS 肚子里的自检、枚举、那一整套服务,是另一门手艺,咱们不揽。

Linux 那边的第一指令落点,咱们还没逐字核过文献,这块留白——拿没核过的数往书里写,不是咱们的做法,核完再补。

咱们还该在这儿搁一句:C++ 标准里住着同款分离,名字叫 as-if 规则。编译器怎么重排、怎么合并、怎么删,都行,只要程序的可观察行为不变。咱们写 C++ 时从不追问编译器肚里干了什么,底气跟单步调试时一模一样。

您想核原文的话:xv6 书第 2 章开头几页,就是上面这一段的出处。Intel SDM Vol 3A §9.1.4,复位后处理器状态的官方口径。

## 这一章留下了什么

这一章走完,咱们攥在手里的都是些实在东西。五个字节 `b8 00 7c cd 10`,两拍,边界要等译码那一刻才见分晓。笔者摔的那一跤,PC 指进没加载的内存,机器照念不误。从 0x7c00 一路核到 0x7e00,停在哪个边界上,值都算得出、对得上。读代码敢按一行一行想,靠的也是规格:取指循环一条一条花家当,是 ISA 写明的,不是实现里排的队。下一章咱们把家当摊开,细看字节、寄存器和栈怎么互相搬东西。

## 练一练

光读不跑,这一章咱们就白走一半。头一道动手,第二道猜想,第三道对着屏幕想。

**题一,动手。** 把 r01_mbr 的镜像跑起来,挂上 GDB,在 0x7c00 断住,亲眼看 ljmp 前后 CS 和 PC 各是什么。命令咱们实测过,照敲就行:

```bash
git switch --detach r01_mbr
cmake -B build && cmake --build build --target boot_image
timeout 120 qemu-system-i386 -drive format=raw,file=build/boot/cinux.img \
  -nographic -display none -no-reboot -S -gdb tcp:127.0.0.1:1235 &
```

QEMU 挂在后台,冻在复位那一点上等您,同一个终端接着敲:

```bash
gdb -q -nx -batch \
    -ex 'target remote 127.0.0.1:1235' \
    -ex 'break *0x7c00' \
    -ex 'continue' \
    -ex 'info registers cs' \
    -ex 'x/i $pc' \
    -ex 'si' \
    -ex 'info registers cs' \
    -ex 'x/i $pc' \
    -ex 'detach'
```

跑完 GDB 自己退。continue 敲下去之后,终端里会涌进 SeaBIOS 和 iPXE 自家的几行吆喝,什么 Press Ctrl-B、Booting from Hard Disk,那是固件出场的动静,不是咱们的字节,别被带跑。QEMU 裹在 timeout 里,到点自己收走,不想等就把后台任务收掉。最后 `git switch -` 切回您来的地方,新克隆的仓回的是 main。

**题二,猜想。** SeaBIOS 按 0000:7C00 交棒,cs 进来是 0。您换个按 07C0:0000 交棒的 BIOS 想想:ljmp 执行完,cs 是多少,下一拍取指的线性地址是多少?跟 QEMU 里比,变的是哪样,不变的又是哪样?

**题三,对着屏幕想。** GDB 在 0x7c00 念出的 ljmp,和您反汇编 mbr.bin 看到的头一条,一字不差吗?差不上的话,是机器错了,还是眼睛的口径错了?反汇编这么下:

```bash
objdump -D -b binary -m i8086 -Mintel build/boot/mbr.bin | head
```

### 参考答案

题一:断住时 GDB 报 `0x00007c00`,`cs` 是 0x0——SeaBIOS 按 0000:7C00 交棒,CS 进来就是平的。单步一脚,`$pc` 落到 0x7c05,cs 还是 0x0。咱们实测的屏,关键几行长这样:

```text
Breakpoint 1, 0x00007c00 in ?? ()
cs             0x0                 0
=> 0x7c00:	ljmp   $0xc031,$0x7c05
0x00007c05 in ?? ()
cs             0x0                 0
=> 0x7c05:	xor    %eax,%eax
```

ljmp 把 CS:IP 一次写齐成 0x0000:0x7c05。写之前 CS 本来就是 0,所以数值上瞧不出动静——这正是它的用处:不管 BIOS 什么口味,写完都一个样。下一拍取指落在 0x7c05,mbr_real_start 那儿,正是咱们反汇编量过的 `ea 05 7c 00 00` 的落点。至于屏里 ljmp 念歪的半截,题三专门伺候它。

题二:cs 变成 0x0000,下一拍的线性地址还是 0x7c05,跟咱们在 QEMU 里看到的一模一样。变的只有写之前那一下:另一种 BIOS 交棒时 cs 是 0x07c0、IP 是 0,折出来同一个 0x7C00。两种姿势,远跳一落地,世界一模一样,这就是头一条指令非它不可的理由。

题三:差得不少,而机器一个字节都没错。GDB 念的是 `ljmp $0xc031,$0x7c05`,objdump 按 16 位口径念的是 `jmp 0x0:0x7c05`。段值那半截,GDB 咬出来个 $0xc031,乍看真像那么回事,咱们拿字节一对就露馅:那其实是紧跟着的 xor 的两个字节 `31 c0`。它把远跳的偏移按四格咬,段值就咬到了别人身上。字节一个没换,解码器按哪套宽度下嘴,切出来的指令就不一样,前置卷里讲计算机怎么工作的那一卷,开篇把五个字节读出两种结果,讲的就是它。还有一处同款:0x7c05 的 xor,GDB 念成 `%eax` 口径,objdump 念 `%ax`,又是宽度口径差的另一面。
