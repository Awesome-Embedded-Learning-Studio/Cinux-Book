## 1. tag 粒度规则(怎么界定"这是一个 tag")

tag 的根本属性是 **kernel 源码到达一个可教学、可构建、可运行的绿色状态**(不是"我写了一章")。章节是叙事单位、tag 是源码单位,通常 1:1,但 tag 是 ground truth。

**四条判据(从现有 43 tag 反推,全要满足)**:
1. **单一新能力**:让系统"现在能做到一件之前做不到的事",一个 punchline。干了两件事 → 拆。
2. **绿**:`cmake --build` + QEMU `run` 都过。不在重构半途打 tag。
3. **一章装得下**:能在一篇 book 章讲透。装不下 → 拆字母子 tag。
4. **可验证**:lab 能让读者复现"现在 OS 能干 X"。

**新号 vs 字母后缀**:
- **给新号**(如 `015` PMM → `016` VMM → `017` heap):换了**机制/子系统**。判据:新机制 → 新号。
- **给字母**(如 `028` ext2 读 → `028b` 写 → `028c` cwd → `028d` sync):**同一机制**在扩展/打磨。判据:同机制延伸 → 字母。
- 字母风格:`028b`(小写、无下划线)。**不用** `004_A`(早期废弃风格)。

**回迁切 tag 第一刀**:**CinuxOS 的 milestone(M1-Mn)天然就是一个绿状态+一个新能力 → 一个候选 tag**。然后套上面规则:milestone 太大→拆字母;milestone 换机制→新号;同机制扩展→字母。

**验证档(每个 tag 必落一个档,决定 lab 形态)**:不是每个 tag 都要"用户可见现象",但每个 tag 都要有**可验证信号**——一个"tag 前做不到、tag 后做得到"的具体动作。分三档:
- **A 功能档**:OS 多了一项用户能看/能用的新能力。lab = reader 真去做那件事(写文件 / ping / 捕获 SIGSEGV)。本 roadmap 29 tag。
- **B 机制/重构档**:内部改写,**无新用户能力**,但有清晰 before/after 信号。lab = reader 跑测试 / 看指标 / 量差异(碎片率、boot 日志、地址随机化)。比 A 轻。~10 tag。
- **C 工具/可观测档**:加调试/工具能力。lab = reader 触发调试路径看新输出(panic 符号化栈、lockdep 报告)。~4 tag。
- **硬规则**:找不到任何 before/after 差异的 tag ≈ 没教学 punchline ≈ **不该单独成 tag**(并入相邻或砍)。每 tag 的档见 §3 表"验证档"列。

## 2. 单 tag 执行循环(patch-replay,每个 tag 都走一遍)

每个 Book tag = CinuxOS 时间序里**一组 first-parent 步**(通常 1 个 PR,大里程碑几个 PR)。以一个 tag 为例:

1. **定位 + 笔记抓手**:查附录,确认本 tag 对应哪几个 CinuxOS 步(commit/PR#)。然后:
   - `python3 tools/replay.py notes <n>` 找**命中的 dev note**(CinuxOS 309 篇,按日期±2 天 + 弧关键词匹配)。
   - **读 note 当抓手**:它有设计意图 / 踩坑叙事 / 验证数据,是教学原料。
   - **实际考察**:`grep`/`read` CinuxOS 源码核对 note 说的机制(note 是提示**不是福音**,以源码为准)。
   - 再进 patch-replay + 写章。没命中 note 就直接 `git -C ~/CinuxOS show <sha>` 看源码。
2. **打 patch**(核心,替代"手工搬码"):
   ```bash
   git -C ~/CinuxOS format-patch -1 <step-sha> --stdout > /tmp/p   # 该步相对父的净 diff
   git -C ~/Cinux am --3way /tmp/p                                  # 基底 366 文件一致→基本干净 apply
   ```
   多步拼一个 tag 就逐个 am。偶尔 context 漂移 → `--3way` 或手收(几乎都在那 ~4 个 CMake 文件上,§0.5)。
3. **构建 + 跑(= 1:1 客观验证)**:
   ```bash
   cmake --build build -j$(nproc) && cmake --build build --target run
   ```
   绿 = 这个 CinuxOS 增量在 Book 上 1:1 复现。红 → 多半踩在那 4 个 CMake 文件或漏了前置步,定位修。
4. **写章**:代码已绿、行号是 patch 刚落下的真值 → `grep -n` 抽进章节,讲 why/how/踩坑(踩坑从该步 dev note 重构)。中文、不是答案堆。代词用**「咱们 / 你 / 笔者」**(不用「我们 / 我」)。
   > ⚠️⚠️ **铁律:写的是教程,不是 CinuxOS 变更汇报**(2026-07-21 作者痛批)。把自己当**教读者一个 OS 概念的老师**,不是**汇报"这个 milestone 干了啥"的记者**。**丢掉过程产物**:批号(批1/批2/批3)、GOTCHA 编号(GOTCHA #7)、commit SHA/PR 号、「从迁移笔记搬来」「本弧摩擦:#N 冲突」、run-kernel-test 计数、CinuxOS 的「产出表格」结构。dev note 是**事实/调试原料**,要提炼成**概念讲解**,不照搬它的工程叙事。范本:`document/book/15-smp/051-percpu-ap-conboot.md`(作者亲改)——概念先行、读者视角、诚实划边界、零脚手架。详见记忆 `cinux-tutorial-not-changelog`。
5. **lab**(按 §1 验证档):A=reader 真做那件事;B=跑测试/看指标;C=触发调试路径看输出。
6. **humanize + 叠风格(写完教程必走,不可跳)**:按 `.claude/tools/humanizer-zh/SKILL.md` 走**手术式**(别跑全套磨平文风,判定见记忆 `cinux-humanizer-voice`)——
   - 代词:**我→笔者、我们→咱们、你们→你**;移除 AI-isms(至关重要/此外/彰显/格局/深入探讨/「钉死」式等空洞词)。
   - **去完 AI 话,再叠一轮作者风格**:保留「不是 A 而是 B」技术对比、系列意象(夯地基/承重柱)、调试五段标签、折腾感口语、笔者见证、做活破折号、诚实承认不完美。这些是文风指纹,不是 slop,别磨。
7. **注册 + VitePress 构建验证**:章 + lab 挂 `project.config.ts`/sidebar.ts(章节放 `document/`,规划放 `meta/`);`npm run build` 干净(humanize 后**再**验一次)。
8. **提交 + 打 tag(最后一步,完整 commit)**:把源码 + 章 + lab(humanize 后)一起提交;**`git tag 0NN_<topic>` 打在「源码 + 章 + lab + humanize 都齐」的完整 commit 上**。
   > ⚠️ **铁律:tag = 完整状态**。tag 是读者 checkout 的快照点,必须同时含源码(绿)+ book 章 + lab。**别在源码刚绿就先打 tag、章节后面补** —— 那样 checkout tag 看不到本章教学。tag 永远是 §2 循环的**最后一步**。

> **卡住协议**:`git am` 反复冲突超 3 次 → 多半漏了前置步或踩那 4 个 CMake 文件,停下查附录依赖 + 写 handoff(§6),不 thrash。

## 6. 并行会话协同规则(patch-replay 版)

- **replay 基本串行**:按附录时间序做**下一个** ⬜ tag,不要跳序(跳序 patch 必冲突)。在附录表 tag 行写 owner 标记认领。
- 唯一并行:「tag N 的文档写作」与「tag N+1 的 patch 打 + 构建」可分给两个会话(但 N+1 的 patch 要等 N 的 patch 已 am)。
- 不并发改全局文件(`project.config.ts`、`sidebar.ts`、本 roadmap、`CLAUDE.md`)。
- 不并发往同一 replay 链打 patch(撞 context)。
